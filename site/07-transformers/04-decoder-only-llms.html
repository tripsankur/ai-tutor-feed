Track 7 · Transformer Architecture · Episode 4

Decoder-Only LLMs: Training Objective, BPE Tokenization, Embeddings

17 min listen · The two ends of the building: a cutting table that turns text into tokens by merging frequent byte pairs, a wall of pigeonholes that turns tokens into vectors, a rooftop scoreboard that scores every possible next token, and a grader measuring surprise — how one simple objective, predict the next token, trains a decoder-only LLM.

Facts verified: 2026-09-25

One-sentence thesis

A decoder-only LLM is a pipeline of tokenizer (BPE) → embedding lookup → causal transformer stack → output projection to vocabulary logits → softmax, trained with one self-supervised objective — next-token cross-entropy at every position in parallel — which turns raw text into trillions of free labeled examples.

The mental image: the two ends of the building

  • Cutting table (ground floor, left) = tokenizer: byte-level BPE cuts text into pieces.
  • Pigeonhole wall (ground floor, right) = embedding table: one hole per vocab ID, each holding a d_model-wide card.
  • The building from episode 3 = the causal transformer stack.
  • Rooftop scoreboard = unembedding / LM head: one light per vocab entry → logits → softmax.
  • Grader beside the scoreboard = cross-entropy loss: surprise at the true next token; every tile graded at once behind the causal curtain (teacher forcing).
flowchart LR
    T["Raw text"] --> TOK["BPE tokenizer: text to token IDs"]
    TOK --> EMB["Embedding lookup: V x d table"]
    EMB --> STACK["N causal transformer blocks (RoPE, GQA, RMSNorm, SwiGLU)"]
    STACK --> FN["Final RMSNorm"]
    FN --> HEAD["LM head: d x V (optionally tied to embeddings)"]
    HEAD --> SM["Softmax over vocab"]
    SM --> LOSS["Cross-entropy vs true next token (every position)"]

BPE training in miniature

# Byte-level BPE, conceptually
vocab = {bytes([b]) for b in range(256)}       # 256 base tokens: nothing is ever out-of-vocabulary
corpus = [list(word.encode()) for word in sample_text_split]
while len(vocab) < TARGET_VOCAB:               # e.g. 32K, 128K, 200K
    pair = most_frequent_adjacent_pair(corpus) # e.g. (b"t", b"h")
    corpus = merge(corpus, pair)               # b"th" becomes one token everywhere
    vocab.add(pair[0] + pair[1])               # merges are applied in learned order at encode time

# Counting tokens (OpenAI tokenizers)
import tiktoken
enc = tiktoken.get_encoding("o200k_base")
print(len(enc.encode("How many r's are in strawberry?")))
print([enc.decode([t]) for t in enc.encode("strawberry")])   # pieces, not letters

Rule of thumb (English): 1 token ≈ ¾ word → 1,000 words ≈ 1,300 tokens. Underrepresented languages can need several times more tokens for the same content.

The objective

Loss = − (1/T) Σ_t  log p_θ( x_{t+1} | x_1 … x_t )        (cross-entropy, averaged over all positions)
Perplexity = exp(Loss)
Random init baseline: Loss ≈ ln(V)  → ln(128,256) ≈ 11.76
  • Teacher forcing: each position conditions on the real prefix; causal mask means one forward pass yields T predictions.
  • Scale example: Llama 3 405B — 15.6T training tokens, ~3.8 × 10²⁵ FLOPs (≈ 6 × params × tokens).

Embeddings

  • Lookup table E ∈ R^{V × d}; context-free (same "bank" vector everywhere); layers add context.
  • No position in the embedding for RoPE models — position enters in attention.
  • Size: 128,256 × 4,096 ≈ 525M params (big share of an 8B model); 128,256 × 16,384 ≈ 2.1B (≈0.5% of 405B).
  • Weight tying: LM head reuses E (common in small models, e.g. Llama 3.2 1B/3B) to save parameters.

Architecture families

Family Attention Objective Good at Examples
Encoder-only Bidirectional Masked-token prediction Classification, retrieval embeddings BERT family
Encoder-decoder Bidirectional encoder + causal decoder + cross-attention Seq2seq / span corruption Translation, summarization with paired data Original Transformer, T5
Decoder-only Causal Next-token prediction General generation, everything-as-continuation GPT, Llama, Mistral, DeepSeek

Pitfalls

  • Character-level blindness (letter counting, reversal, spelling): model sees subword tokens.
  • Numbers tokenized inconsistently hurt arithmetic; some tokenizers split digits into fixed small groups.
  • Language token tax: cost, context, and latency scale with tokens, not words — measure per language before forecasting (war story: multi-market support assistant ran >2× forecast spend and hit context truncation).
  • Tokenizer / chat-template mismatch: wrong tokenizer, missing special tokens, or wrong template → silently degraded outputs, no error. Always use the model's own tokenizer and tokenizer.apply_chat_template.
  • Pretraining ≠ assistant: instruction following and preferences come from post-training (episode 7).

5 interview questions

Q1. What is the pretraining objective of a decoder-only LLM? Next-token prediction with cross-entropy, at every position simultaneously thanks to the causal mask (teacher forcing). Self-supervised — text is its own label — so it scales to trillions of tokens. Instruction-following comes from post-training.

Q2. Explain BPE and the vocabulary-size tradeoff. Start from bytes; repeatedly merge the most frequent adjacent pair until reaching the target vocab. Larger vocab → shorter sequences (cheaper attention, more effective context, often better multilingual coverage) but a larger embedding/LM-head matrix and rarer per-token training signal.

Q3. Why do LLMs struggle to count letters, and why do some languages cost more? They operate on subword tokens, not characters. Merges were learned on a skewed data mix, so underrepresented languages fragment into more tokens — more cost, less effective context, slower generation.

Q4. Why did decoder-only architectures win over encoder-decoder for general LLMs? One simple objective on unlabeled text; native generation; every task can be framed as continuation; one stack is simpler to scale and serve (single KV cache). Encoders remain strong for embeddings/classification.

Q5. You fine-tuned a chat model and outputs ramble and never stop. First thing to check? Tokenizer and chat template: correct model tokenizer, the model's own chat template, special/end-of-turn tokens present in training data and in inference, and EOS handling in generation config.
