Track 7 · Transformer Architecture · Episode 5

Inference: KV Cache, Sampling, Speculative Decoding

18 min listen · What actually happens between hitting enter and seeing tokens stream back: prefill versus decode, why the KV cache turns inference into a memory problem, how sampling picks each word, and how speculative decoding lets a small draft model buy speed without changing a single output.

Facts verified: 2026-09-25

One-sentence thesis

LLM inference is an autoregressive loop whose decode phase is memory-bandwidth-bound, so serving performance is decided by how you manage the KV cache (size, paging, sharing, batching), how you pick each token (sampling), and whether you can verify several tokens per expensive forward pass (speculative decoding).

The mental image: the shelf and the cabinet

  • Shelf (left → right) = the token sequence; prompt on the left, the answer grows at the right end.
  • Many-floored machine above = the transformer; one floor per layer.
  • Cabinet below = the KV cache; one folder per token, one slip per layer, each with a key stamp and a value stamp. Written once, read forever (causal mask).
  • Spinning wheel at the right end = sampling over the vocabulary distribution.
  • Apprentice with a pencil = the speculative draft model; the master verifies pencilled cards in one pass, inks the accepted prefix, erases from the first rejection.

Prefill vs decode

Prefill Decode
Tokens per pass whole prompt 1 (or k+1 with speculation)
Bottleneck compute (FLOPs) memory bandwidth (stream weights + KV)
User-facing metric time to first token (TTFT) inter-token latency / tokens per second

Rough bound: decode time per token ≥ (bytes of weights + bytes of KV read) / memory bandwidth. A 70B model in BF16 ≈ 140 GB of weights; at a few TB/s that's tens of ms per step for a batch — which is why batching (weights read once, shared by the batch) is the main throughput lever.

Sizing the KV cache

$$\text{KV bytes per token} = 2 \times n_\text{layers} \times n_\text{kv heads} \times d_\text{head} \times \text{bytes per element}$$

Model shape (Llama-3-style) Layers KV heads (GQA) d_head Per token (BF16) At 128K tokens
8B 32 8 128 2·32·8·128·2 = 131,072 B ≈ 128 KB ≈ 16 GB
70B 80 8 128 327,680 B ≈ 320 KB ≈ 40 GB

Total KV memory = per-token × sequence length × concurrent sequences. With 32 query heads and no GQA, the 8B case would be 4× larger.

def kv_bytes(layers, kv_heads, d_head, seq_len, batch=1, bytes_per=2):
    return 2 * layers * kv_heads * d_head * bytes_per * seq_len * batch

print(kv_bytes(32, 8, 128, 128_000) / 2**30)   # ~15.6 GiB for one 128K sequence

PagedAttention (vLLM)

  • Prior systems pre-reserved contiguous KV space per request for max length → 60–80% of KV memory wasted (fragmentation + over-reservation).
  • PagedAttention splits KV into fixed-size blocks (e.g. 16 tokens) mapped via a block table, like OS virtual memory → waste < 4% (only the last block), 2–4× throughput vs prior SOTA at the same latency (SOSP 2023).
  • Enables prefix caching / block sharing: many requests with the same system prompt point to the same blocks (copy-on-write).
  • Related: continuous batching (insert new requests at every decode step), chunked prefill, prefill/decode disaggregation.

Sampling cheat sheet

Knob Effect on the "wheel" Use
Greedy (argmax) take the widest slice extraction, classification; can loop on long text
Temperature T logits / T; T<1 sharpens, T>1 flattens 0–0.3 factual; 0.7–1.0 creative
Top-k keep k most likely tokens crude truncation
Top-p (nucleus) keep smallest set with cumulative prob ≥ p adaptive truncation
Min-p keep tokens with p ≥ min_p × p_max robust at higher temperatures
Repetition / frequency penalties down-weight tokens already generated reduce loops
Constrained / structured decoding mask tokens that violate a grammar/JSON schema guaranteed-valid structured output

Caveat: T=0 is not guaranteed bit-reproducible in production — batch-dependent floating-point reduction order can flip near-ties.

Speculative decoding

sequenceDiagram
    participant D as Draft (apprentice)
    participant T as Target (master)
    D->>D: propose k tokens autoregressively (cheap)
    D->>T: k draft tokens
    T->>T: ONE forward pass scores all k positions
    T-->>T: accept prefix via rejection sampling
    T->>D: accepted n tokens + 1 corrected/bonus token
  • Acceptance rule (Leviathan et al. 2022; Chen et al. 2023): accept draft token x with prob min(1, p_target(x)/p_draft(x)); on rejection resample from the normalized residual max(0, p_target − p_draft). Output distribution is identical to the target model — lossless.
  • Draft sources: small same-family model (shared tokenizer), Medusa heads, EAGLE / EAGLE-3 (draft head over target hidden states; vLLM reports up to ~2.5× speedups; EAGLE 3.1 and P-EAGLE landed in vLLM in 2026), n-gram / prompt lookup (great for code edits, RAG echoing sources), MTP heads (DeepSeek-V3 trained a multi-token-prediction module usable for speculation).
  • Wins at low/moderate batch where GPU compute is idle; gains shrink at large batch; depends on acceptance rate (predictable text ≫ high-temperature creative text).
# vLLM (illustrative; check current docs for exact keys)
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct",
          speculative_config={"method": "eagle3", "model": "<eagle3-draft-head>", "num_speculative_tokens": 4},
          enable_prefix_caching=True, kv_cache_dtype="fp8")
out = llm.generate(["Explain the KV cache."], SamplingParams(temperature=0.7, top_p=0.9, max_tokens=256))

5 interview questions

Q1. Why is decode memory-bound while prefill is compute-bound? Prefill multiplies the weights against many tokens at once, so each byte of weight loaded does lots of FLOPs. Decode processes one new token per sequence, so each step streams all weights (and that sequence's KV) for very little arithmetic — the GPU waits on HBM bandwidth. Batching raises arithmetic intensity by sharing weight reads.

Q2. Estimate the KV cache for an 8B GQA model at 128K context. 2 × 32 layers × 8 KV heads × 128 dims × 2 bytes ≈ 128 KB per token → ≈ 16 GB per 128K sequence — as large as the BF16 weights. So concurrency for long contexts is limited by KV memory, not weights.

Q3. What problem does PagedAttention solve? Contiguous per-request pre-allocation wasted 60–80% of KV memory. Paging into fixed-size blocks with a block table cuts waste to under 4%, allows larger batches (2–4× throughput), and enables prefix sharing across requests.

Q4. Is speculative decoding an approximation? No. With the rejection-sampling acceptance rule the output distribution equals the target model's. It trades extra (otherwise idle) compute for fewer sequential target passes; speedup depends on acceptance rate and batch size.

Q5. Why do providers charge more for output tokens than input tokens, and less for cached input? Input tokens are processed in parallel in prefill; output tokens each require a memory-bound sequential decode step. Cached input reuses existing KV blocks, skipping prefill compute for that prefix.

When they ask, "What is the K V cache and why does it exist?" — "Because of the causal mask, past tokens' keys and values never change, so we compute them once per layer and store them, turning quadratic recomputation into linear reads. The cost is memory: about a hundred and twenty-eight kilobytes per token for an eight-billion model with grouped-query attention, so sixteen gigabytes at a hundred-and-twenty-eight-thousand context. Mitigations are grouped-query or latent attention, K V quantization, paging, and prefix caching." When they ask, "How does speculative decoding work, and does it change outputs?" — "A cheap draft proposes several tokens, the target model verifies them all in one forward pass, keeps the longest accepted prefix, and substitutes its own token at the first rejection. With the rejection-sampling acceptance rule the output distribution is identical to the target model alone, so it is lossless. It pays when acceptance rates are high and batch sizes are modest." And if they ask about temperature zero being deterministic, you now know the honest answer: mostly, not guaranteed, because of batch-dependent floating-point effects. [PAUSE 2s] ## Sixty-second recap Re-walk the picture. The long shelf of cards, left to right, one card per token, prompt on the left, the answer growing at the right. Above it, the many-floored machine, one floor per layer. Prefill lays the whole prompt down at once — compute-bound, sets time to first token. Then decode, one card at a time, each step streaming every weight in the machine — memory-bound. Below the shelf, the cabinet: one folder per card, key and value stamps for every floor, computed once and reused forever thanks to the causal mask. It grows with every card and every user, and it is why memory fills while compute idles. PagedAttention chops it into drawers, prefix caching shares drawers, grouped-query attention and quantization shrink the folders. At the right end, the wheel: temperature sharpens or flattens it, top-k and top-p trim it, constrained decoding masks illegal slices. And beside the wheel, the apprentice with the pencil: draft several cards, let the master verify them in one pass, ink the accepted run, erase at the first disagreement — same output distribution, fewer expensive steps.
