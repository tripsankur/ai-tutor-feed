Fine-Tuning Landscape: LoRA/PEFT, RLHF, DPO

16 min listen · How a raw pre-trained model becomes a useful assistant: supervised fine-tuning, LoRA and QLoRA for doing it cheaply, preference tuning with RLHF and DPO, and the reinforcement learning with verifiable rewards and on-policy distillation that power today's reasoning models.

Facts verified: 2026-09-25

One-sentence thesis

Post-training turns a knowledgeable next-token predictor into a useful assistant in stages — SFT for behaviour and format, preference tuning (RLHF or DPO) for "better vs worse", and RL with verifiable rewards (GRPO family, plus on-policy distillation) for reasoning — and parameter-efficient methods like LoRA/QLoRA make most of it affordable on one GPU.

The mental image: the great console

  • Great console against the back wall = the base model; billions of knobs (parameters) set by pre-training; mostly taped down (frozen).
  • Clip-on panel at its side = LoRA adapter; two thin strips (low-rank A and B) are the only trained knobs.
  • Classroom (left) = SFT on worked examples.
  • Judging table (middle) = preference pairs → RLHF (reward model + PPO) or DPO.
  • Practice arena with scoreboard (right) = RLVR with GRPO/DAPO; teacher grading each token = on-policy distillation.
flowchart LR
    B["Base model (pre-trained)"] --> S["SFT: instruction/response pairs, loss on response tokens"]
    S --> P{"Preference tuning"}
    P --> R1["RLHF: reward model + PPO + KL to reference"]
    P --> R2["DPO: direct loss on chosen vs rejected"]
    R1 --> V["RLVR: GRPO / DAPO with verifiers (tests, exact match)"]
    R2 --> V
    V --> OPD["On-policy distillation: student samples, teacher scores every token"]
    OPD --> A["Deployed assistant / reasoning model"]
    L["LoRA / QLoRA adapters"] -.->|can be applied at any stage| S
    L -.-> R2

Memory: why full fine-tuning hurts

Mixed-precision Adam ≈ 16 bytes/param (BF16 weights 2 + grads 2 + FP32 master 4 + Adam m 4 + v 4), before activations.

Model Full FT (≈16 B/param) LoRA (frozen BF16 base) QLoRA (4-bit base)
7–8B ~115–130 GB ~16–20 GB + adapters ~6–10 GB
65–70B ~1.1 TB ~140 GB fits a single 48 GB GPU (QLoRA paper)

LoRA and QLoRA

$$W' = W_0 + \Delta W = W_0 + \frac{\alpha}{r} B A,\quad B \in \mathbb{R}^{d \times r},\ A \in \mathbb{R}^{r \times k},\ r \ll \min(d,k)$$

  • W₀ frozen; only A, B trained. LoRA paper (GPT-3 175B): ~10,000× fewer trainable params, ~3× less GPU memory, no added inference latency once merged.
  • Typical r = 8–64; target attention projections or all linear layers.
  • QLoRA: 4-bit NF4 frozen base + double quantization + paged optimizers; 65B on one 48 GB GPU at 16-bit fine-tuning quality.
  • Multi-LoRA serving: one base in memory, many adapters swapped per request.
  • "LoRA learns less and forgets less": less capacity for big distribution shifts, less catastrophic forgetting.
from peft import LoraConfig, get_peft_model

RLHF vs DPO vs GRPO

RLHF (InstructGPT, 2022): SFT → reward model on pairwise comparisons → PPO maximizing reward − β·KL(π‖π_ref). Four models in memory (policy, reference, reward, value). InstructGPT 1.3B was preferred by labelers over 175B GPT-3.

DPO (Rafailov et al., 2023): no reward model, no sampling:

$$\mathcal{L}\text{DPO} = -\log \sigma!\left(\beta \log\frac{\pi\theta(y_w|x)}{\pi_\text{ref}(y_w|x)} - \beta \log\frac{\pi_\theta(y_l|x)}{\pi_\text{ref}(y_l|x)}\right)$$

Relatives: KTO (unpaired thumbs-up/down), ORPO (folds SFT in), SimPO (reference-free). Offline — cannot explore.

RLVR + GRPO: reward = verifier (unit tests, exact-match math, schema check). "RLVR" named in AI2's Tülu 3. GRPO (DeepSeekMath, then DeepSeek-R1): sample G completions per prompt, advantage = (r_i − mean(r)) / std(r), clipped policy-gradient update with KL; no value model.

  • DAPO: removes length bias and stabilizes training — the default loss_type in TRL's GRPOTrainer. GSPO: sequence-level importance weights (reproduce in TRL with importance_sampling_level="sequence", loss_type="grpo").
  • On-policy distillation: student generates; teacher assigns per-token reverse-KL grades. Thinking Machines reported ~70% AIME'24 for Qwen3-8B-Base (teacher Qwen3-32B) at ~1/10 the compute of RL. 2026 research pipelines commonly combine OPD with RLVR.
Method Signal Models in memory Online? Main risk
SFT demonstrations 1 no imitation ceiling, forgetting
RLHF (PPO) learned reward model 4 yes reward hacking (verbosity, sycophancy), instability
DPO preference pairs 2 no stale off-policy data
GRPO/DAPO (RLVR) verifier 2 (+ rollout engine) yes verifier gaming, compute for rollouts
On-policy distillation teacher per-token 2 yes capped by teacher quality

def correctness_reward(completions, answer, **kw):
    return [1.0 if c.strip().endswith(a) else 0.0 for c, a in zip(completions, answer)]

5 interview questions

Q1. When should you fine-tune rather than use RAG or prompting? Prompt first (cheapest iteration). RAG for knowledge that changes or needs citations. Fine-tune for behaviour — format, tone, tool-calling patterns, domain phrasing, latency/cost via distilling into a smaller model. Fine-tuning is a poor, uncitable way to inject facts.

Q2. How does LoRA work and why is it popular? Freeze W₀ and learn ΔW = BA with small rank r on selected layers. Trainable params and optimizer memory drop by orders of magnitude, adapters are megabytes, can be merged (no latency) or hot-swapped per tenant. QLoRA adds a 4-bit frozen base so a 65B model fits on one 48 GB GPU.

Q3. Compare RLHF and DPO. RLHF: reward model from preferences, then online PPO with a KL tether — powerful but four models, unstable, reward-hackable. DPO: closed-form loss on the same preference pairs against a frozen reference — no reward model or sampling, cheap and stable, but offline.

Q4. What is GRPO and why did it matter for reasoning models? For each prompt sample a group of completions, score with a verifier, and use each completion's reward relative to the group mean/std as its advantage — no value network. Paired with verifiable rewards (RLVR) it scaled RL cheaply and produced emergent long chain-of-thought in DeepSeek-R1; DAPO/GSPO refine its stability and length bias.

Q5. What can go wrong in post-training? Reward hacking (verbosity, sycophancy, gaming tests), catastrophic forgetting (including safety), chat-template mismatch between training and serving, overfitting to eval sets that overlap training data, and verifier weaknesses. Mitigate with broad regression evals, KL tethers, mixed general data, LoRA, and robust verifiers.
