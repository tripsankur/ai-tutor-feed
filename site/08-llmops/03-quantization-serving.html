Track 8 · LLMOps + Prompting · Episode 3

Quantization & Efficient Serving

18 min listen · Inside the GPU warehouse: why generating text is limited by memory bandwidth, how quantization shrinks the weight crates, and how paged KV cache, continuous batching, prefix caching and speculative decoding turn one expensive GPU into a high-throughput server.

Facts verified: 2026-09-25

One-sentence thesis

LLM decode is memory-bandwidth bound: every generated token re-reads all the weights. So the two big levers are quantization (move fewer bytes) and batching (more tokens per pass over the weights). Paged KV cache, continuous batching, prefix caching, chunked prefill, and speculative decoding are how modern engines make batching work.

The mental image: the GPU warehouse

  • Room = one GPU. Floor space = HBM (H100 80 GB, H200 141 GB).
  • Left wall, crates = model weights (static, shared by every request).
  • Right wall, shelves = KV cache (per conversation, grows by one slot per token).
  • Center, workers = compute cores.
  • One conveyor = memory bandwidth (~3.35 TB/s on H100 SXM). During decode, the whole left wall rides it for every token.

Back-of-envelope formulas

  • Weights memory ≈ params × bytes/param. 70B: FP16 140 GB, FP8 70 GB, INT4/FP4 ~35–40 GB.
  • Single-stream decode ceiling ≈ bandwidth ÷ weight bytes. 3.35 TB/s ÷ 70 GB ≈ ~48 tokens/s.
  • KV cache per token = 2 (K and V) × layers × KV heads × head_dim × bytes. For Llama-3-70B-class (80 layers, 8 KV heads, head_dim 128, FP16): 2×80×8×128×2 ≈ 0.33 MB/token. 4K context ≈ 1.3 GB. 128K ≈ 40+ GB.
  • Worked sizing: 2×H100 (160 GB) − 70 GB FP8 weights − ~10 GB overhead ≈ 80 GB KV. That's ~60 conversations at 4K with an FP16 KV cache, ~120 with an FP8 KV cache, or ~2 at 128K.

Quantization formats

Format What Hardware Quality rule of thumb
FP8 (W8A8) 8-bit float weights + activations Hopper (H100/H200) and newer Near-lossless for most large models; default first step
AWQ / GPTQ 4-bit weight-only, protects salient weights Broad Usually OK on chat; can regress on math/code/extraction
NVFP4 4-bit float, 16-element blocks with FP8 scale Blackwell ~2x throughput over FP8; vendor-reported ≤~1% loss on large reasoning models (verify on your own eval set)
GGUF File format for llama.cpp / local runtimes, many bit widths CPU / Apple / consumer GPU Local and edge use
FP8 KV cache Halves KV memory Engine flag Often worth more than weight quantization for long context

Engine techniques

Technique Problem it fixes How
Continuous batching Static batches idle while the longest request finishes Iteration-level scheduling: requests join and leave after every decode step
PagedAttention (vLLM) Contiguous max-length KV reservations waste 60–80% of memory (vLLM paper) Fixed-size KV blocks (default 16 tokens) + block table; waste drops to a few %
Prefix caching Repeated system prompts recomputed per request Share KV blocks for identical prefixes (vLLM automatic; SGLang RadixAttention)
Chunked prefill Huge prompts stall ongoing decodes Split prefill into chunks interleaved with decode
Speculative decoding Idle compute during decode Draft model/heads (EAGLE family) propose k tokens; target verifies in one pass. Lossless output distribution; ~2–3x when acceptance is high; best at low batch
Tensor / pipeline parallelism Model too big for one GPU Split layers' weights across GPUs (TP, intra-node) or layer groups across nodes (PP)
Disaggregated prefill/decode Prefill is compute-bound, decode bandwidth-bound Separate GPU pools, hand off KV cache

Engines (as of 2026-09-25)

  • vLLM: broadest default. Still 0.x versioning (0.30.0 released 2026-09-22), frequent releases. Supports FP8, AWQ, GPTQ, INT8/INT4, GGUF, NVFP4 (via llm-compressor checkpoints), FP8 KV cache, multi-LoRA, speculative decoding (EAGLE-3, P-EAGLE).
  • SGLang: RadixAttention prefix caching, strong on agent and multi-turn workloads, PD disaggregation.
  • TensorRT-LLM: NVIDIA engine, often fastest on NVIDIA hardware, more build steps.
  • HF TGI: maintenance mode since December 2025. HF recommends vLLM or SGLang for new deployments.
  • llama.cpp / Ollama: local GGUF.

Code: vLLM serve (illustrative)

vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --tensor-parallel-size 2 \
  --quantization fp8 \
  --kv-cache-dtype fp8 \
  --max-model-len 16384 \
  --enable-prefix-caching \
  --gpu-memory-utilization 0.90

Cap --max-model-len to what the product needs. Route long-document work to a separate pool. Alert on KV cache usage and preemptions, not just GPU utilization.

Metrics

Metric Driven by
TTFT (time to first token) Queueing + prefill (prompt length, prefix cache hits)
TPOT / ITL (time per output token) Decode: bandwidth, batch size, speculative decoding
Throughput (tokens/s) Batch size, quantization, KV capacity
Goodput Throughput delivered while meeting TTFT/TPOT SLOs, which is the number to optimize

Key terms

Term Meaning
HBM High-bandwidth memory on the GPU: the warehouse floor
Prefill / decode Parallel prompt processing (compute-bound) / token-by-token generation (bandwidth-bound)
KV cache Stored attention keys/values per token per layer
GQA Grouped-query attention: fewer KV heads, smaller KV cache
Quantization Storing weights/activations/KV in fewer bits
Weight-only vs W8A8 Only weights shrunk vs weights + activations computed in low precision
Preemption Engine evicts a request's KV under memory pressure and recomputes later

5 interview questions

Q1. Why is LLM inference memory-bound? In decode, each token requires reading all the weights from HBM but only a little arithmetic per weight. So the single-stream ceiling ≈ bandwidth ÷ model bytes (e.g. 3.35 TB/s ÷ 70 GB ≈ 48 tok/s). Levers: quantization (fewer bytes) and batching (more tokens per pass).

Q2. Does quantization hurt quality? It depends on bit width, method, model size, and task. FP8 is near-lossless for most large models. 4-bit (AWQ/GPTQ/NVFP4) usually holds on general tasks but can regress on math, code, long reasoning, and structured extraction, and small models suffer more. Always gate on your own eval set, and consider mixed precision per workload.

Q3. What is PagedAttention and why does it matter? It manages the KV cache like OS virtual memory: fixed-size blocks allocated on demand with a block table, instead of contiguous max-length reservations. That cuts KV waste from 60–80% to a few percent, so more concurrent sequences fit and continuous batching and prefix sharing become practical.

Q4. How does speculative decoding speed things up without changing output? A cheap draft (small model or EAGLE-style heads) proposes several tokens. The target model verifies them all in one forward pass, which costs about the same as one token because decode is bandwidth-bound. Accepted tokens are kept, and rejection sampling preserves the target distribution. The speedup depends on acceptance rate and is highest at low batch sizes.

Q5. Size a deployment for a 70B model with ~200 concurrent users. FP8 weights (70 GB) and FP8 KV cache, tensor-parallel over 2–4 H100s. Compute KV per token (~0.33 MB at FP16, half at FP8) × the real context distribution × concurrency to size the shelf. Cap max context, and use vLLM/SGLang with prefix caching. Load test for goodput against TTFT/TPOT SLOs, and autoscale on queue depth and KV utilization.
