Track 8 · LLMOps + Prompting · Episode 4

Monitoring, Drift, Feedback Loops

19 min listen · Why an L L M system can return a perfect two hundred OK while being quietly wrong, and how to see it: a three-layer monitoring picture of operational dials, sampled quality judging, and a feedback return pipe, plus the four kinds of drift that break production assistants.

Facts verified: 2026-09-25

Thesis: An LLM system's worst failures return 200 OK at normal latency, so monitoring must layer cheap operational metrics on 100% of traffic, sampled + targeted quality judging, drift detection at four points, and a feedback loop that turns production failures into release-gating tests.

The mental image: the conveyor

  • Belt (left → right): requests drop on at the left, pass through the box (prompt + retrieval + model + tools), exit right as answers.
  • Dials above the belt: operational metrics on every request (latency/TTFT, tokens, cost, errors) — cheap, 100%.
  • Tap + tasting room below: 5–10% random sample plus every flagged trace judged for quality (code checks → LLM judges → humans).
  • Return pipe underneath (right → left): explicit + implicit feedback flows back to become golden-set cases that gate releases.
  • Drift entry points: input (left end), model + knowledge (inside the box), output (right end), judge (tasting room).

Code: MLflow 3 production monitoring (sampled scorers)

import mlflow
from mlflow.genai.scorers import Safety, RelevanceToQuery, ScorerSamplingConfig

mlflow.set_experiment("/Shared/support-assistant-prod")

# Register a built-in judge against the experiment, then start it with sampling
safety = Safety().register(name="safety_judge")
safety = safety.start(sampling_config=ScorerSamplingConfig(sample_rate=0.10))

relevance = RelevanceToQuery().register(name="relevance_judge")
relevance = relevance.start(
    sampling_config=ScorerSamplingConfig(sample_rate=0.05)  # optional filter_string also supported
)
# Scores are attached back to sampled production traces as feedback.

Code: judge calibration (agreement with human labels)

from sklearn.metrics import cohen_kappa_score

human = [1, 0, 1, 1, 0, ...]   # expert labels on a few hundred traces
judge = [1, 0, 1, 0, 0, ...]   # LLM judge verdicts on the same traces
print("agreement:", sum(h == j for h, j in zip(human, judge)) / len(human))
print("kappa:", cohen_kappa_score(human, judge))
# Low agreement -> fix rubric / add examples / change judge model; pin judge version.

Pitfalls (war-story shaped)

  • Stale index, green dashboards: refresh job silently stopped; groundedness judge passed (answers matched the stale docs); only escalation rate revealed it. Monitor the inputs to the model (index freshness), not just outputs.
  • Optimizing for thumbs: OpenAI's April 2025 GPT-4o update was rolled back for sycophancy; OpenAI cited an added reward signal from thumbs-up/down data as a contributing factor. Feedback finds failures; don't train on it naively.
  • Random sampling misses rare disasters: add targeted sampling (every refusal, schema failure, negative thumb, escalation).
  • Traces are personal data: redact at capture, retention limits, access control.
  • Floating model aliases in prod: pin snapshots; treat upgrades as releases gated by evals. Pin the judge model too.

5 interview questions

1. How would you monitor an LLM application in production? Three layers: operational metrics on 100% via tracing (TTFT, p95/p99 latency, tokens and cost per feature/tenant, error/429/timeout/schema-failure rates); quality on a sample plus flagged traces (deterministic checks, calibrated LLM judges for groundedness/relevance/safety, small human sample); and a feedback loop where explicit and implicit signals feed triage, confirmed failures become golden-set cases, and every release must pass the set.

2. Where does drift come from in an LLM system and how do you detect each kind? Input drift (embedding clusters, intent frequency), model drift (pin snapshots, eval-gate upgrades), knowledge drift (index freshness, retrieval scores, zero-hit rate, embedding version consistency), output drift (length, refusal rate, tone — usually a symptom). Plus judge drift if the evaluator model changes.

3. Can you trust LLM-as-a-judge? Only after calibration: known biases (position, verbosity, self-preference). Measure agreement with human labels on a few hundred traces, iterate the rubric, pin the judge version, keep a permanent small human review sample, and use judges for trends/triage rather than as sole release authority unless calibrated.

4. How do you keep evaluation cost under control at a million requests a day? Deterministic checks on everything; LLM judges on a 5–10% random sample plus 100% of flagged traces; judge only the relevant span; smaller judge models for simple criteria; keep full payloads only for sampled/flagged traces and lightweight metrics for all.

5. What feedback signals would you collect and how do they improve the system? Explicit (thumbs, ratings — sparse and extreme-biased) and implicit (regenerate, immediate rephrase, copy, abandon, escalate to human, edit distance on drafts). Route negatives to triage, have humans confirm and write correct answers, add them to the golden set, fix root cause, and gate the fix on the expanded set. Avoid feeding raw thumbs straight into training (sycophancy risk).

And output drift, length, refusals, tone, which is usually a symptom of the other three." And when they push with, "Can you trust L L M as a judge?", say: "Only after calibration. Judges have position, verbosity and self-preference biases, so I measure their agreement with human labels on a few hundred examples, fix the rubric until agreement is acceptable, pin the judge version, and keep a small human review sample running permanently." ## Sixty-second recap [PAUSE 1s] Back to the conveyor one more time. Parcels, user requests, drop on at the left, ride through the box in the middle, your prompt, retrieval, model and tools, and roll off the right as answers. Above the belt, the dials read every parcel: time to first token and total latency at the tail, tokens, cost, errors, schema failures, all captured through traces built on OpenTelemetry-style conventions. Below the belt, a tap drops five to ten percent of answers, plus every flagged one, into the tasting room, where code checks, calibrated L L M judges, and a few humans estimate quality. Drift enters at four points: input drift at the left end, model drift and knowledge drift inside the box, output drift at the right end, and judge drift down in the tasting room. And underneath it all, the return pipe carries thumbs, regenerations, rephrases and escalations from the right end back to the left, where confirmed failures become golden-set tests that gate every future release. Dials above, tasting room below, return pipe underneath. If the telco had had all three, the stale index would have been caught in a day. See you in the next episode.
