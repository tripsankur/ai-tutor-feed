Prompt vs RAG vs Fine-Tune: The Decision Tree

18 min listen · A staircase with a fork: climb from prompting to retrieval to fine-tuning only as far as the problem needs, and diagnose first whether the gap is knowledge or behavior, because each step fixes a different kind of gap.

Facts verified: 2026-09-25

One-sentence thesis

Diagnose the gap before picking the tool. Knowledge gaps (facts that are large, changing, private, or need citing) go to retrieval. Behavior gaps (format, tone, narrow-task skill, cost/latency) go to fine-tuning or distillation. Both sit on a well-engineered prompt, which you exhaust first and never leave.

The mental image: a staircase with a fork

  • Floor (far left): you, a problem, and an evaluation set. Without it you can't tell which step helped.
  • Step 1 (low, wide): prompting. Instructions, few-shot examples, structured output, reasoning room, and context stuffing plus caching for small, stable knowledge.
  • Fork at the top of step 1:
  • Right corridor → the library (RAG): labeled knowledge.
  • Steep flight up → the workshop (fine-tuning): labeled behavior.

Facts worth quoting (verified 2026-09-25)

  • OpenAI is winding down self-serve fine-tuning. Notice on May 7, 2026: orgs that hadn't fine-tuned can't create jobs. Existing customers can't create new jobs from ~January 6, 2027. Existing fine-tuned models stay available for inference until their base models are deprecated. Stated rationale: strong base models + prompt + RAG cover most cases. (Several independent reports; OpenAI's own community announcement thread.)
  • Fine-tuning is still widely available elsewhere: Azure AI Foundry (SFT, DPO, RFT on OpenAI and open models), Amazon Bedrock (SFT, RFT incl. open-weight GPT-OSS/Qwen, managed distillation), plus any open-weight model.
  • Bedrock distillation claim: distilled models "up to 500% faster and up to 75% less expensive", "<2% accuracy loss" for use cases like RAG (AWS marketing figure).
  • Fine-tuning and new facts: Gekhman et al., EMNLP 2024. New-knowledge examples are learned significantly slower, and once learned they linearly increase the tendency to hallucinate.
  • Context rot: Chroma (July 2025) tested 18 LLMs. Performance grows less reliable as input length increases, even on simple tasks. Lost-in-the-middle effects persist.
  • Prompt caching: e.g. Anthropic cache reads at 0.1x base input price.
  • QLoRA: 4-bit (NF4) frozen base + LoRA adapters lets a 70B model fine-tune on a single 80 GB GPU. Adapters are typically <1% of base size. vLLM multi-LoRA serves many adapters on one base model.

Key terms

Term Meaning
Knowledge gap Model lacks facts: private, changing, large, or needing citation
Behavior gap Model has the facts but acts wrong: format, tone, consistency, narrow task, cost/latency
Few-shot prompting 3–5 worked examples in the prompt
Structured output Provider-enforced output matching a JSON schema
Context stuffing Putting a whole small corpus in the prompt; pair with caching
Context rot Reliability degrades as input length grows
Reranker Model that re-scores retrieved candidates against the query
SFT / DPO / RFT Supervised fine-tuning / direct preference optimization / reinforcement fine-tuning with a grader
LoRA / QLoRA Low-rank adapters on a frozen base / same with 4-bit quantized base
Distillation Train a small "student" on a large "teacher" model's outputs
Retrieval-aware fine-tuning (e.g. RAFT) Fine-tune a model to use retrieved context well: cite, abstain, ignore distractors

5 interview questions

Q1. RAG or fine-tuning? Diagnose with an eval set first. Knowledge that's large, changing, private, or needs citations → RAG (fresh, permissioned, citable). Behavior (format, tone, narrow-task consistency, or cost/latency at scale) → fine-tune with LoRA, or distill. Both sit on a prompt you've exhausted first.

Q2. Why not fine-tune on our documents so the model "knows" them? Fine-tuning injects facts unreliably. They're learned slowly, and training on unfamiliar facts has been shown to increase hallucination (Gekhman et al., 2024). The knowledge also goes stale, can't be cited, and can't be permissioned per user.

Q3. With 1M-token context windows, do we still need RAG? For small, stable corpora, long context plus caching can replace retrieval. At scale, no: models degrade with length (context rot), cost scales per call, and you lose per-document permissions and clean citations. Retrieve the best ~20K tokens instead of sending a million.

Q4. When is fine-tuning clearly the right call? Stable, narrow, high-volume tasks with hundreds to thousands of good examples: strict output formats, domain classification or extraction, house tone. Also shrinking a long instruction prompt into weights, or distilling a large model into a small one for latency/cost. Plan for retraining whenever the base model is retired.

Q5. How do you know you've exhausted prompting? You have an eval set (50 to a few hundred cases with references/rubrics). You've iterated instructions, examples, structured output, and reasoning, and tried the strongest affordable model. Scores have plateaued, and you can categorize the remaining failures as knowledge or behavior.
