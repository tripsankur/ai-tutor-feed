Track 8 · LLMOps + Prompting · Episode 1

LLMOps vs MLOps: What Actually Changes

19 min listen · Opening Track 8: what carries over from classical MLOps, and what really changes once the model is a rented, non-deterministic text engine and the prompt, context and token meter matter as much as the weights.

Facts verified: 2026-09-25

One-sentence thesis

LLMOps keeps the MLOps foundations (versioning, CI/CD, promotion, eval gates, monitoring) but moves the unit of change from model weights to the whole application config, the unit of quality from labeled metrics to rubric-based evaluation, and the unit of cost to the token. It also adds non-determinism, provider-controlled model retirement, and prompt injection as first-class risks.

The mental image: two workshops, split by a line

  • Left bench (MLOps): one sealed box you trained and own. Labeled data goes in, a deterministic score comes out, and one accuracy dial hangs overhead. The only way to change behavior is to retrain and swap the box.
  • Right bench (LLMOps): a bigger, padlocked, rented box (the foundation model) with a provider-controlled retirement date. The work happens around it: the prompt card on the wall, the document shelf (retrieval) on the left, the tool pegboard on the right, the guardrail gate at the exit, a token meter by the door, and a panel of gauges overhead (groundedness, relevance, safety, format, latency, cost), partly read by LLM judges.

What changes vs what carries over

Dimension MLOps (left bench) LLMOps (right bench)
Unit of change Model artifact (retrain) Prompt + retrieval config + tools + guardrails + model ID, versioned together
Determinism Same input gives same output Sampling; no bit-exact repeatability promise; some newer models reject non-default temperature
Evaluation Held-out labeled test set; single metric Curated golden set plus production replays; rubric gauges; deterministic checks + LLM judges + sampled human review
Who changes the model You Provider (deprecation and retirement schedule)
Cost driver Training + fixed serving cluster Tokens per request (input, output, tool loops); caching and routing are levers
Observability Log features + prediction Trace tree per request (retrieval, model calls, tool calls, guardrails)
Security Feature vectors aren't instructions Prompt injection, direct or indirect (via documents and tool results)
Carries over Git, CI/CD, IaC, dev→staging→prod, access control, lineage, eval gate before release, canary/shadow, runbooks same

Useful numbers (order of magnitude, verified 2026-09-25)

  • Model retirement notice: Anthropic commits to ≥60 days for publicly released models. Hyperscalers typically give ~6 months for GA models; preview models can go with ~2 weeks. In May 2026 xAI retired several API models with ~9 days' notice and redirected old slugs to a newer model at the newer price.
  • Prompt caching: e.g. Anthropic cache reads bill at 0.1x base input price; cache writes cost 1.25x (5-min TTL) or 2x (1-hour TTL). A hit requires an identical prefix.
  • OpenTelemetry GenAI semantic conventions: still Development (not Stable). They moved to a dedicated semantic-conventions-genai repo around June 2026 (semconv v1.42.0). Operations include chat, execute_tool, invoke_agent, and more.

5 interview questions

Q1. How is LLMOps different from MLOps? The foundations carry over: versioning, CI/CD, promotion, eval gates, monitoring. Three units move. Change moves from weights to the full app config. Quality moves from labeled metrics to rubric-based eval with calibrated LLM judges. Cost moves to the token. New risks come with it: non-determinism, provider-driven model retirement, and prompt injection.

Q2. How do you deploy a prompt change safely? Version the prompt in a registry. Evaluate the candidate against the golden set plus a replay of production traffic, and require it to meet or beat production on the rubric gauges and on cost per request. Canary it behind a gateway, then promote by moving an alias, which also gives instant rollback.

Q3. Your provider retires your model in 60 days. What do you do? Run the model-agnostic eval suite against the replacement on day one and diff by category. Fix regressions in prompts and output parsing. Shadow on live traffic, compare cost and latency, then cut over behind the gateway with rollback ready. Going forward, run the suite on new model releases continuously so a retirement notice is never the first time you test.

Q4. Why can't you evaluate an LLM app with accuracy alone? Outputs are free text with no single label. Quality is multi-dimensional: groundedness, relevance, safety, format, latency, cost. You combine deterministic checks (schema parse), LLM judges on rubrics, and sampled human review that measures judge agreement.

Q5. Where do LLM costs hide, and how do you control them? They hide in oversized retrieved context, long system prompts, agent loops (multiple model calls per question), and long outputs. Controls: tighter retrieval with a reranker, prompt caching of a stable prefix, routing easy traffic to smaller models, per-request token budgets tracked in traces, and cost per request as a release-gate metric.
