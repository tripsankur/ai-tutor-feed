LLM-as-a-Judge: Selecting Representative Evaluation Examples

16 min listen · A map of production traffic, a small display case, a judge and a human panel: how to pick evaluation examples that actually represent your users, using stratified sampling, embedding clusters, difficulty mixes and adversarial cases, how many you need, how to calibrate the judge against humans with Cohen's kappa, and how to keep the set fresh and leak-free.

Facts verified: 2026-09-25

Thesis: A good judge scoring the wrong examples gives you a precise, confident, wrong number. Build the eval set from production traffic: stratify by business dimensions with risk-weighted floors, discover hidden segments by embedding clustering (centroids and outliers), tilt toward hard cases, add a hand-built adversarial slice, size it with confidence intervals, calibrate the judge against humans with Cohen's kappa, then refresh on a cadence and guard against leakage.

Interview question (as asked): "When you use an LLM as a judge, how do you select representative examples?"

The eight steps

Step What Detail
1. Source Production logs or closest proxy (tickets, transcripts) Redact PII, check retention/consent, restrict access; window spans month-end/seasonal peaks; dedupe
2. Stratify Intent, product, segment, channel, language, risk tier Proportional vs equal vs risk-weighted allocation; floor ~30–50/stratum; reweight to traffic share for headline score; report per-slice too
3. Cluster Embed → k-means or HDBSCAN Centroid-nearest = prototypes; far-from-centroid + noise = stress tests; unnamed clusters = new strata; store cluster label as metadata
4. Difficulty mix ~⅓ easy / ⅓ medium / ⅓ hard Hardness signals: thumbs-down, rephrase, escalation, abandonment, low retrieval score, long multi-turn, model-version disagreement
5. Red pins Hand-built adversarial slice Prompt injection, out-of-scope, unanswerable (abstention), ambiguous, long inputs, PII, regulated advice; reported separately, can block release
6. Size Confidence intervals SE = √(p(1−p)/n); Wilson interval for small slices; paired comparisons; clustered SEs
7. Calibrate judge Stratified human-labeled subset Cohen's kappa, confusion matrix (false passes), per-slice agreement, human–human ceiling, dev/test split of calibration set
8. Refresh + leakage Cadence + triggers; separate store Frozen core + rotating slice; incidents become permanent cases; embedding-dedupe across train/eval; time-based splits

from statsmodels.stats.proportion import proportion_confint

# Paired comparison: same items, old vs new (1 = pass)

# Judge calibration on held-out half of calibration set
kappa = cohen_kappa_score(human_labels, judge_labels)
tn, fp, fn, tp = confusion_matrix(human_labels, judge_labels, labels=[0, 1]).ravel()
false_pass_rate = fp / (fp + tn)   # human said FAIL, judge said PASS

# Stratified + cluster-aware selection sketch
import pandas as pd
from sklearn.cluster import KMeans

X = embed(df.text)                               # your embedding model
km = KMeans(n_clusters=40, n_init="auto", random_state=0).fit(X)
df["cluster"] = km.labels_
df["dist"] = np.linalg.norm(X - km.cluster_centers_[km.labels_], axis=1)

protos   = df.sort_values("dist").groupby("cluster").head(3)           # centroid-nearest
outliers = df.sort_values("dist", ascending=False).groupby("cluster").head(1)
floor    = df.groupby("stratum", group_keys=False).apply(
             lambda g: g.sample(min(len(g), 40 if g.risk.iloc[0] == "high" else 30), random_state=0))
eval_set = pd.concat([protos, outliers, floor]).drop_duplicates("id")

Kappa worked example

Humans pass 90%, judge passes 90%, observed agreement 92%. Chance agreement p_e = 0.9·0.9 + 0.1·0.1 = 0.82 → κ = (0.92 − 0.82)/(1 − 0.82) ≈ 0.56 (moderate). A judge that always says PASS: 90% raw agreement, κ = 0. Landis & Koch scale: 0.41–0.60 moderate, 0.61–0.80 substantial, 0.81–1.00 almost perfect. Compare against human–human kappa as the ceiling. Reference point: MT-Bench found strong judges reached >80% agreement with humans on non-tie pairwise cases, similar to human–human agreement (~81%).

Key terms

Term Meaning
Stratum A segment of traffic (intent, product, segment, risk) sampled separately
Proportional / equal / risk-weighted allocation Slots ∝ traffic / same per stratum / floors + extra for high-risk
Post-stratification reweighting Re-weight slice scores to true traffic shares for the headline number
Centroid-nearest (medoid) Most typical example of a cluster
HDBSCAN noise Points belonging to no cluster — natural outlier candidates
Wilson interval Binomial CI that behaves well for small n and extreme p
Paired comparison Compare versions item-by-item to cancel per-item difficulty variance
Cohen's kappa Agreement corrected for chance: (p_o − p_e)/(1 − p_e)
False pass Human fails, judge passes — the dangerous error direction
Criteria drift Graders' definition of "good" evolves as they see outputs (Shankar et al., UIST 2024)
Leakage Eval items (or paraphrases) appearing in prompts, judge examples or training data

5 interview questions with strong answers

1. How do you select representative examples for an LLM judge? Start from PII-redacted production traffic over a multi-week window; stratify by intent/product/segment/channel/language/risk with floors and risk-weighted extras; embed and cluster to find unknown segments, taking centroid-nearest prototypes plus outliers; over-sample hard cases via user and retrieval signals; add a hand-built adversarial slice; reweight to traffic for the headline score and report per slice.

2. How many examples do you need? Think in confidence intervals: 100 items at 80% ≈ ±8 pts, 400 ≈ ±4. A few hundred to ~1,000 overall, 50+ per critical slice, Wilson intervals for small slices, paired comparisons between versions, clustered SEs for correlated items, and a pre-agreed minimum detectable difference.

3. How do you know the judge is trustworthy? Calibrate on a stratified human-labeled subset including borderline cases; use Cohen's kappa (not raw agreement), inspect false passes and per-slice agreement, compare to human–human kappa, tune on one half and report on the other; re-calibrate on any judge-model or rubric change.

4. How do you keep the eval set current? Frozen versioned core for trend comparability plus a rotating fresh slice; refresh monthly/quarterly and on triggers (launches, new production clusters without coverage, embedding drift); every incident becomes a permanent case.

5. How do you prevent leakage? Separate access-controlled store; never reuse eval items as few-shot examples in the app or judge prompt, or in fine-tuning/distillation data; embedding-based near-duplicate removal across train/eval; time-based splits; a held-out slice nobody iterates against.

Then decide how many slots in the case each neighborhood gets. There are three allocation rules worth naming. Proportional allocation mirrors traffic, so the case looks like the map. Equal allocation gives every neighborhood the same number of slots, so you can measure each one with similar precision. [PAUSE 1s] ## Step six: how big should the case be Now the numbers, because this is where interviewers check whether you think statistically. Your score is a proportion, so its standard error is the square root of p times one minus p, divided by n. With a hundred examples and a true pass rate around eighty percent, the ninety-five percent confidence interval is roughly plus or minus eight points. Every production incident becomes a new pin in the case, permanently. And any time you change the judge model or the rubric, re-run calibration. Leakage. This is the quiet killer. If examples from the case end up in the assistant's prompt as few-shot examples, in the judge's prompt as rubric examples, or in fine-tuning or distillation data, your scores inflate and stop meaning anything.
