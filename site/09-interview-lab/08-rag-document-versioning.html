RAG Document Versioning: Section Edits, Removals, Index Consistency

19 min listen · The interview question every production RAG system eventually has to answer: when a document changes, a section is edited, or a section disappears, how do you keep the index consistent? Stable section IDs, content hashes, a manifest ledger, delete-then-verify writes, tombstones, as-of versions for regulated documents, blue-green index aliases, cache invalidation and reconciliation.

Facts verified: 2026-09-25

Thesis: the vector index is derived data; keep a transactional manifest (ledger) of section IDs, content hashes, versions and chunk IDs, gate reads with a current-version pointer, and prove consistency with nightly reconciliation.

Interview question answered: "A document in your RAG corpus is updated — one section modified, another removed entirely. How do you manage the changes and keep indexed content consistent?"

The mental image

A long room. Left wall = the archive (source of truth; every section stamped with a stable ID). Middle desk = the ledger/manifest (doc, section ID, version, normalized hash, chunk IDs, tombstones) with a small board above it = current-version pointer per doc. Right wall = the card wall (vector index). A tray by the door = answer/semantic cache. A second wall behind the first + a "live" sign = blue-green index behind an alias. Nightly, an auditor walks left → right (reconciliation).

Change classification (the diff)

Case Detection Action
Unchanged section same section_id, same hash skip (no embed, no write)
Modified section same section_id, different hash embed new chunks → write → flip pointer → delete/retire old chunks
Moved section same hash, new position/path metadata-only update
New section section_id not in manifest embed + insert
Removed section in manifest, absent from new version tombstone row → delete (or retire) chunks
Metadata-only (ACL, owner, status) hash same, metadata differs update metadata on all chunks — fast path (ACL lag = data leak)
Embedding model / chunker / parser change config version differs full rebuild, blue-green behind alias

Write ordering — why "write, flip, delete"

sequenceDiagram
    participant J as Ingest job
    participant V as Vector index
    participant L as Manifest + pointer
    J->>V: upsert chunks (sec4, v8, 1..4)
    J->>L: set current_version(doc)=8 (atomic)
    Note over V: retriever filters version == current -> v7 chunks now invisible
    J->>V: delete where section_id=sec4 AND version != 8
    J->>L: update manifest row (hash, chunk_ids)
    Note over J,L: crash anywhere -> rerun is idempotent, reconciliation catches leftovers

The orphan bug: chunk IDs = section + ordinal, upsert-only. v7 had 5 chunks, v8 has 4 → chunk 5 (old rule) survives forever. Fix: version in the chunk ID + delete-by-filter (or delete by the chunk-ID list stored in the manifest).

Code sketches

Normalized section hash:

import hashlib, re, unicodedata

def section_hash(text: str) -> str:
    t = unicodedata.normalize("NFKC", text)
    t = re.sub(r"(?im)^(page \d+ of \d+|printed on .*)$", "", t)  # footers/page nums
    t = t.replace("’", "'").replace("“", '"').replace("”", '"')
    t = re.sub(r"\s+", " ", t).strip()
    return hashlib.sha256(t.encode("utf-8")).hexdigest()

Diff against the manifest:

def diff(new_sections: dict[str, str], manifest: dict[str, dict]):
    new_ids, old_ids = set(new_sections), set(manifest)
    added    = new_ids - old_ids
    removed  = old_ids - new_ids
    modified = {s for s in new_ids & old_ids
                if section_hash(new_sections[s]) != manifest[s]["hash"]}
    return added, modified, removed

Delete circuit breaker:

if len(removed_docs) > 0.05 * corpus_size or len(source_listing) == 0:
    raise RuntimeError("Refusing mass delete; source listing looks incomplete")

As-of retrieval filter (pseudo-syntax — translate to your store's filter DSL; model "open" as a sentinel far-future date if nulls are awkward):

now_filter   = {"effective_to": OPEN}                         # default users
asof_filter  = {"effective_from": {"$lte": t}, "effective_to": {"$gt": t}}   # OPEN = 9999-12-31  # compliance replay

Key terms

Term Meaning One-liner
Stable section ID Identity that survives edits/renumbering (source key or aligned via heading + similarity) "No identity, no incremental update"
Content hash Normalized SHA-256 of section text "Skip what didn't change"
Manifest / ledger Transactional table: doc, section, version, hash, chunk IDs, status "Don't use the vector store as your source of truth for what's in it"
Upsert vs replace-by-section Overwrite by ID vs write-new + delete-by-filter "Upsert-only leaves orphans when chunk count shrinks"
Current-version pointer Per-doc version the retriever filters on "Physical cleanup is eventual; visibility is atomic"
Tombstone Manifest record of a removal (when/by what) "Audit trail + idempotent retries"
As-of query Filter on effective_from/effective_to "Time travel for the index — what did we know on 14 March?"
Index alias / blue-green Name pointing at a physical index; swap to cut over "Rebuild behind, flip the sign, keep old for rollback"
Reconciliation Nightly source ↔ manifest ↔ index compare "Orphans, missing, freshness lag as metrics"
CDC Change events incl. deletes from source log "Deletes as events beat deletes inferred from absence"

Numbers worth quoting

  • Embedding: cents per million tokens for hosted small models → re-embedding a section is ~free; parsing is the cost (layout parsers ~US$10–15 per 1,000 pages: Azure Document Intelligence Layout ~$10/1k, Textract Tables ~$15/1k).
  • Azure AI Search alias update: up to ~10 s to propagate.
  • Qdrant alias changes: atomic; concurrent requests unaffected.
  • Databricks Vector Search Delta Sync: triggered or continuous (seconds of latency, higher cost); incremental, propagates inserts/updates/deletes from the Delta table.
  • HNSW-style indexes: deletes are typically soft (marked) until compaction/optimization → watch recall and memory under churn.

5 interview questions (with strong answers)

  1. A section of a policy document is modified. Walk me through the update. Detect via stable section ID + changed normalized hash; chunk and embed only that section; write new chunks tagged with version N+1; atomically flip the doc's current-version pointer that retrieval filters on; delete (or retire) the old version's chunks by section+version filter; update the manifest; evict caches tagged with the doc. Crash-safe because each step is idempotent and reconciliation cleans leftovers.

  2. A section is removed completely. What happens, and what can go wrong? Set difference between manifest section IDs and the new version → tombstone row → delete chunks. The risk is inferring deletes from absence: a failed or partial listing can wipe the index. Guard with a mass-delete circuit breaker, prefer explicit delete events (CDC/webhooks), and keep tombstones for audit.

  3. How do you guarantee users never see a mix of old and new versions? Vector stores rarely offer multi-record transactions, so make visibility the atomic step: a per-document current-version pointer (or is_current flag) enforced as a query filter. Write new first, flip pointer, then delete old; readers see either all-old or all-new.

  4. A regulator asks what your assistant told a customer six months ago. Can you answer? Yes, if you retire instead of delete: chunks carry effective_from/effective_to, and every answer logs chunk IDs, doc versions and hashes. Replay with an as-of filter to reconstruct the exact context. Retention vs purge (PII) is a policy decision encoded separately.

  5. You're changing the embedding model. How do you roll it out? Full rebuild into a new index (never mix vector spaces), record the change-log position, evaluate against the golden set, replay changes since the start, then swap the alias; keep the old index for rollback. Store model + chunker version in the manifest and check it at query-service startup.

The key property: deletes arrive as events, which is far safer than inferring them from absence. ## Proving it: reconciliation Last piece. Even with all this, jobs crash, networks drop, and someone deletes cards by hand during an incident. So every night, a reconciliation job walks the whole room, left to right. For each document on the left wall, is there a ledger line with a matching fingerprint? For each ledger line, do the cards it lists actually exist on the right wall? And for each card on the right wall, is there a ledger line that claims it? Cards claimed by nobody are orphans: delete them. Ledger lines pointing at missing cards: re-embed. Fingerprint mismatches: re-ingest. Emit three numbers as metrics: orphan count, missing count, and freshness lag, meaning the time from a source change to its cards going live. Alert on any of them drifting. That lender with the three-month rule? A reconciliation job would have flagged that orphan card on day one. [PAUSE 1s] ## Tradeoffs and pitfalls A few numbers to keep the tradeoffs honest. Embedding is the cheap part: current hosted embedding models cost cents per million tokens, so re-embedding one changed section is effectively free. Parsing is not always cheap: layout-aware cloud parsers are priced per page, typically around ten to fifteen dollars per thousand pages, so re-parsing an entire three-hundred-page manual because one clause changed adds up across thousands of documents. Cache parsed output keyed by the file's own hash. Deletes are also not free inside the index. In graph-based vector indexes, deleted vectors are usually marked, not physically removed, and search quality and memory can degrade until the store compacts or you rebuild. If your corpus churns heavily, schedule compaction, and watch recall on your evaluation set over time. Granularity is a tradeoff. Whole-document replacement is simple and always correct, and for short documents that change rarely, it's fine. Section-level machinery earns its keep on long, frequently amended documents: policies, contracts, disclosure statements, procedure manuals. And don't rely on the vector store as your ledger. Stores are good at similarity search, and weak at "list every card for section four across versions." Keep the ledger in a proper database or a Delta table, where you get transactions, history, and easy auditing. [PAUSE 1s] ## The strong answer When they ask, "How do you handle document version changes in R A G: modified sections, removed sections, keeping the index consistent?", a strong ninety-second answer sounds like this. "I treat the index as derived data with a ledger. Each document is split into sections with stable identifiers, from the source system if possible, otherwise by aligning sections against the previous version. For each section I store a normalized content hash, its version, and the chunk identifiers it produced, in a manifest table, not in the vector store. When a new version arrives, I diff hashes: unchanged sections are skipped, so I only re-embed what changed. For a modified section, I write the new version's chunks first, then flip a current-version pointer that the retriever filters on, then delete the old chunks by section and version, so there are never orphans from a shrinking chunk count and readers never see a mix. For a removed section, I write a tombstone and delete its chunks, with a circuit breaker so an empty source listing can't wipe the index. For regulated documents I retire instead of delete, with effective-from and effective-until dates, so I can answer as-of questions and I log chunk versions with every answer for audit. Caches are tagged by document version and evicted when the pointer moves. Model or chunking changes are full rebuilds behind an index alias with a blue-green cutover. And a nightly reconciliation compares source, manifest and index, and alerts on orphans and freshness lag." [PAUSE 2s] Likely follow-ups. "Two updates to the same document arrive at once?" Process per document serially and reject any write older than the current pointer. "Permissions changed but content didn't?" A fast metadata-only update, because a revoked permission that lingers is a data leak. And the trap: "Why not just re-index everything nightly?" Name the cost, the staleness window, and the missing as-of history, then admit it's a fine start for a small corpus. ## Sixty-second recap Back to the room. On the left wall, the archive: the truth, every section stamped with a stable identifier that survives edits and renumbering. On the desk in the middle, the ledger: for each section, its fingerprint, its version, and the cards it produced, plus tombstones for sections that were removed. On the right wall, the cards the searcher can see. A section changes: its fingerprint differs, you embed only that section, write the new cards, flip the current-version pointer on the board above the desk, then delete the old cards. A section disappears: tombstone in the ledger, cards removed, and a circuit breaker so a blank listing never empties the wall. Regulated documents: retire, don't delete, and let an as-of filter replay the past. A new model: build a second wall behind the first and move the "live" sign. Evict the answer tray by the door when the pointer moves. And every night, walk the room from left to right and prove the three places still agree. See you in the next episode.
