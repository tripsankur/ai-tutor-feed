Building an LLM Inference Microservice

19 min listen · The interview question 'walk me through the LLM inference microservice you built', answered floor by floor: API layer, validation, per-tenant token rate limits, deadlines and cancellation, SSE streaming, a vLLM engine underneath, health probes, cold start, observability, and a tour of the optimization techniques that live on each floor.

Facts verified: 2026-09-25 (vLLM v0.30.0 source + docs, Kubernetes probe docs, Gateway API Inference Extension docs)

Thesis: an LLM inference microservice is two layers — a thin, async, policy-owning gateway (auth, validation, token-based tenant limits, deadlines, streaming) over a batching engine (vLLM) — and the interview is won by explaining the seams between them: cancellation, backpressure, probes, cold start and the right metrics.

Interview questions this answers (Round 1 opener): "Tell me how you built an LLM inference microservice." · "What inference optimization techniques did you use?"

The mental image: the building (dollhouse cross-section)

  • Ground floor = API layer, left → right: front door → security desk (authN, tenant, request ID) → forms desk (schema + real token counting + PII masking) → turnstile (per-tenant token-bucket limits, 429 + Retry-After) — with a clock on the wall (deadlines: TTFT, inter-token idle, total).
  • Basement = engine room: the foreman with a clipboard (vLLM scheduler: continuous batching, paged KV, prefix cache, chunked prefill) in front of the machine (GPU).
  • Speaking tube from basement to street = SSE streaming.
  • Loading dock at the back = weights delivery / cold start.
  • Two lamps on the roof = liveness / readiness (+ startup probe).
  • Gauges on the outside wall = observability (TTFT, ITL, queue, KV usage, preemptions).

Gateway: stream with deadline + cancellation propagation (FastAPI + httpx sketch):

@app.post("/v1/chat/completions")
async def chat(req: ChatRequest, request: Request, tenant=Depends(auth)):
    n_in = count_tokens(req.messages)                     # model's own tokenizer
    if n_in + req.max_tokens > MAX_MODEL_LEN: raise HTTPException(400, "context too long")
    if not await bucket.take(tenant, n_in + req.max_tokens):  # Redis token bucket
        raise HTTPException(429, headers={"Retry-After": "2"})
    async def gen():
        async with httpx.AsyncClient(timeout=httpx.Timeout(connect=2, read=10, write=5, pool=2)) as c:
            async with c.stream("POST", VLLM_URL, json={**req.model_dump(), "stream": True,
                                 "stream_options": {"include_usage": True}}) as r:
                async for line in r.aiter_lines():
                    if await request.is_disconnected():
                        break                      # exiting closes upstream → vLLM aborts
                    yield line + "\n"
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"X-Accel-Buffering": "no", "Cache-Control": "no-cache"})

(read=10 doubles as the inter-token idle timer; add a total-deadline wrapper with asyncio.timeout. Reconcile the token bucket with the real usage from the final chunk.)

Key terms

Term Meaning One-liner
SSE Server-sent events, text/event-stream, one-way over HTTP "Stream tokens so the connection is never idle"
Cancellation propagation Client disconnect/deadline closes upstream; vLLM aborts & frees KV "No ghost generations"
Token-based rate limit Per-tenant input/output tokens per minute + concurrency cap "Cost follows tokens, not requests"
Startup probe Separate probe covering slow model load "Don't let kubelet kill a loading pod"
Cold start Node provision + image pull + weight load + compile/graph capture "1 to 15+ minutes; keep warm floor"
Priority scheduling vLLM policy=priority; lower value served first "Interactive lane ahead of batch"
Cache salt Per-request cache_salt isolates prefix-cache reuse by trust group "Multi-tenant timing-attack defence"

5 interview questions with strong answers

  1. "Walk me through the inference microservice you built." — Two layers: vLLM's OpenAI-compatible server on GPU nodes for continuous batching, paged KV and prefix caching; a thin async gateway on top for auth/tenant, token-counted validation, PII masking, per-tenant token-bucket limits returning 429 + Retry-After, deadlines with cancellation all the way down, SSE streaming with buffering off. Ops: startup/liveness/readiness probes, cached weights and warm minimum replicas, TTFT/ITL/queue/KV metrics, OTel traces, audit logs without raw prompts.
  2. "Why rate-limit on tokens rather than requests?" — GPU cost and KV occupancy scale with tokens; request sizes vary 1000×. Limit input and output tokens per minute plus concurrent requests per tenant; reconcile with actual usage from the stream's final chunk.
  3. "What happens when a client disconnects mid-generation?" — Gateway must close its upstream stream; vLLM detects the disconnect and aborts the request, freeing its KV blocks. If the gateway doesn't propagate it, the GPU keeps generating ghost tokens — and with naive retries, load multiplies.
  4. "How do you handle cold start?" — Break it down (node, image, weights, compile/graphs), then attack each: node-local NVMe or pre-populated volumes, streaming loader from ADLS/S3, baked compile cache, sleep mode for rarely used models, long startup probe, and a warm replica floor sized to the latency SLO.
  5. "Which optimizations did you apply and what did they buy?" — Name floor + metric: stable-prefix-first prompts for prefix-cache hits (TTFT), FP8 weights (memory → concurrency), tuned max_num_batched_tokens for ITL vs TTFT, priority scheduling for interactive traffic, speculative decoding where batch sizes are small; always quote vs baseline, hardware and latency target.

Be careful with semantic caching in finance: two questions that look alike can have different correct answers. In the basement, the scheduler techniques. Continuous batching and paged attention are the baseline. Prefix caching, on by default in current v L L M: put the stable parts of the prompt first, system prompt, tool definitions, policy text, so requests share cached blocks and skip that prefill, which cuts time to first token sharply for agent workloads. Chunked prefill splits long prompts and interleaves them with ongoing decodes, so one giant document doesn't freeze everyone else's stream. Speculative decoding lets a small draft guess several tokens that the big model verifies in one pass, often two to three times faster decoding at low batch sizes, with the same output distribution. On the machine itself, make each step cheaper. Eight-bit floating point weights are the near-lossless default on modern G P Us; four-bit when memory is tight and your own evaluations pass. An eight-bit K V cache fits twice the tokens. And tensor parallelism spreads a model that doesn't fit on one G P U across several. And across buildings: route requests to the replica that already holds their prefix in cache, instead of plain round robin. The Kubernetes Gateway A P I Inference Extension, now at a stable version one A P I, does this with an endpoint picker that reads each replica's queue and K V cache usage. At the largest scale, disaggregated serving runs prefill and decode on separate pools of G P Us. Then autoscaling, on the right signal, which is episode three. [PAUSE 1s] ## Trade-offs, pitfalls and a war story Three pitfalls come up again and again. One: autoscaling or alerting on G P U memory. v L L M reserves around nine-tenths of G P U memory at startup and carves it into K V cache blocks, so memory reads about ninety percent whether the replica is idle or on fire. Use the waiting-requests gauge and K V cache usage instead. Two: setting the maximum context length to the model's full limit "just in case". That pulls more K V cache into every worst case, and one tenant sending huge documents can starve everyone else. Size it to what the product actually needs, and route long-document work to a separate pool. Three: retries without budgets. A second war story, in a shape common in banks. An operations assistant shared an inference pool with a nightly job summarizing regulatory filings, whose client had aggressive retries and no per-tenant limit. One night slow storage stretched the batch prompts, the retries filled the queue, and at seven the next morning interactive users saw a forty-second time to first token against a two-second target. The fixes came straight off the ground floor: token-based tenant limits, a retry budget, and a priority lane, using v L L M's priority scheduling so the foreman serves interactive requests first. On cost: the gateway adds a few milliseconds, negligible next to generation. Warm replicas cost real money, several dollars an hour per top-end G P U, so the warm floor is a business decision about your latency target. Say so in the interview. [PAUSE 2s] ## The strong answer, out loud When they ask "tell me how you built an L L M inference microservice", a strong ninety-second answer sounds like this. "It had two layers. Underneath was v L L M running its OpenAI-compatible server on G P U nodes in Kubernetes, because I wanted continuous batching, paged K V cache and prefix caching without building them myself. On top was a thin async gateway that owned everything v L L M shouldn't. It handled authentication and tenant identity, and request validation with real token counting against the context limit. It did personal data masking and per-tenant rate limits measured in tokens per minute, not requests, returning four twenty-nines with retry-after. Every request got a deadline, and cancellation went all the way down, so a disconnected client aborted its generation. Responses streamed over server-sent events, with heartbeats and buffering turned off at the proxies. Operationally, we used startup, readiness and liveness probes against the health endpoint, with a long startup window for weight loading. Weights were cached on local N V M e to cut cold start, and we kept a warm minimum of replicas. We tracked time to first token, inter-token latency, queue depth and K V cache usage from v L L M's Prometheus metrics, with Open Telemetry traces and audit logging that kept raw prompts out of general logs. For optimization, we put the shared prefix first for cache hits, used eight-bit weights, tuned the batching parameters against our latency targets, and used priority scheduling for interactive traffic." Then stop, and let them choose where to dig. Expect these follow-ups. "Why not a managed endpoint?" Because cost follows tokens, and requests vary a thousand times in size. "What happens when the G P U fills up?" Preemption, next episode. "How did you pick your scaling metric?" Episode three. And the traps. Don't claim a throughput gain you can't explain: ten x compared to what, on which G P U, at what latency? Don't say you autoscaled on G P U utilization.
