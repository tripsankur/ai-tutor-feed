Autoscaling LLMs on Kubernetes: HPA, KEDA & Picking the Scaling Metric

19 min listen · The interview question 'how did you set up HPA and pick your scaling parameters?' answered from the mechanics up: why CPU and GPU utilization lie for LLM serving, how waiting requests and KV cache usage reach the autoscaler through Prometheus and KEDA, how HPA behavior and cold starts shape the numbers, and how load testing picks the targets.

Facts verified: 2026-09-25

The interview questions

"How did you set up HPA for your inference service?" · "How did you pick the scaling parameters?"

One-sentence thesis

For LLM serving, scale on the engine's saturation signals (waiting requests, KV-cache usage) — not CPU, memory, or GPU utilization — feed them to the HPA via Prometheus + KEDA, make scale-up eager and scale-down slow, and derive the target from a one-replica load test with headroom for a multi-minute cold start.

The mental image: the restaurant with a thermostat

  • Waiting chairs (left) = queued requests → vllm:num_requests_waiting. Most honest throughput signal.
  • Kitchens (middle) = replicas (pods). Burner grid = KV-cache blocks → vllm:kv_cache_usage_perc (leading latency signal). Order rail = running batch → vllm:num_requests_running.
  • Thermostat (ceiling) = HPA: every 15 s, desired = ceil(current × metric / target), max across metrics.
  • Basement + slow freight elevator (below) = GPU node pool + cold start (node provisioning → image pull → weight load → warm-up ≈ 5–10 min).
  • Dials that lie: tired greeter = CPU; reserved floor space = memory (vLLM pre-allocates gpu_memory_utilization=0.9); gas meter "any burner lit" = GPU utilization (DCGM_FI_DEV_GPU_UTIL = fraction of time any kernel ran).

Signals: which dial for which goal

Signal vLLM metric (current names) Use for Notes
Queue depth vllm:num_requests_waiting (gauge) Throughput/cost within a latency bound GKE guidance: start threshold ~3–5 per pod, tune by test
KV-cache usage vllm:kv_cache_usage_perc (gauge, 0–1) Latency-sensitive services (leading indicator) Old vllm:gpu_cache_usage_perc removed in v0.12 — check your version
Batch size vllm:num_requests_running Tighter latency targets
Queue time / TTFT vllm:request_queue_time_seconds, vllm:time_to_first_token_seconds (histograms) Validation, SLO alerting Lagging, noisy at low traffic
Preemptions vllm:num_preemptions_total Alert: KV cache too small Recompute = latency cliff
CPU / memory / GPU util — Don't scale on these Flat / pinned / saturates at low load

KEDA ScaledObject (recommended bridge)

KEDA creates and owns an HPA for you; it adds 0↔1 scaling, 60+ scalers (Prometheus, cron, queues). Defaults: pollingInterval: 30, cooldownPeriod: 300 (only governs →0). prometheus-adapter is heading to deprecation with KEDA as the recommended alternative.

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: llm-chat
spec:
  scaleTargetRef:
    name: vllm-chat            # Deployment
  minReplicaCount: 2           # warm floor: normal load + growth during one cold start
  maxReplicaCount: 12          # <= GPU quota / capacity reservation
  pollingInterval: 15
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
          policies:
            - type: Pods
              value: 4
              periodSeconds: 60
        scaleDown:
          stabilizationWindowSeconds: 900     # 15 min: cold start is expensive
          policies:
            - type: Pods
              value: 1
              periodSeconds: 300
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: sum(vllm:num_requests_waiting{model_name="chat"})
        threshold: "5"            # per-replica target (AverageValue) ≈ 2/3 of load-test knee
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: avg(avg_over_time(vllm:kv_cache_usage_perc{model_name="chat"}[2m]))
        threshold: "0.7"
        metricType: Value         # average ratio, not divided by replicas
    - type: cron                  # pre-warm predictable peaks (month-end, market open)
      metadata:
        timezone: Etc/UTC
        start: 30 8 28-31 * *
        end: 0 18 28-31 * *
        desiredReplicas: "6"

Plain HPA v2 equivalent (external metric via an adapter)

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: vllm-chat }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: vllm-chat }
  minReplicas: 2
  maxReplicas: 12
  metrics:
    - type: External
      external:
        metric: { name: vllm_num_requests_waiting }
        target: { type: AverageValue, averageValue: "5" }
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 0 }
    scaleDown:
      stabilizationWindowSeconds: 900
      policies: [ { type: Pods, value: 1, periodSeconds: 300 } ]

HPA mechanics to quote: sync every 15 s; desired = ceil(current × current/target); multiple metrics → max; global tolerance 10% (per-HPA tolerance in behavior.scaleUp/scaleDown via KEP-4951 — alpha 1.33, beta 1.34); defaults: scaleUp window 0 s, policies 100 % or 4 pods per 15 s (selectPolicy Max), scaleDown window 300 s. Scale-to-zero: HPAScaleToZero is beta and on by default in Kubernetes v1.37 (Aug 2026); minReplicas: 0 requires an Object or External metric.

Cold-start mitigations (the elevator)

  • Node: Karpenter (EKS) or AKS node auto-provisioning (Karpenter-based) / Cluster Autoscaler on GPU node pools; GPU quota ≥ maxReplicas × GPUs per replica; capacity reservations for thin GPU pools.
  • Over-provisioning: low-priority placeholder pods holding GPU nodes, preempted by real pods.
  • Image: pre-pull / image streaming. Weights: node-local NVMe cache or shared volume; Run:ai Model Streamer (published: ~4–6× faster for 15–233 GiB models).
  • Predictable peaks: KEDA cron trigger (month-end, payroll, market open).

Picking targets: load-test procedure

  1. Write SLO (e.g. TTFT p95 < 1 s, ITL p95 < 50 ms).
  2. Replay real prompt/output length distribution (vllm bench serve, NVIDIA AIPerf, Locust, k6).
  3. One replica; ramp concurrency/rate; record p95 TTFT/ITL and waiting, KV usage, running.
  4. Find the knee where p95 breaks SLO (e.g. ~8 waiting, ~90 % KV).
  5. Target ≈ knee ÷ (1 + growth during one cold start) — e.g. 50 % growth → ~⅔ of knee (5 waiting, 70 % KV).
  6. Fleet test: ramp, spike, decline; check SLO during scale-up, flapping, scale-down interrupting generations. Re-test on model / quantization / engine / GPU change.

Key terms

Term Meaning
HPA v2 autoscaling/v2 HorizontalPodAutoscaler — resource, pods, object, external metrics + behavior
Stabilization window Look-back period; scale-down uses the max recommendation in the window
Scale policy Rate limit: Pods or Percent per periodSeconds; selectPolicy Max/Min/Disabled
KEDA ScaledObject CRD that manages an HPA from event sources; adds 0↔1 activation
Custom vs External metrics API Per-pod metrics of scaled objects vs arbitrary metrics not tied to pods
Knee Load point where p95 latency turns sharply upward
Warm floor minReplicas sized for normal load + growth during one cold start
Scale-to-zero 0 replicas when idle; needs a signal that exists at zero (gateway/queue)

5 interview questions

  1. Why not scale LLM pods on GPU utilization? — DCGM GPU util is the fraction of time any kernel ran, so one active decode stream pins it near 100 %. It saturates at trivial load and can't distinguish 1 from 40 concurrent requests. Memory is pre-allocated (~90 %) and CPU doesn't track GPU work. Use waiting requests and KV-cache usage.
  2. How does a Prometheus metric reach the HPA? — Prometheus scrapes vLLM /metrics; KEDA's Prometheus scaler (or the older prometheus-adapter) serves it through the external/custom metrics API; KEDA creates the HPA. With multiple triggers the HPA takes the largest desired replica count.
  3. How did you choose target values? — One-replica load test with production length distribution, find the knee where p95 TTFT breaks SLO, then set the target below the knee by the traffic growth expected during a cold start (~⅔ of knee), validate with ramp/spike tests, re-test on every model/engine change.
  4. What HPA behavior settings for LLMs and why? — Immediate scale-up (window 0, several pods at once) because cold start is 5–10 min; scale-down window 10–15 min, 1 pod per few minutes, long terminationGracePeriodSeconds so in-flight generations drain. Tolerance per direction on 1.34+.
  5. Should you scale to zero? — Only for dev, internal, queue-driven batch or long-tail models. At zero the engine's metrics vanish, so wake-up needs a gateway/queue signal, and the first request eats the full cold start. Native HPA scale-to-zero is beta in K8s 1.37; KEDA has done it for years. Customer-facing SLO paths keep a floor of ≥2.

Likely follow-ups / traps: averaging hides a hot pod → use inference-aware routing (Gateway API Inference Extension / llm-d); multi-GPU replicas scale in units of TP size and need matching nodes/quota; split batch vs interactive pools; VPA doesn't apply (GPU count fixed by parallelism); on managed endpoints this becomes pay-per-token vs provisioned throughput sizing.

Expect one to a few minutes, and sometimes much longer, because G P U capacity pools are thin — the instance type you want may simply not be available in that zone, and the request bounces around. And quotas bite: teams often discover mid-surge that their G P U quota is below their max replicas. Step two: pull a container image of many gigabytes. Step three: load the weights. An eight-billion-parameter model in sixteen-bit precision is about sixteen gigabytes; a seventy-billion one is about a hundred and forty. Pulling that from object storage — S three on Amazon, Blob storage or A D L S on Azure — at a naive pace takes minutes. Published measurements put default loading of very large models at three to five minutes on a fresh node. Step four: warm-up — profiling memory, allocating burners, capturing execution graphs — another thirty seconds to a couple of minutes. Add it up: five to ten minutes from "open a kitchen" to "first meal served." Traffic can double in less time than that. What do you do about it? Shorten the elevator ride: cache weights on local disk or a fast shared volume, pre-pull images, and use a streaming loader like the Run A I model streamer, which v L L M supports — it reads tensors from object storage concurrently straight into G P U memory, cutting large-model load times several-fold in published tests. Keep spare basement space: over-provisioned G P U nodes held by low-priority placeholder pods that get evicted the moment a real serving pod needs them. Use scheduled scaling for the spikes you can predict — in financial services, market open, payroll day, month-end and quarter-end statement runs — a Keda cron trigger can pre-warm kitchens thirty minutes before. And set a generous startup probe, so Kubernetes doesn't kill a pod still loading weights, plus a readiness probe so no traffic arrives before the kitchen can cook. And set minimum replicas deliberately. The floor isn't "one because it's cheap"; it's the kitchens needed for normal traffic plus the growth during one full cold start — for a customer-facing service, usually at least two, which also buys availability across zones. [PAUSE 1s] ## Scale to zero Which brings us to the tempting option: close every kitchen at night. Keda has supported scaling to zero for years. As of Kubernetes one point thirty-seven, released last month, the built-in autoscaler's scale-to-zero support is beta and on by default, as long as you scale on an external or object metric — not C P U or memory, which can't exist when no pods do. But notice the chicken-and-egg problem in the picture. At zero, there are no kitchens, so there's no one to report waiting requests. The engine's own queue metric vanishes. To wake up, you need a signal from something that exists at zero: a gateway or proxy in front that counts incoming requests and holds them, or a message queue depth for batch work. And then the first customer waits the full cold start — minutes. So: scale to zero is excellent for dev environments, relaxed internal tools, queue-driven overnight batch, and long-tail fine-tuned models called a few times a day. It's wrong for anything customer-facing with a latency objective — there, savings come from the ceiling and scale-down speed, not from hitting zero. [PAUSE 1s] ## Picking the target with load testing Now the heart of the second question: "How did you pick the numbers?" The honest answer is: not by guessing — by load testing one kitchen until it breaks, and reading the dials at the moment it breaks. Here's the procedure. First, write down the objective. For example: time to first token under one second at the ninety-fifth percentile, and inter-token latency under fifty milliseconds at the ninety-fifth. Second, replay a realistic traffic shape — your real prompt and output length distribution, not a fixed hundred-token prompt. A load test with the wrong shape measures the wrong kitchen. Third, test one replica. Use a benchmarking tool — v L L M's own bench serve command, Nvidia's A I perf, or a Locust or k six script — and ramp concurrency or request rate step by step. At each step, record the latency percentiles alongside the dials: waiting requests, K V cache usage, running batch size. Fourth, find the knee. Plot ninety-fifth percentile time to first token against queue depth, and against cache usage. You'll see latency stay flat and then turn sharply upward. Say it bends when the queue holds about eight requests per pod and cache usage crosses roughly ninety percent. That's the breaking point of one kitchen. Fifth, set the target below the knee, with headroom for the elevator. If traffic can grow by, say, fifty percent during one cold start, your target should sit around two-thirds of the knee — about five waiting requests rather than eight, cache usage around seventy percent rather than ninety. The principle: the target encodes your cold start time. Sixth, validate the whole fleet with autoscaling on. Run a ramp, a sudden spike, and a slow decline. Watch for three things: did latency stay inside the objective during scale-up, did replicas flap up and down, and did scale-down interrupt long-running generations. Re-test whenever the model, quantization, engine version or G P U type changes — each one moves the knee. [PAUSE 1s] ## War story, resolved Back to the team scaling on G P U utilization. They moved the thermostat off the gas meter and onto the chairs and the burners: a Keda scaled object with waiting-requests and cache-usage triggers, targets from a one-replica load test, immediate scale-up, a fifteen-minute scale-down window, minimum two, maximum twelve, and a cron trigger for month-end. Node-local weight caching and a streaming loader cut cold start from about eight minutes to under three. Overnight, the fleet sat at two replicas instead of eight. At month-end, it scaled to eleven before the queue formed, and time to first token stayed under a second. [PAUSE 1s] ## Traps and follow-ups A few follow-ups interviewers probe. "What about multi-G P U models?" A seventy-billion model on four G P Us is one replica; scaling adds units of four, and nodes with four free G P Us are even scarcer capacity — plan quota for your maximum. "What if long prompts and short chats share the fleet?" Separate deployments with separate autoscalers — a batch pool on queue depth, an interactive pool on cache usage — so the document job can't starve chat users. "How do you avoid flapping?" Scale-down stabilization windows, per-direction tolerance, rate-limited scale-down, and metrics smoothed over a window in the Prometheus query. And on a managed endpoint — Bedrock, Microsoft Foundry, Databricks Model Serving — the same questions return as a capacity choice: pay-per-token with rate limits, or provisioned throughput sized by the same load test. [PAUSE 2s] ## The strong answer, out loud So when they ask, "How did you set up H P A and pick the scaling parameters for your inference service?", a strong answer, in about ninety seconds, sounds like this: "First, I didn't scale on C P U, memory, or G P U utilization. C P U doesn't track G P U work, the engine pre-allocates roughly ninety percent of G P U memory so memory is flat, and G P U utilization only says whether any kernel ran in the sample window, so it saturates at low load. Instead I scaled on the engine's own saturation signals from Prometheus: waiting requests as the throughput signal, and K V cache usage as the latency leading indicator. I used Keda with a Prometheus trigger, which manages an H P A underneath, and when you give it two metrics, it takes whichever demands more replicas. To pick targets, I load tested one replica with our real prompt and output lengths, ramped concurrency, and found the knee where ninety-fifth percentile time to first token broke our one-second objective — around eight queued requests or ninety percent cache usage. I set targets at about two-thirds of that, because cold start was several minutes. Behavior: immediate scale-up, several pods at once; scale-down with a fifteen-minute stabilization window, one pod at a time, with a long grace period so in-flight generations finish. Minimum two replicas; a cron trigger pre-warms for month-end. Node-local weight caching and a streaming loader shortened cold start. I'd scale to zero only for batch or internal endpoints. And we re-ran the load test on every model or engine change, because each one moves the knee." [PAUSE 2s] ## Sixty-second recap Back to the restaurant. On the left, the waiting chairs — queued requests, the most honest throughput signal. In the middle, kitchens with burner grids — the K V cache — whose occupancy warns you before the chairs fill. The dials that lie: the tired greeter, which is C P U; reserved memory; and the gas meter that reads a hundred percent whenever one burner is lit, which is G P U utilization. On the ceiling, the thermostat: current replicas times metric over target, the largest of several metrics wins, eager scale-up, slow and gentle scale-down. Keda wires Prometheus to it and handles zero. Below the floor, the basement and the slow elevator: node provisioning, image pull, weight loading, warm-up — five to ten minutes — which is why you keep a warm floor, cache weights, pre-warm for known peaks, and set targets below the knee you found by load testing one kitchen until it broke.
