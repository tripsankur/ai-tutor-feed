Classical ML Refresher: Imbalanced Datasets, Micro vs Macro F1

16 min listen · The classical ML questions that still show up in agentic AI interviews: how to handle an imbalanced dataset, and the difference between micro, macro and weighted F1. Resampling and SMOTE, class weights, threshold tuning, PR-AUC and recall at fixed precision, and a fraud-flavoured worked example you can say out loud.

Facts verified: 2026-09-25

Thesis: imbalance is fixed by changing three defaults on purpose — the metric (PR curve / constrained recall, not accuracy), the objective (class weights, resampling inside training folds only), and above all the decision threshold (tuned to business cost); micro F1 = per-decision (≈ accuracy), macro F1 = per-class (exposes the broken rare class).

Interview questions answered: "How do you handle an imbalanced dataset?" and "What's the difference between micro and macro F1?"

The mental image

A horizontal score line from 0 (left) to 1 (right). Every transaction is a dot: a huge grey dune of legitimate transactions on the left, a scatter of red fraud dots mostly on the right. A vertical gate = the threshold; right of it = flagged. Above, a scoreboard: left dial precision (flagged dots that are red), right dial recall (red dots that are flagged). Training techniques move dots; threshold tuning moves the gate; metric choice picks the dial. For micro/macro, split the line into three lanes, one per class.

Why accuracy and ROC flatter you

At 0.2% fraud (2 per 1,000), predicting "never fraud" = 99.8% accuracy, 0 recall.

Decent model: recall 80%, false positive rate 1%. Per 100,000 transactions: 200 fraud → 160 caught; 99,800 legit × 1% ≈ 998 false alarms → precision ≈ 14% (≈1 in 7 alerts real). ROC looks great because FPR divides by the huge negative class; precision feels every false alarm.

PR-AUC baseline = prevalence (0.002 here), not 0.5 as for ROC-AUC.

Techniques

Technique How Pros Cons / pitfalls
Random undersampling drop most majority rows fast discards info; overfits at extreme ratios; shifts probabilities
Random oversampling duplicate minority rows keeps all data memorization
SMOTE (k=5 neighbours default) synthetic point on segment between minority neighbours smoother than duplication paints minority into overlap regions; needs SMOTENC for categoricals; weak in high-dim; leakage if applied before split
Class weights (class_weight="balanced", XGBoost scale_pos_weight ≈ neg/pos) reweight the loss one line, no fake data distorts calibration
Threshold tuning (TunedThresholdClassifierCV, sklearn ≥ 1.5; FixedThresholdClassifier) choose the gate by cost/constraint via CV directly optimizes the business trade-off must tune on validation, not test
Calibration (CalibratedClassifierCV) map scores to true probabilities needed when scores feed provisions/ensembles do before thresholding

Evidence: van den Goorbergh et al. (JAMIA 2022) — undersampling/oversampling/SMOTE produced strongly miscalibrated models (overestimated minority probability) with no AUROC gain; threshold shifting gave a similar sensitivity/specificity balance. Carriero et al. (Statistics in Medicine 2025) report similar harms for ML models.

Leak-free resampling:

from imblearn.pipeline import make_pipeline
from imblearn.over_sampling import SMOTE
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.model_selection import TimeSeriesSplit, cross_val_score

pipe = make_pipeline(SMOTE(k_neighbors=5, random_state=0),
                     HistGradientBoostingClassifier())
# sampler runs only during fit, skipped at predict -> no synthetic points in validation folds
cross_val_score(pipe, X, y, cv=TimeSeriesSplit(5), scoring="average_precision")

Threshold tuned to a business cost:

import numpy as np
from sklearn.metrics import make_scorer, confusion_matrix
from sklearn.model_selection import TunedThresholdClassifierCV

def neg_cost(y, y_pred, fn_cost=300, fp_cost=5):
    tn, fp, fn, tp = confusion_matrix(y, y_pred, labels=[0, 1]).ravel()
    return -(fn * fn_cost + fp * fp_cost)

clf = TunedThresholdClassifierCV(
    HistGradientBoostingClassifier(class_weight="balanced"),
    scoring=make_scorer(neg_cost), cv=5).fit(X_train, y_train)
clf.best_threshold_

Recall at a minimum precision:

from sklearn.metrics import precision_recall_curve
p, r, t = precision_recall_curve(y_val, scores)
ok = p[:-1] >= 0.33
best_t = t[ok][np.argmax(r[:-1][ok])]   # max recall s.t. precision >= 1/3

Micro vs macro vs weighted F1 — worked example

100 transactions: 90 legit (L), 8 card fraud (C), 2 account takeover (T). Model: all 90 L correct; 4 of 8 C caught, 4 called L; 0 of 2 T caught, both called L; never predicts fraud for a legit.

Class Support Precision Recall F1
Legit 90 90/96 = 0.94 1.00 0.97
Card fraud 8 1.00 0.50 0.67
Takeover 2 0 (no predictions → zero_division) 0.00 0.00
  • Macro F1 = (0.97 + 0.67 + 0) / 3 ≈ 0.54–0.55 → per class, equal weight; exposes the broken class.
  • Micro F1 = pooled TP/FP/FN = 94/100 = 0.94 = accuracy (single-label multi-class).
  • Weighted F1 = 0.9·0.97 + 0.08·0.67 + 0.02·0 ≈ 0.92 → leans to the majority class.
from sklearn.metrics import f1_score, classification_report
f1_score(y, y_pred, average="macro", zero_division=0)     # ~0.545
f1_score(y, y_pred, average="micro")                      # 0.94
f1_score(y, y_pred, average="weighted", zero_division=0)  # ~0.924
f1_score(y_bin, y_bin_pred, average="binary", pos_label=1)  # report this for binary fraud

Traps: binary + average="micro" over both classes = accuracy again. "Macro F1" has two definitions — mean of per-class F1 (scikit-learn) vs F1 of mean precision and mean recall — say which. Never-predicted classes hit the zero_division rule.

Fraud-specific practice

  • Time-based splits (train on earlier months, validate later) — fraud drifts.
  • Label delay — chargebacks arrive weeks later; evaluate on matured windows.
  • Don't rebalance the test set — it must match production prevalence.
  • Monitor precision, alert volume and prevalence; re-tune the threshold after attack waves.
  • Reference dataset scale: the public European credit-card dataset has 492 frauds in 284,807 transactions (≈0.17%).

Key terms

Term Meaning
Prevalence fraction of positives; PR-AUC baseline
Precision / recall flagged-that-are-real / real-that-are-flagged
Average precision (PR-AUC) area under PR curve (step-wise)
Recall @ precision max recall subject to a precision floor
SMOTE interpolated synthetic minority samples
Class weight loss multiplier per class
Threshold tuning choosing the decision cut-off by cost/constraint
Calibration scores that behave like true probabilities
Micro / macro / weighted F1 pooled / unweighted per-class mean / support-weighted mean

5 interview questions (with strong answers)

  1. Why is accuracy a bad metric here? At 0.2% prevalence, "never fraud" scores 99.8%. Use the PR curve/average precision with prevalence as the baseline, plus an operating-point metric like recall at a precision floor or precision at the analysts' daily alert budget.

  2. SMOTE or class weights? Start with class weights (or scale_pos_weight) in gradient boosting — no synthetic data, one line. SMOTE only inside training folds via an imblearn pipeline; beware overlap regions, categoricals and calibration damage.

  3. What's the single most important lever? The threshold. Train a good ranker, calibrate if probabilities matter, then pick the gate on validation data by expected cost or the precision/alert constraint. Resampling mostly achieves what moving the threshold would, at the cost of calibration.

  4. Micro vs macro F1? Micro pools all decisions (= accuracy in single-label multi-class) and is dominated by frequent classes; macro averages per-class F1 equally and exposes rare-class failure; weighted averages by support. Example: 0.94 micro / 0.92 weighted / 0.55 macro for the same model.

  5. How would you validate a fraud model? Time-based split, matured labels, test set at production prevalence, report PR-AUC + recall@precision + per-class metrics, calibrate, tune threshold on validation, then monitor precision, alert volume and prevalence drift in production.
