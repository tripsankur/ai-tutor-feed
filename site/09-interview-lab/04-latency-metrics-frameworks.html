Latency Metrics That Matter & Choosing an LLM Deployment Framework

19 min listen · Two round-two questions, answered properly: which latency metrics you measured and why (time to first token, inter-token latency, end-to-end, throughput, goodput, tail percentiles, and how each is measured), and which framework you'd deploy with, from vLLM, SGLang and TensorRT-LLM through Dynamo, KServe, llm-d and Ray Serve to managed options, with current status verified.

Facts verified: 2026-09-25

The interview questions

"Which latency metrics did you measure, and why?" · "Which frameworks did you use for LLM deployment?"

One-sentence thesis

Measure what the user (or the calling agent) experiences — TTFT, ITL/TPOT, end-to-end at the median and tail — and report capacity as goodput (requests/s meeting all SLOs), then choose a serving stack by control, traffic shape, hardware, workload and team, settled by a goodput benchmark on your traffic.

The mental image: the wall of strips and the machine room

  • Wall (front): each request = a horizontal strip, time left→right. Left dot = sent; blank stretch = TTFT; flag = first token; tick marks = tokens (gaps = ITL); right dot = done (E2E). Stack thousands of strips → sort for p50/p95/p99; colour green/red vs SLO → green rate = goodput; fill rate = throughput.
  • Machine room (behind): bottom shelf = engines (vLLM, SGLang, TensorRT-LLM, llama.cpp/Ollama, TGI-in-maintenance); middle shelf = orchestrators (Dynamo, Dynamo-Triton, KServe, llm-d, Ray Serve LLM); curtain = managed (Bedrock, Microsoft Foundry, Databricks Model Serving).

Metrics cheat sheet

Metric Definition Dominated by Why it matters Typical target
TTFT Send → first visible content token (client-side, streaming) Network, gateway, queue, prefill Silence the human feels Chat p95 < ~1 s (often few hundred ms); voice tighter
ITL Gap between consecutive tokens (distribution) Decode, batch size, prefill interference Mid-stream freezes (watch p99) ~30–50 ms ≈ 20–30 tok/s (> reading speed ~6–7 tok/s)
TPOT (E2E − TTFT) / (output_tokens − 1) per request Decode Overall streaming pace Same order as ITL
E2E Send → last token ≈ TTFT + TPOT × (n−1) Output length Machine consumers (agents, JSON, tools) Budget per step + per agent run
Throughput req/s, output tok/s, total tok/s — per GPU / per $ Batch size, engine Cost efficiency —
Goodput Completed req/s meeting all SLOs (DistServe, OSDI '24) Everything above Honest capacity Max rate where ≥99 % meet SLO

Tail compounding: 5 sequential calls each within p95 → all five within target ≈ 0.95⁵ ≈ 77 %.

Measuring without fooling yourself

  • Client-side, streaming, first non-empty content chunk; reasoning models → time to first visible token.
  • Never average percentiles across pods — merge histograms:
histogram_quantile(0.99,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))

vLLM histograms: vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds (replaces time_per_output_token_seconds), vllm:e2e_request_latency_seconds, vllm:request_queue_time_seconds, vllm:request_prefill_time_seconds, vllm:request_decode_time_seconds. Quantile precision is bounded by bucket boundaries.

  • Open-loop (Poisson) arrivals for capacity tests; closed-loop users hide queueing (coordinated omission).
  • Real prompt/output length distributions; enough samples for p99 (thousands, not hundreds).
  • Different tokenizers → compare words/chars per second across models.
  • Production: OpenTelemetry span per LLM call with TTFT + token counts as attributes.
# vLLM benchmark with goodput against SLOs (ms)
vllm bench serve --model my-org/chat-model \
  --dataset-name custom --dataset-path prod_sample.jsonl \
  --request-rate 8 --burstiness 1.0 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,95,99 \
  --goodput ttft:1000 tpot:50 e2el:20000

(NVIDIA AIPerf is the successor to GenAI-Perf; reports TTFT, ITL, request latency, throughput, goodput with percentiles and configurable arrival patterns.)

Choosing: five questions

  1. Control/compliance — weights & data inside your network? → self-host or managed with private networking + no retention.
  2. Traffic shape — steady high volume → self-host; spiky / long tail → pay-per-token.
  3. Hardware — NVIDIA-only + max perf → TensorRT-LLM; mixed/portable → vLLM.
  4. Workload — prefix-heavy agents → benchmark SGLang, cache-aware routing; large fleets + long prompts → disaggregation (llm-d / Dynamo).
  5. Team — K8s platform team → KServe / llm-d; Python/Ray team → Ray Serve. Tie-breaker: goodput benchmark on your traffic and SLOs.

Key terms

Term Meaning
Prefill / decode Prompt processing (compute-bound, sets TTFT) / token-by-token generation (memory-bound, sets ITL)
Chunked prefill Split long prefills to interleave with decode → fewer ITL spikes
Goodput Req/s meeting all SLOs
SLO attainment Fraction of requests meeting SLOs
Open vs closed loop Arrival rate independent of server vs users waiting on responses
Disaggregated serving Prefill and decode on separate GPU pools with KV transfer
Coordinated omission Load generator backs off when server slows → under-reported latency

5 interview questions

  1. Which latency metrics did you measure and why? — Client-side TTFT (silence; queue + prefill), ITL p99 (freezes) and TPOT (pace), E2E for agent/structured steps, throughput per GPU reported as goodput vs SLOs; median + tail from merged histograms; open-loop load tests on real length distributions; OTel traces in prod.
  2. Why goodput instead of throughput? — Throughput rises with batch size until saturation even as many requests blow their SLOs; goodput counts only requests that met all SLOs, so it's the capacity you can actually promise (DistServe).
  3. Why is p99 of the fleet not the mean of pod p99s? — Percentiles aren't additive; sum histogram buckets across pods, then compute the quantile; precision bounded by bucket boundaries.
  4. vLLM vs SGLang vs TensorRT-LLM? — vLLM default for breadth/hardware portability; SGLang excels at prefix-heavy/multi-turn/structured workloads; TensorRT-LLM for peak NVIDIA perf and new precisions. Winner depends on workload and version → benchmark goodput.
  5. When would you pick a managed endpoint? — Spiky or long-tail traffic, small ops team, or models only available hosted; with private networking, no-retention terms, and provisioned throughput for SLO-critical paths. Still measure TTFT from your side.

Traps: quoting average latency; server-side TTFT only; recommending TGI for new work; Ollama for multi-tenant prod; "X is fastest" without workload conditions.

Hugging Face itself now points new deployments at v L L M or S G Lang. If T G I is in your stack, it still works — but have a migration plan, and say so. [PAUSE 1s] ## The middle shelf: orchestrators Middle shelf. An engine runs one model replica well. The orchestrators decide which replica gets which request, how many replicas exist, and whether one request's prefill and decode even happen on the same machine. Nvidia's stack has two names to keep straight. Triton Inference Server has been renamed Dynamo-Triton: a mature multi-framework server that can host language models alongside classical models — handy in financial services, where a fraud model and a language model often sit side by side. Nvidia Dynamo is the newer distributed layer designed for large language model serving across many G P Us: disaggregated serving, where prefill runs on one pool and decode on another, K V-cache-aware routing, and dynamic allocation of G P U workers. It sits on top of engines — Tensor R T L L M, v L L M or S G Lang. K Serve is the Kubernetes-native model serving platform, a C N C F incubating project, where you declare an inference service as a Kubernetes resource. Its newer resource type for language models, the L L M inference service, is built on L L M D and became production-ready earlier this year. L L M D itself is a Kubernetes-native distributed inference stack, founded by Red Hat, Google Cloud, I B M Research, CoreWeave and Nvidia, and accepted into the C N C F sandbox in March twenty twenty-six. It pairs v L L M with an inference-aware gateway that routes by K V cache hits and predicted latency rather than round-robin, plus prefill-decode disaggregation and autoscaling recipes. If the previous episode's point — scale with the autoscaler, balance with a smart router — made sense, this is that router, productised. Ray Serve's L L M layer is the Python-native option: v L L M engines under Ray, easy composition of multi-model pipelines, prefill-decode disaggregation and wide expert parallelism for mixture-of-experts models. It fits teams already running Ray, or Anyscale. [PAUSE 1s] ## The curtain: managed options And the curtain. Pull it closed, and you never touch the machine room; you just consume strips. On A W S, Amazon Bedrock gives serverless access to many hosted models, provisioned throughput for guaranteed capacity, and custom model import for your own fine-tuned open-weight models, billed by active model copies per minute in five-minute windows. On Azure, Microsoft Foundry — renamed from Azure A I Foundry at the start of this year — offers serverless pay-per-token deployments, provisioned throughput units for guaranteed capacity, and managed compute for open models. And Databricks Model Serving, on both clouds, offers pay-per-token foundation model endpoints, provisioned throughput billed in model units, either on demand or reserved for one or three months, plus custom model serving, with the A I gateway for rate limits and guardrails and Unity Catalog for governance. For regulated workloads, the questions behind the curtain are private networking — Private Link on Azure, PrivateLink with a customer V P C on A W S — data residency, whether prompts are retained or logged, and whether the provider's latency service level matches yours. Managed doesn't remove the metrics from the wall; you still measure time to first token from your side of the curtain. [PAUSE 1s] ## How to choose So how do you choose? Five questions, in order. One: control and compliance. Must weights and data stay inside your network, with your own audit? That pushes toward self-hosting or managed services with private networking and no data retention. Two: traffic shape. Steady, high-volume traffic on one or two models favours self-hosting, where a saturated G P U beats per-token pricing. Spiky, low-volume, or a long tail of models favours managed pay-per-token. Three: hardware. Nvidia only, and performance is paramount? Tensor R T L L M is on the table. Mixed hardware or likely to change? v L L M. Four: workload. Prefix-heavy agents and multi-turn chat: benchmark S G Lang against v L L M, and use cache-aware routing. Many replicas and long prompts: disaggregation through L L M D or Dynamo starts to pay. Five: team. Kubernetes-native platform team: K Serve or L L M D. Python-native M L team on Ray: Ray Serve. And the tie-breaker: run a goodput benchmark with your own traffic shape and your own objectives. Leaderboards measure someone else's wall. [PAUSE 2s] ## The strong answer, out loud When they ask, "Which latency metrics did you measure, and why?", a strong answer in about ninety seconds sounds like this: "We measured from the client side with streaming on. Time to first token — the silence before anything appears — because it's dominated by queueing and prefill, and it's what a human feels first; our target was under one second at the ninety-fifth percentile. Inter-token latency at the ninety-ninth percentile, to catch mid-stream freezes when a long prompt's prefill interrupted other streams, alongside time per output token for overall pace — anything above reading speed is fine for humans. End-to-end latency for agent steps and structured outputs, because a machine consumer waits for the whole response, and sequential calls compound the tail. Then throughput per G P U, but reported as goodput: requests per second that met all our latency objectives, because raw throughput at saturation hides failed requests. Always median and tail, never the mean, and fleet percentiles computed from merged histograms, never averaged across pods. We load tested with open-loop arrivals on our real prompt and output lengths, and traced production with OpenTelemetry to find which step owned the tail." And when they ask, "Which framework did you use?": "We served with v L L M behind an Open A I compatible A P I, because of its model coverage, paged K V cache, prefix caching and chunked prefill, and hardware portability. I'd benchmark S G Lang for our prefix-heavy agent traffic, and Tensor R T L L M if we were committed to Nvidia and needed the last margin of performance. On Kubernetes, K Serve or L L M D for inference-aware routing and autoscaling; Dynamo if we needed disaggregation at larger scale. I'd avoid T G I for new work since it's in maintenance mode, and keep Ollama for local development. For spiky or long-tail models, a managed endpoint — Bedrock, Foundry or Databricks — with private networking. And the decision was made on goodput for our own traffic, not on a leaderboard." [PAUSE 1s] Likely follow-ups. "Is v L L M or S G Lang faster?" — it depends on workload and version; name the conditions and say you'd benchmark. "Why not report the average?" — it hides the tail. "Why is server-side time to first token lower than what users see?" — network, gateway, and guardrails aren't in it. "Why can raw throughput go up while users get angrier?" — that's the difference between throughput and goodput. [PAUSE 2s] ## Sixty-second recap Back to the wall. Every request is a strip, left to right. The blank stretch before the flag is time to first token — network, gateway, queue, prefill — the silence a human feels. The gaps between tick marks are inter-token latency; watch the ninety-ninth percentile for freezes, time per output token for pace. Dot to dot is end-to-end, the number for agents and structured output, and sequential calls compound it. How fast the wall fills is throughput; colour every strip green or red against your objectives, and the green rate is goodput. Sort the strips for median and tail, merge histograms instead of averaging percentiles, and load test open loop with your real traffic shape. Behind the wall, the machine room. Bottom shelf, engines: v L L M the default, S G Lang for prefix-heavy work, Tensor R T L L M for peak Nvidia performance, llama C P P and Ollama for local, and T G I in maintenance mode. Middle shelf, orchestrators: Dynamo and Dynamo-Triton, K Serve, L L M D, Ray Serve. And the curtain: Bedrock, Microsoft Foundry, Databricks Model Serving.
