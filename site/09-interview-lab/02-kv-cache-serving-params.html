KV Cache Management & Serving Parameters (max seqs, batched tokens)

19 min listen · How the KV cache really works and is managed in vLLM: sizing math, paged blocks, prefix caching, LRU eviction and preemption, chunked prefill, and exactly what max_num_seqs, max_num_batched_tokens, gpu_memory_utilization and max_model_len trade off, with a step-by-step tuning procedure.

🎙 Audio not rendered yet.

Facts verified: 2026-09-25 (vLLM v0.30.0 source: vllm/config/cache.py, vllm/config/scheduler.py, vllm/engine/arg_utils.py, vllm/v1/core/kv_cache_utils.py; docs: optimization, prefix caching design, benchmarking sweeps)

Thesis: on a self-hosted LLM the KV cache — not compute — caps concurrency; vLLM manages it as a fixed pool of paged blocks, and four knobs (gpu_memory_utilization, max_model_len, max_num_seqs, max_num_batched_tokens) decide how that pool is sized, admitted into, and fed each step.

Interview questions this answers: "How does the KV cache work, and how is it managed?" · "Explain serving parameters like number of sequences and batched tokens — how would you set them?"

Sizing math

KV bytes/token = 2 (K,V) × n_layers × n_kv_heads × head_dim × bytes_per_elem

Model (BF16 KV) layers KV heads head_dim bytes/token 8k-token conversation
Llama 3.1 8B 32 8 128 131,072 B = 128 KiB 1 GiB
Llama 3.x 70B 80 8 128 327,680 B = 320 KiB 2.5 GiB

Worked example (8B on one 80 GB GPU): 80 × 0.92 ≈ 73.6 GB − 16 GB weights − ~4 GB activations/graphs ≈ 54 GB → ~410k tokens → ≈ 50 concurrent at 8k tokens, ≈ 200 at 2k, ≈ 3 at 128k. FP8 KV (--kv-cache-dtype fp8) doubles these. TP=2 halves per-GPU KV per token (each GPU holds half the KV heads).

Don't trust arithmetic alone — vLLM logs at startup:

GPU KV cache size: 409,600 tokens, Maximum concurrency for 16,384 tokens per request: 25.00x

and refuses to start if one max_model_len request can't fit, printing "the estimated maximum model length is N".

The four knobs (v0.30.0)

Knob What it is Default Raise it → Lower it →
gpu_memory_utilization Fraction of total GPU memory this instance may use (weights + activations + KV) 0.92 more KV blocks, fewer preemptions; OOM risk with co-tenants/fragmentation safer, less concurrency
max_model_len Max prompt + output tokens per request model's config allows long docs; few giants can hog the pool protects pool; rejects long requests
max_num_seqs Max requests in RUNNING per engine (per DP rank); also sizes CUDA-graph/buffers OpenAI server: 1024 on ≥70 GB non-A100 (H100/H200) and ≥160 GB (B200/B300); 256 otherwise incl. A100 throughput ↑ until KV full; ITL ↑; preemptions if > what KV holds smoother ITL; queueing ↑ → TTFT ↑
max_num_batched_tokens Max tokens per engine step (decodes + prefill chunks) OpenAI server: 8192 (H100/H200-class), 16384 (≥160 GB), 2048 otherwise TTFT ↓, throughput ↑; ITL ↑ (big prefills slow decodes) ITL ↓; TTFT ↑

Related (v0.30.0): enable_prefix_caching (default True) · prefix_caching_hash_algo (default sha256) · chunked prefill (default on where supported) · long_prefill_token_threshold (default 0 = off) · policy = fcfs | priority · max_num_queued_reqs (reject with HTTP 503 when full) · watermark (fraction of blocks kept free at admission, default 0.0) · scheduler_reserve_full_isl (default True: admit only if full prompt fits) · performance_mode = balanced | interactivity | throughput (throughput doubles default max_num_seqs and max_num_batched_tokens) · kv_cache_dtype (auto, fp8, …) · KV offloading via OffloadingConnector (--kv-transfer-config).

Preemption: V1 default mode is RECOMPUTE (not SWAP). Log line: "…is preempted by PreemptionMode.RECOMPUTE mode because there is not enough KV cache space…". Remedies (from docs): raise gpu_memory_utilization, lower max_num_seqs / max_num_batched_tokens, raise tensor/pipeline parallel size.

Tuning procedure

  1. Measure prompt/output length distributions (p50, p99), peak concurrency; set SLOs (e.g. TTFT p95 < 1 s, ITL p95 < 50 ms).
  2. max_model_len ← p99(prompt + output) + headroom, not the model card max.
  3. gpu_memory_utilization as high as stable (0.92–0.95 on dedicated GPUs); consider kv_cache_dtype=fp8; read startup log (KV tokens, max concurrency).
  4. max_num_seqs ≈ KV tokens ÷ typical live tokens per request (+ credit for prefix sharing), not 1024.
  5. Sweep max_num_batched_tokens {2048, 4096, 8192, 16384} × 2–3 max_num_seqs values with vllm bench sweep serve / vllm bench serve (or GuideLLM) at target request rate on a realistic mix; choose max goodput meeting both SLOs.
  6. Production: alert on vllm:num_preemptions rate, vllm:kv_cache_usage_perc, vllm:num_requests_waiting, prefix hit rate (vllm:prefix_cache_hits / vllm:prefix_cache_queries), TTFT/ITL histograms.
  7. Split conflicting workloads (long-doc summarization vs interactive chat) into separate pools with their own knobs.

Key terms

Term Meaning
KV cache Per-token, per-layer key and value vectors kept so decode doesn't recompute attention inputs
Block / block table Fixed-size page of KV (16 tokens by default) / per-request map from logical positions to physical blocks
PagedAttention Attention kernel reading KV through block tables; waste limited to last partial block
Automatic prefix caching Full blocks hashed with parent hash + extras (LoRA, multimodal, cache_salt); ref-counted sharing
LRU eviction Freed blocks stay cached in a free queue; head (least recently used) is evicted on reuse
Preemption (RECOMPUTE) When pool is exhausted, newest running request is freed and later re-prefilled
Chunked prefill Long prompts split across steps; decodes scheduled first each step
Goodput Throughput counted only for requests meeting latency SLOs

5 interview questions with strong answers

  1. "How does the KV cache work?" — Attention for each new token needs K and V of all prior tokens at every layer; caching them avoids quadratic recomputation. Prefill writes them for the whole prompt (compute-bound); each decode step reads all and appends one (memory-bound). Size/token = 2 × layers × KV heads × head_dim × bytes → ~128 KiB for Llama 3.1 8B.
  2. "How does vLLM manage it?" — Reserves gpu_memory_utilization of GPU memory, carves post-weights space into 16-token blocks, allocates on demand via block tables (PagedAttention), shares identical prefixes by hashed, ref-counted blocks (salted per tenant), keeps freed blocks cached until LRU eviction, and preempts the newest request (recompute) when the pool runs dry.
  3. "What do max_num_seqs and max_num_batched_tokens control?" — max_num_seqs caps requests per batch: more → throughput, but ITL rises and beyond KV capacity causes preemption. max_num_batched_tokens is the per-step token budget: decodes first, prefill chunks fill the rest; small → smoother ITL, large → better TTFT/throughput.
  4. "You see frequent preemption warnings — what do you do?" — Confirm with vllm:num_preemptions and KV usage; then lower max_num_seqs toward real KV capacity, cap max_model_len/max output, enable FP8 KV cache, raise gpu_memory_utilization, add TP, or split long-context traffic into its own pool.
  5. "Prefix cache hit rate is near zero — why?" — Something variable (timestamp, user name, request ID) at the top of the prompt changes every downstream block hash; also only full 16-token blocks are cached, per-tenant salts partition sharing, and round-robin routing spreads prefixes across replicas (use prefix-aware routing). If the startup log says maximum concurrency is about fifty at your typical length, a counter of a thousand doesn't buy a thousand users. It buys preemptions. The lane budget: max num batched tokens, the most tokens processed in one engine step, decodes and prefill chunks combined. The server default is eight thousand one hundred and ninety-two on H one hundred class cards, sixteen thousand three hundred and eighty-four on the largest, like the B two hundred, and two thousand and forty-eight on smaller ones. The trade is time to first token against inter-token latency. A small budget, like two thousand, keeps steps short and streams smooth, but new prompts take more steps to get through. A large budget does the opposite, and the v L L M docs recommend going above eight thousand for throughput, especially for small models on big G P Us. A related knob, the long prefill token threshold, caps how much of one step a single long prompt can take, so one filing can't crowd out a dozen chat questions. Two more controls: a performance mode, whose throughput option doubles the default counter and lane budget, and a queue cap that rejects new requests with a five oh three once the line gets too long, so clients retry elsewhere. [PAUSE 1s] ## The tuning procedure Here's the procedure, in order. Step one: write down the workload and the targets. Get the distributions of prompt length and output length, the median and the ninety-ninth percentile, not the averages. Know the peak concurrency. Set the service levels, for example time to first token under one second at p ninety-five and inter-token latency under fifty milliseconds. Step two: set max model len from those distributions, not from the model card. Step three: set the fence as high as is stable. Consider an eight-bit K V cache. Then read the startup log for K V cache tokens and maximum concurrency. Step four: estimate the real concurrency the grid can hold. Divide the K V tokens by the typical tokens a live conversation holds, and give a little credit for prefix sharing. Set max num seqs near that number, not at the default of a thousand. Step five: sweep the lane budget, say two, four, eight and sixteen thousand, with a couple of counter values, replaying your real traffic mix at your target request rate. v L L M ships benchmark and sweep commands for exactly this. Pick the configuration with the best goodput: the most requests per second that still meet both latency targets. Step six: watch it in production. Chart K V cache usage, preemptions, waiting requests, prefix cache hit rate, and the time to first token and inter-token latency histograms. Any steady stream of preemptions means you're over-admitting. Lower the counter or add memory. Step seven: split workloads that fight. Long-document summarization and short interactive chat want opposite settings. Two pools with their own knobs beat one pool with a compromise. [PAUSE 1s] ## Pitfalls and a war story Four traps. One: treating G P U memory utilization as a live metric; it's a setting, and memory graphs will read ninety-some percent forever. Two: confusing max num batched tokens, a per-step engine budget, with maximum output length, a per-request cap. Three: leaving max num seqs at a thousand and twenty-four when your grid holds fifty real conversations. Four: breaking prefix caching by putting something variable at the very top of the prompt, like a timestamp or a user's name. Every row after it gets a different fingerprint. Stable content first, variable content last. A war story in a common shape: an agent platform put the current timestamp at the top of its system prompt, followed by six thousand tokens of tool definitions. Prefix cache hit rate near zero, time to first token over a second. Someone moved the timestamp to the end. Hit rate above ninety percent, time to first token a few hundred milliseconds, same hardware, no settings changed. [PAUSE 2s] ## The strong answer, out loud When they ask "how does the K V cache work and how is it managed?", a strong ninety-second answer sounds like this. "During generation, each token's attention needs the keys and values of all earlier tokens at every layer, so we cache them instead of recomputing. Prefill writes them for the whole prompt, and each decode step reads them all and appends one. Size per token is two, times layers, times K V heads, times head dimension, times bytes. For an eight-billion Llama that's about a hundred and twenty-eight kilobytes per token, so memory, not compute, caps concurrency. v L L M manages it with paged attention. At startup it reserves a fraction of G P U memory, carves what's left after the weights into fixed blocks of sixteen tokens, and gives each request blocks on demand through a block table, so waste is only the last partial block. Full blocks are hashed with their prefix for automatic prefix caching, shared by reference count, with a cache salt for tenant isolation. Freed blocks stay reusable until they're evicted least recently used. When the pool runs out mid-decode, the scheduler preempts the newest request and recomputes it later. So I alert on preemptions and K V usage, and I can shrink the cache with an F P eight K V cache or add memory with tensor parallelism." When they ask about serving parameters: "Four knobs. G P U memory utilization sets the pool size. Max model len caps the worst-case request. Max num seqs caps how many requests share a batch: more gives throughput, but costs inter-token latency, and past what the cache holds it just causes preemption. Max num batched tokens is the per-step token budget. Decodes go first, and prefill fills the rest in chunks, so smaller favors smooth streaming and larger favors time to first token and throughput. I tune them by measuring the length distributions, reading the startup concurrency estimate, and sweeping configurations under realistic load to maximize goodput against both latency targets." Follow-ups to expect. "Why not swap preempted requests to C P U?" Recompute is cheaper in the current design; for long, reused contexts, K V offloading to C P U memory through a connector is the modern answer. "Can prefix caching leak between tenants?" Through timing, yes, hence cache salts. "What changes for a hundred-and-twenty-eight-thousand-token workload?" A separate pool, eight-bit cache, tensor parallelism, a low counter, a long-prefill cap. The traps: saying the cache stores attention scores, since it stores keys and values; saying max model len reserves memory per request; and quoting defaults without saying they depend on G P U and version.
