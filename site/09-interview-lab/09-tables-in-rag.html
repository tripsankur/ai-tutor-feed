Tables in RAG: Multi-Page Tables, Parsing & Ingestion Strategies

16 min listen · Answers the interview questions on large tables that span multiple pages and on table parsing and ingestion: why naive chunking shreds tables, how layout-aware parsers and vision models recover structure, how to stitch continued tables across page breaks, which representations to index, when to route to text-to-SQL, and how to evaluate it all.

Facts verified: 2026-09-25

Thesis: tables must be parsed structurally, stitched across page breaks, validated, and indexed in several representations (summary → rows-with-headers → intact parent), with aggregation questions routed to SQL instead of retrieval.

Interview questions answered: "How would you handle large tables that span multiple pages?" and "What are your table parsing and ingestion strategies?"

Why naive chunking destroys tables

  • Line-by-line extraction interleaves cells across columns; wrapped cells become extra rows.
  • Header row separated from data rows by a chunk boundary or a page break.
  • Merged cells / multi-level headers flattened away.
  • Units and scale live in the caption ("in thousands") and never reach the rows.
  • Running headers/footers spliced mid-table; footnote markers detached.
  • Scanned/image tables yield nothing from the text layer.

Pattern: route — cheap parser everywhere, expensive parser only for table pages / failed checks.

Stitching multi-page tables

Continuation score between fragment A (page n) and B (page n+1):

def continuation_score(a, b, page_h):
    s = 0
    s += a.bottom > 0.80 * page_h            # A ends near page bottom
    s += b.top    < 0.20 * page_h            # B starts near page top
    s += a.n_cols == b.n_cols                # same column count
    s += cols_aligned(a.col_x, b.col_x, tol=0.02)   # column edges line up
    s += no_heading_between(a, b)            # ignoring running header/footer
    s += (b.header == a.header) or looks_like_data(b.rows[0], a.col_types)
    s += "continued" in (b.caption or "").lower()
    return s

def merge(a, b):
    rows = b.rows[1:] if b.header == a.header else b.rows   # drop repeated header
    if rows and is_continuation_row(rows[0]):               # split row across break
        a.rows[-1] = glue(a.rows[-1], rows[0]); rows = rows[1:]
    return Table(header=a.header, rows=a.rows + rows, pages=a.pages + b.pages)

Then validate: row counts vs pages, column totals vs totals row, numeric columns parse as numbers. Log every merge decision. Flatten multi-level headers ("2025 › Q1").

Evaluation (three layers)

  1. Parsing — cell-level accuracy vs hand-checked sample; TEDS (tree-edit-distance similarity) for structure; automatic totals/row-count checks.
  2. Retrieval — golden set split by type: single-cell lookup, row comparison, whole-table, aggregation; right table + right rows returned?
  3. Answers — numeric comparison with units (not string match); tag failures by stage: parse / stitch / retrieve / reason.

War story: tables parsed perfectly but caption "in thousands" not propagated → answers 1,000× too small; string-match evals missed it.

5 interview questions (with strong answers)

  1. Why does naive chunking fail on tables? It extracts line by line and cuts by size, so headers separate from rows, cells interleave across columns, merged headers and units are lost, and page breaks splice footers into the table — the model gets unlabeled numbers and picks the wrong column.

  2. A table spans three pages. How do you ingest it? Parse each page with a layout-aware parser, then stitch: fragments at page bottom/top, same column count, aligned column edges, no heading between, repeated header dropped or first row typed like data; glue split rows; validate row counts and totals; store as one logical table with page provenance.

  3. What do you actually embed for a table? A model-written summary (retrieval key) and row-level chunks carrying title, full headers and units; the intact HTML/Markdown table is the parent passed to the LLM. Large numeric tables also go to a database for text-to-SQL.

  4. When would you use a vision LLM parser, and how do you trust it? For scans, image tables, nested headers — routed only for hard pages. Trust via validation: totals reconciliation, row counts, cross-check with the text layer, human review on disagreement; pin model versions.

  5. How do you evaluate table QA? Separately at parse (cell accuracy/TEDS), retrieval (by question type) and answer (numeric match with units), tagging failures by stage.
