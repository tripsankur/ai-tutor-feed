Track 1 · Databricks Platform & Data Engineering · Episode 2

Databricks on Azure vs AWS: Deployment, Identity, Storage, Networking, Billing

19 min listen · Same architecture, different keys — how the two-buildings model maps onto Azure and AWS: first-party vs third-party deployment, Entra ID vs IAM, ADLS vs S3, VNet injection vs customer VPC, Private Link on both, and the billing split.

Facts verified: 2026-07-17 (Azure serverless workspaces GA Mar 2026; first-party vs third-party model)

The mental model: two plots, identical buildings

Platform identical (Spark, Delta, UC, MLflow, APIs). Five civic details differ: permits, keys, vault, fence, bills.

The five differences

# Dimension Azure AWS
1 Permits (deployment) First-party service; workspace from portal/ARM/Terraform; locked managed resource group auto-created; Microsoft support Third-party (first cloud, 2014, most mature); connect via cross-account IAM role (control plane assumes it to provision EC2 in your VPC) + root S3 bucket; account console manages credential/storage/network configs as objects
2 Keys (identity) Entra ID end-to-end: users, service principals, managed identities, SCIM, conditional access SSO federation for humans; IAM roles for machines; clusters wear instance profiles
3 Vault (storage) ADLS Gen2 via abfss://, storage accounts + containers, hierarchical namespace ON (real dirs, atomic renames) S3 buckets via s3://
3b UC storage credential Access connector (managed identity + Storage Blob Data Contributor) IAM role + external ID (trust policy to Databricks; external ID prevents confused-deputy)
4 Fence (network) Managed VNet (default) or VNet injection (2 subnets: host+container, your NSGs/routes); Private Link front-end + back-end; Serverless Workspaces GA 2026 — no VNet/NAT/PE, seconds to create Customer-managed VPC, security groups, AWS PrivateLink (front+back), S3 gateway VPC endpoint; NCC for serverless egress on both clouds
5 Bills One Microsoft invoice; DBUs draw down Azure committed spend Two invoices: Databricks (DBUs) + AWS (EC2/S3/network); FinOps must join them

Word-for-word translation pairs (say these in interviews)

  • VNet injection ↔ customer-managed VPC
  • NSG ↔ security group
  • Azure Private Link ↔ AWS PrivateLink
  • Service endpoint ↔ VPC endpoint
  • Managed identity / service principal ↔ IAM role / instance profile
  • Access connector ↔ storage-credential IAM role + external ID
  • abfss://container@account.dfs.core.windows.net/ ↔ s3://bucket/

Gotchas

  1. Subnet sizing (Azure VNet injection) — subnets not resizable post-deploy; IP exhaustion kills cluster scale-out. Size = peak concurrent nodes × 2 + headroom. AWS twin: shared-VPC subnet IP exhaustion.
  2. External ID missing on AWS storage-credential role = confused-deputy audit finding. Know why it exists.
  3. Egress cost blindness — cross-region/cloud reads can dwarf DBUs. Co-locate compute + storage.
  4. Feature parity lag — historically AWS first, Azure close, GCP later. Check availability matrix before design promises.

Interview Q&A

Q1. What changes when you move Databricks work from Azure to AWS? "Same architecture, different keys." Platform identical; five integration deltas: portal deploy → cross-account IAM role handshake; Entra → IAM roles/instance profiles; ADLS+access connector → S3+credential role with external ID; VNet injection+Private Link → customer VPC+PrivateLink; one invoice → split billing. Concept-for-concept translation — walk the trust policies past security the same way any cross-cloud design change gets reviewed. [If you're deepest on one cloud, say so and show you'd validate the equivalent controls before shipping on the other.]

Q2. How does Databricks create clusters in a customer's AWS account? Cross-account IAM role the customer creates and scopes; the control plane assumes it to provision/manage EC2 + networking in the designated VPC. No credentials shared; role assumption is auditable via CloudTrail.

Q3. How does Unity Catalog access cloud storage securely on each cloud? Storage credential abstraction: Azure = access connector (managed identity) granted on the storage account; AWS = IAM role with Databricks trust policy + external ID. External locations bind paths to credentials; notebooks never hold raw keys.

Q4. What's the enterprise networking pattern on each cloud? Azure: VNet injection (host/container subnets, NSGs, your routing) + Private Link front/back; 2026 option: serverless workspaces, no customer network at all. AWS: customer-managed VPC + security groups + PrivateLink + S3 gateway endpoint. Serverless egress both clouds: Network Connectivity Configuration.

Q5. Billing difference and why enterprises care? Azure: single Microsoft invoice, counts toward Azure commit — procurement-friendly. AWS: separate Databricks + AWS bills, negotiated independently, FinOps joins the meters.
