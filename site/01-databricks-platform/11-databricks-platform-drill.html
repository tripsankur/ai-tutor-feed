This is the Track One drill — fifteen questions covering the entire platform, from the two buildings to Lakebase. Same format as always: I ask, you answer out loud, then I give you a strong answer to compare. These are ordered roughly as the track was, so you can hear where the gaps are. Ready. [PAUSE 2s] Question one. Walk me through Databricks architecture — where does code run and where does data live? [PAUSE 6s] Strong answer: two planes. The control plane in Databricks' account holds the U I, job scheduler, cluster manager, and Unity Catalog metastore — metadata and orchestration only. The compute plane holds clusters and storage in the customer's account, with connections initiated outbound from the customer side. Instructions cross one way, results the other; raw data never enters the control plane. Serverless moves compute into Databricks-operated pools, but storage access stays governed through Unity Catalog with short-lived scoped credentials. [PAUSE 2s] Question two. What is Photon and when would you NOT enable it? [PAUSE 6s] Strong answer: a C plus plus vectorised execution engine under unchanged Spark A P Is — column batches instead of rows, two to four times faster on C P U-bound work, billed at a premium D B U rate. Skip it when the workload is I O-bound or U D F-heavy, because the speed needle barely moves while the money needle climbs. [PAUSE 2s] Question three. How does Delta Lake provide ACID transactions on object storage that has none? [PAUSE 6s] Strong answer: immutable parquet files plus a transaction log — and the log IS the table. A write stages files invisibly, then commits by atomically writing one numbered log entry. Readers reconstruct state from a checkpoint plus the log tail. Concurrent writers race for the next entry number; the loser rechecks for real conflicts and retries — optimistic concurrency. [PAUSE 2s] Question four. What are deletion vectors and why do they matter for compliance deletes? [PAUSE 6s] Strong answer: sidecar bitmaps that mark rows dead without rewriting the parquet file, turning deletes, updates, and merges into metadata-sized operations, compacted later in the background. Privacy-law purges stop being terabyte rewrites. Caveat: they need reader version three, so every external consumer of the table must speak that protocol before you enable them. [PAUSE 2s] Question five. Liquid clustering versus partitioning — what's the current guidance? [PAUSE 6s] Strong answer: liquid clustering by default for new tables — incremental, metadata-driven, keys changeable without rewrite, and cluster-by-auto can pick keys from the real query workload. Hive partitioning survives for one honest case: hard lifecycle boundaries, like dropping whole months on a retention schedule. Z-order is the legacy answer you migrate away from. [PAUSE 2s] Question six. What did Unity Catalog actually change compared to the workspace-metastore world? [PAUSE 6s] Strong answer: it moved governance from per-workspace to account level — one metastore per region, one three-level namespace, and every asset type — tables, volumes, functions, models, vector indexes — as securables under one grant, lineage, and audit system. Storage access goes through credentials and external locations, so no keys live in code. [PAUSE 2s] Question seven. Explain ABAC in Unity Catalog and the chain that makes it scale. [PAUSE 6s] Strong answer: attribute-based access control — row-filter and column-mask policies attached at catalog or schema level, triggered by governed tags rather than object names, auto-applying to current and future objects. The chain is classify, tag, protect: agentic classification discovers sensitive data and applies tags, tags trigger policies, policies enforce masks and filters — thousands of policies per metastore instead of per-table sprawl. [PAUSE 2s] Question eight. How does the managed C D C connector in Lakeflow Connect actually work? [PAUSE 6s] Strong answer: two pieces. An ingestion gateway on classic compute inside the customer's network reads the database's change log continuously and stages raw events into a Unity Catalog volume. A serverless ingestion pipeline applies those changes to Delta tables in order — initial snapshot, then C D C convergence, exactly-once. The gateway needs real network planning, and its lag must stay inside the source's change-log retention. [PAUSE 2s] Question nine. Streaming table versus materialized view in declarative pipelines. [PAUSE 6s] Strong answer: streaming tables accumulate — they're Unity Catalog managed tables that are also streaming targets, processing append and C D C flows exactly once. Materialized views derive — engine-maintained computed results where the engine chooses incremental refresh or full recompute. Accumulate versus derive: bronze and silver lean streaming tables; gold leans materialized views. [PAUSE 2s] Question ten. How do you get slowly-changing-dimension type two without writing a merge? [PAUSE 6s] Strong answer: auto C D C — declare the flow with a key, a sequence-by column to resolve out-of-order events, and stored-as S C D type two. The engine maintains validity windows and history. S C D two becomes a declared property of the table instead of hand-written merge choreography. [PAUSE 2s] Question eleven. When do you orchestrate with Lakeflow Jobs versus Airflow? [PAUSE 6s] Strong answer: Databricks-internal D A Gs belong in Lakeflow Jobs — zero orchestrator infrastructure, repair runs, and data-driven triggers: file-arrival on volumes and table-update triggers so downstream fires on actual upstream commits instead of cron optimism. Airflow keeps cross-platform flows that span systems outside Databricks, calling Jobs through the A P I as single tasks. Two conductors, clear jurisdictions. [PAUSE 2s] Question twelve. Where does d b t fit on Databricks when declarative pipelines already exist? [PAUSE 6s] Strong answer: d b t models are SELECT statements compiled onto a sequel warehouse, with ref building the D A G — same declarative philosophy, batch-sequel-only, beloved by analytics engineers, portable across platforms. Streaming and C D C go to declarative pipelines; analyst-owned gold marts can stay d b t, running as a d b t task in Lakeflow Jobs under the same governance. Common split: engineering owns bronze and silver, analytics owns gold, handoff at silver. [PAUSE 2s] Question thirteen. A pipeline is slow AND expensive. First three moves? [PAUSE 6s] Strong answer: one, read both gauges — slow, expensive, or both, because they point at different failures. Two, open the query profile and find where time actually went. Three, classify the bottleneck — reading too much, shuffling too much, C P U pegged, or workers idle — and match the fix: clustering and skipping for I O, broadcast and A Q E for shuffle, Photon eligibility for C P U, sizing and partitioning for idle. One change at a time, re-measure. [PAUSE 2s] Question fourteen. How does serverless cost governance work? [PAUSE 6s] Strong answer: budget policies and tags — every serverless workload carries attribution tags, budget policies bind spend to teams and projects, and everything lands in the system billing usage table as queryable Delta. Cost reports become scheduled queries; anomaly alerts become thresholds on the same table. Consumption tracking replaces capacity planning. [PAUSE 2s] Question fifteen. Last one. Delta or Iceberg — and how do you answer the lock-in worry? [PAUSE 6s] Strong answer: both, one vault. Same parquet underneath; UniForm maintains Iceberg metadata over a Delta table for external readers; managed Iceberg tables are native Unity Catalog citizens with automated maintenance; and the Iceberg REST catalog A P I plus federation opens the catalog to outside engines with credential vending. The format war ended in interoperability — differentiation moved up the stack to governance and automation. And for the operational gap, Lakebase: serverless Postgres with branching and C D C sync into Delta, on the same governed platform. [PAUSE 2s] That's the track. Fifteen questions, the whole platform.
