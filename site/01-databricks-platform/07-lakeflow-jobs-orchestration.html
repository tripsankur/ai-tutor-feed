Track 1 · Databricks Platform & Data Engineering · Episode 7

Lakeflow Jobs & Orchestration Patterns

17 min listen · The orchestra mental model of Lakeflow Jobs — task DAGs, the five trigger types including table-update and file-arrival, repair runs, serverless compute choices, and when Airflow still earns its place.

Facts verified: 2026-07-17 (table-update triggers + dynamic refs, file-arrival triggers on UC locations/volumes, file events)

The mental model: the orchestra

Score = job definition (task DAG) · musicians = tasks · conductor = Jobs engine (cues, failure handling, recovery). Formerly "Workflows".

Task types (musicians)

Type Notes
Notebook / Python wheel / JAR Versioned wheels = CI/CD artifact slot
SQL task Runs on SQL warehouse
Pipeline task A whole Declarative Pipeline as one node
dbt task dbt project on warehouse compute (see T1E8)
Condition (if/else) Branch on params/results
For-each Fan out over list — metadata-driven table loops
Run-job Nest jobs — compose team scores into symphonies

Edges: depends_on + run-if (success/failure/always) — cleanup + alerting in-graph.

Triggers (the cues) — interview-current

Trigger Mechanism
Schedule Cron + timezone
Manual/API REST
Continuous Restart on finish
File arrival Watches UC external location/volume — data's arrival IS the cue
Table update Fires when upstream Delta tables get data; dynamic refs e.g. {{job.trigger.table_update.updated_tables}}

Enable file events on storage → cheap notifications (Event Grid/S3) instead of polling; also speeds Auto Loader. Killer line: "Wire medallion layers with table-update triggers — orchestration follows data readiness, not wall-clock optimism."

Compute per task

Serverless (spiky/short, zero sizing) · job clusters (heavy sustained, instance control) · shared job cluster (reuse across tasks in run) · SQL warehouse (SQL/dbt). Never all-purpose clusters in scheduled jobs.

Failure handling

  • Per-task retries (+ intervals) — safe only on idempotent tasks (merge-writes, deterministic outputs)
  • Task/job timeouts, queueing, max-concurrent-runs (queue/skip/parallel)
  • Notifications: start/success/failure → email/webhook/Slack/Teams
  • Repair runs — rerun only failed task + downstream, same run ID/params, audit intact

Parameters: job params → tasks; dynamic value refs (run ID, trigger time, updated tables); task values pass results between tasks (≈ Airflow XCom).

Jobs vs Airflow (own this comparison)

Lakeflow Jobs Airflow
Infra Zero (no scheduler/metadata DB/executor ops) You run it (or pay managed)
Data-driven triggers Native table-update/file-arrival Sensors that poll (and cost while waiting)
Recovery Repair runs Clear + rerun subtleties
Cross-platform Weak — Databricks-centric The neutral conductor
Ecosystem Task types Massive operator library

Verdict: Databricks-internal DAGs → Jobs; cross-platform enterprise flows → Airflow calling Jobs via API as single tasks. "Two conductors, clear jurisdictions."

Pitfalls

  1. Cron optimism → replace with table-update triggers.
  2. All-purpose cluster in scheduled job → interactive prices for batch.
  3. Retry on non-idempotent task → double writes. Idempotency is designed, not checked.
  4. One giant 100-task job → compose with run-job; team-sized, independently repairable.

Interview Q&A

Q1. Productionise a medallion platform's orchestration. Pipelines for transforms; Jobs per domain composed via run-job; bronze on file-arrival, silver/gold on table-update triggers; serverless/job clusters; retries on idempotent tasks + timeouts + alerts; repair runs for recovery; for-each + params for metadata fan-out.

Q2. Table-update trigger vs scheduling downstream later? Trigger fires on actual upstream commit — kills before-upstream-finished races; dynamic ref hands the changed-tables list to the run. Schedule = hope; trigger = causality.

Q3. When Airflow over Jobs? DAG spans platforms (on-prem, vendor APIs, non-Databricks); org standard already Airflow. Keep Databricks work as Jobs invoked by Airflow via API.

Q4. What makes retries safe? Idempotent tasks: MERGE-based writes, deterministic outputs, checkpointed streams. Retry a blind INSERT = duplicates.

Q5. Repair run vs full rerun? Repair reruns failed task + downstream only, same run ID and params — surgical, auditable, saves the 5-hour replay.
