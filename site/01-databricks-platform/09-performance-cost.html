Track 1 · Databricks Platform & Data Engineering · Episode 9

Performance & Cost: Photon, AQE, Caching, Liquid Clustering, Serverless Economics

18 min listen · The tuning-garage mental model of Databricks performance — two gauges on every job, the five tuning stations from engine to layout, and the FinOps discipline that turns speed work into money saved.

Facts verified: 2026-07-19 (serverless budget policies + tags, system.billing.usage, Photon default on SQL warehouses, AQE's four mechanisms)

The mental model: the tuning garage

Workload on the lift, two gauges on the wall — speed (wall-clock) and money (DBUs + cloud) — every knob moves both. Performance IS cost (per-second billing). Five stations: engine, gearbox, fuel, chassis, rental desk.

The five stations

Station Tech Mechanics Cost lens
Engine Photon C++ vectorised under unchanged Spark APIs; 2–4× CPU-bound; default on SQL warehouses Premium DBU — pays ONLY when CPU-bound; wasted on IO-bound/UDF-heavy
Gearbox AQE Re-plans at shuffle boundaries with observed sizes: ① sort-merge→broadcast demotion ② shuffle-partition coalescing ③ skew splitting ④ empty-relation short-circuit On by default — delete ancient hand-tuned shuffle configs
Fuel 3 caches Disk cache (worker-local SSD copies, automatic) · Spark cache (manual .cache(), overused — measure, unpersist) · Result cache (warehouses: identical query + unchanged data = free; shared on serverless) Know WHICH cache saved you
Chassis Layout Liquid clustering + data skipping ("fastest read = file never opened"); predictive optimization runs paid maintenance Explainable background spend
Rental desk Serverless Per-second, warm pools, zero idle, zero knobs Budget policies + tags → system.billing.usage (queryable Delta): reports = scheduled queries, alerts = thresholds

The diagnostic loop (say this in interviews)

  1. Read both gauges — slow, expensive, or both? (fast+expensive = sizing/idle; slow+cheap = parallelism)
  2. Query profile — where did time ACTUALLY go
  3. Classify bottleneck → station:
  4. Reading too much → chassis (clustering, skipping, file sizes)
  5. Shuffling too much → gearbox (broadcast, skew, AQE)
  6. CPU pegged → engine (Photon eligibility, UDFs poisoning vectorisation)
  7. Workers idle → sizing/driver (partition count, driver-side loops)
  8. Fix ONE thing, re-measure, repeat.

Pitfalls

  1. Premium-everything cluster — Photon + big instances on an IO-bound job: both needles bad. Classify first.
  2. Cache cargo-culting — .cache() everywhere → memory pressure → shuffle spills → slower than uncached.
  3. Invisible background bill — automations on, nobody owns attribution. Tag everything, budget-police serverless, monthly system.billing.usage review.

Interview Q&A

Q1. Critical pipeline slow and expensive — approach? Two-gauge frame → profile → classify (IO/shuffle/CPU/idle) → matched fix, one change at a time → close with governance (tags, budget policies, system tables). End with a real number if you have one.

Q2. What does AQE actually do? Runtime re-planning at shuffle boundaries using observed sizes: broadcast demotion, partition coalescing, skew splitting, empty-relation pruning. "The gearbox shifts mid-race based on the road, not the map."

Q3. Which cache saved my dashboard? Second refresh same user cluster = disk cache (IO saved). Identical query on warehouse = result cache (all compute saved). .cache() only helps re-reads within a job — and hurts if memory-starved.

Q4. Serverless vs classic clusters for cost? Serverless: zero idle, per-second, no ops, governed by budget policies/tags — spiky + short workloads. Classic job clusters: instance control for heavy sustained crunching. Never all-purpose in production schedules.

Q5. Where do you SEE the money? system.billing.usage — DBU consumption at resource level with tags; account console cost dashboards on top. Governance you can query is governance you can automate.
