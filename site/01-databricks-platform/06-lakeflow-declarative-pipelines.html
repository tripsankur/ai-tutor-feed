Track 1 · Databricks Platform & Data Engineering · Episode 6

Lakeflow Declarative Pipelines (ex-DLT): Streaming Tables, Materialized Views, Expectations

18 min listen · The blueprint-factory mental model of Lakeflow Declarative Pipelines — the DLT rename, streaming tables and flows, materialized views, AUTO CDC for SCD, expectations as quality gates, and the serverless 2026 upgrades.

Facts verified: 2026-07-17 (rename + open-sourcing; UC-stored expectations; serverless standalone MV/ST beta; REPLACE WHERE; CPU vertical autoscaling; AUTO CDC SQL-editor skill)

Naming

DLT → Lakeflow Declarative Pipelines (aka Spark Declarative Pipelines — open-sourced into Apache Spark) at DAIS 2025. Old code runs unchanged; Python: import dlt → from pyspark import pipelines as dp. "The declarative model won — it's a Spark standard now."

The mental model: two factories

Imperative (notebooks+jobs): you're the foreman — orchestration, checkpoints, retries, backfills = your code, your defects. Declarative: pin blueprints ("this table is defined as this transformation"); engine derives DAG, ordering, checkpointing, retries, incremental maintenance.

Core objects

Object What Use for
Streaming table UC managed table that is a streaming target; ≥1 flows (append / AUTO CDC) write into it; exactly-once Accumulate: bronze ingestion, events, CDC targets
Materialized view Engine-maintained computed result; engine picks incremental vs full recompute Derive: transforms, aggregates, gold
View Intermediate, not persisted Staging logic
Sink Write out to Kafka/external Egress

Rule: streaming tables accumulate, materialized views derive.

from pyspark import pipelines as dp

@dp.table                      # streaming table
def bronze_orders():
    return spark.readStream.format("cloudFiles")...

@dp.materialized_view          # derived, engine-maintained
def gold_revenue_by_region():
    return spark.read.table("silver_orders").groupBy("region").agg(...)

AUTO CDC (ex-APPLY CHANGES)

Change stream → correct table, declaratively: key + SEQUENCE BY (resolves out-of-order) + SCD type 1 (current state) or type 2 (full history, validity windows). Replaces hand-written merge choreography. SQL-editor AUTO CDC skill writes boilerplate. Interview phrase: "SCD2 as a declared property, not a hand-written merge."

Expectations (quality gates)

Boolean constraint per dataset; modes: warn (count) / drop (divert+count) / fail (stop update). Violations → event log (queryable Delta) → quality dashboards. 2026: expectations storable in Unity Catalog tables — versioned, shared, governed rules. Echo of ABAC: quality-as-declaration.

Ops & 2026 features

  • Triggered (batch economics, default) vs continuous (real latency, always-on cost)
  • Development vs production mode; serverless default
  • 2026: CPU-based vertical autoscaling; standalone MV/ST on serverless (Beta) — one table without a pipeline; REPLACE WHERE flows (Beta) — surgical incremental rebuilds
  • Lakeflow Designer — no-code canvas compiling to declarative pipelines
  • Medallion fit: bronze ST (Auto Loader/Connect) → silver AUTO CDC + expectations → gold MVs

Pitfalls

  1. Full-recompute surprise — some ops non-incrementalizable; check event log for chosen strategy.
  2. STs need append-only sources — updated/deleted source rows break flows; use CDF, skipChangeCommits, or fix source.
  3. Silent drops — drop-mode without alerts = months of quiet data loss. Alert on violation counts.
  4. Continuous-mode bills — most "NRT" SLAs fine with 10-min triggered runs.

Interview Q&A

Q1. DLT/Declarative Pipelines vs notebooks+jobs — when, why? Declarative inverts ownership: I declare datasets; engine owns orchestration/checkpoints/retries/incremental maintenance — removes highest-defect-rate boilerplate. Jobs still orchestrate the pipelines + non-pipeline tasks (next episode).

Q2. Streaming table vs materialized view? ST = streaming target, accumulates exactly-once, multiple flows allowed. MV = derived result, engine-maintained, incremental when possible. Accumulate vs derive.

Q3. How do you get SCD Type 2 declaratively? AUTO CDC flow: key, SEQUENCE BY event timestamp, STORED AS SCD TYPE 2 → validity-window history, out-of-order handled by sequence column.

Q4. How is data quality enforced and observed? Expectations warn/drop/fail; counts in event log; dashboards + alerts on drops; rules centralizable in UC (2026) instead of copy-paste.

Q5. How does a custom metadata-driven pipeline framework compare to this? Same philosophy, pre-productised: a homegrown framework generates pipeline configs from metadata, where Lakeflow Declarative Pipelines does the same thing natively, with the engine owning orchestration instead of hand-rolled code.
