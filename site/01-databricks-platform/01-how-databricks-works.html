Track 1 · Databricks Platform & Data Engineering · Episode 1

How Databricks Actually Works: Control Plane, Compute Plane, Clusters, Photon, Serverless

19 min listen · The two-buildings mental model of Databricks architecture — where your code runs, where your data lives, what Photon does, how serverless changes the picture, and how to narrate it all in an interview.

Facts verified: 2026-07-17

The mental model: two buildings

Left building = Databricks (control plane). Web app, notebooks UI, job scheduler, cluster manager, Unity Catalog metastore. Metadata + orchestration only — never your data. Right building = your cloud account (compute/data plane). Storage (ADLS) in the vault, cluster VMs on the floors. Connections initiate outbound from your side — key security fact.

Photon depth (interview fishing spot)

  • Why: analytics bottleneck moved from IO to CPU (JVM row-wise interpretation, boxing, GC).
  • What: from-scratch C++ engine, columnar/vectorised batches, SIMD-friendly loops.
  • How it slots in: query plan segments Photon supports run native; rest falls back to classic Spark seamlessly. APIs unchanged.
  • When NOT worth it: IO-bound scans, heavy UDF workloads (UDFs mostly don't photonise) — premium DBU wasted.

Classic fires (war stories)

  1. Immortal all-purpose cluster — no auto-terminate + forgotten dashboard = five-figure bill. Fix: auto-terminate, job clusters, policies, serverless for spiky.
  2. Driver bottleneck — collect() or driver-side Python loops while workers idle. First question on a slow job: is work distributed?
  3. Small files — micro-batch writes → millions of tiny files → file-open overhead dominates. Modern fix: predictive optimisation (auto compaction on managed tables) + liquid clustering (see Delta episode).

Interview Q&A

Q1. Walk me through Databricks architecture. Two planes. Control plane (Databricks account): UI, scheduler, cluster manager, UC metastore — metadata/orchestration only. Compute plane (my account): storage + cluster VMs; connections initiated outbound from my side; instructions go one way, results the other; raw data never crosses. Serverless variant: compute in Databricks-operated pools, storage access still mine, governed by UC with short-lived scoped credentials.

Q2. What is Photon and when would you not enable it? C++ vectorised engine under unchanged Spark APIs; 2–4× on CPU-bound queries; falls back seamlessly for unsupported operators. Skip when IO-bound or UDF-heavy — higher DBU rate with no gain.

Q3. How does Databricks keep customer data secure if the UI is SaaS? Data + classic compute stay in customer subscription; control plane holds metadata; outbound-initiated connections; UC centralises grants/lineage/audit; serverless uses scoped credentials rather than standing access.

Q4. Job cluster vs all-purpose vs serverless — production ETL? Job cluster (or serverless jobs): created per run, dies after, cheapest + isolated. All-purpose is for humans. Serverless when spiky/latency-sensitive or to remove ops burden.

Q5. What's Lakebase and why does it matter? GA serverless Postgres on object storage — operational/OLTP workloads on the same governed platform, with branching and CDC sync into Delta. Kills the separate-OLTP-silo + fragile-pipeline pattern for lakehouse apps.
