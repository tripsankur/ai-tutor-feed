Track 1 · Databricks Platform & Data Engineering · Episode 4

Unity Catalog Deep Dive: Metastore, Securables, Managed vs External, Lineage, Metrics

18 min listen · The governed-city mental model of Unity Catalog — metastore as the city map, three-level namespace addresses, credential gates to storage, inherited grants, the new ABAC policy regime with governed tags, lineage as CCTV, and the metrics semantic layer.

Facts verified: 2026-07-17 (ABAC + governed tags + agentic classification GA May 2026; external lineage GA; UC Metrics; managed Iceberg GA)

The mental model: a governed city

Metastore = council office (one map per region, all workspaces attached). Address = catalog.schema.object (suburb → street → house). Council holds gate keys (storage credentials); zoning stickers (governed tags) trigger laws (ABAC policies); CCTV (lineage) records itself.

flowchart TB
    MS["Metastore (1/region, account-level)"]
    MS --> C1["Catalog (domain)"]
    C1 --> S1["Schema (team/layer)"]
    S1 --> T[Tables/Views]
    S1 --> V[Volumes]
    S1 --> F["Functions (agent tools)"]
    S1 --> M[Models]
    S1 --> VS[Vector indexes]
    MS --> SC["Storage credentials\n(Azure: access connector · AWS: IAM role + ext ID)"]
    SC --> EL["External locations (governed paths)"]
    MS --> GT["Governed tags"] --> POL["ABAC policies\n(row filters + column masks at catalog/schema level)"]

Why UC exists (the before/after)

Before: Hive metastore per workspace, permissions in workspace ACLs, storage keys in mount points, no lineage — N workspaces = N disagreeing registries. After: one account-level metastore, one governance model, every asset type (tables, volumes, functions, models, indexes, shares) under one grant + audit system.

Key facts

Topic Detail Interview line
Managed vs external tables Managed: UC controls location + lifecycle; predictive optimization + managed Iceberg (GA) work here "Managed by default — that's where the automation lives; external only for migration/interop"
Storage credentials Access connector (Azure) / IAM role + external ID (AWS) "No keys in code, ever — gates are auditable and revocable"
Grants Hierarchical inheritance; USE CATALOG + USE SCHEMA + SELECT = read path Groups not users; service-principal ownership
ABAC (GA 5/2026) Row-filter + column-mask policies attached at catalog/schema, conditioned on governed tags; auto-applies to current + future objects; 10k policies/metastore "Laws on zoning stickers, not house addresses"
Governed tags Account-level key-value pairs on catalogs→columns, models, volumes Taxonomy is account-defined, not free-text chaos
Agentic data classification (GA) Auto-scans + tags PII per GDPR/HIPAA/PCI/etc. Chain: classify → tag → protect
Lineage Automatic table+column level from query execution; external lineage GA (register non-Databricks up/downstream) "Nobody documents it; the engine records it"
System tables Audit, billing, lineage, access as queryable Delta tables "Access review = scheduled query, not spreadsheet safari"
UC Metrics KPIs as governed objects (measure+dimensions), consumed by SQL/BI/agents; open-sourced "Genie computes THE churn, not A churn"
Delta Sharing Open protocol, share without copying, any consumer Foundation for clean rooms

Pitfalls

  1. Metastore geography — 1/region; plan before workspace sprawl; consolidation later = surgery.
  2. Inheritance generosity — catalog-level write grants flow into every future object. Read broad+high, write tight+low.
  3. External location sprawl — centralise creation rights; audit via system tables.
  4. Tags without policies — classification theatre. A tag matters only when a policy references it.

Interview Q&A

Q1. Design governance for a multi-team lakehouse. One metastore/region → domain catalogs, team/layer schemas → storage only via credentials+external locations → managed tables default → group grants for coarse access + ABAC (classify→tag→protect) for fine → lineage + external lineage + system-table audits → UC Metrics for shared semantics. Close with production proof: name real scale, row/column-level security in use, and automated retention/purging. [Swap in your own numbers — record counts, RLS/CLM examples, purge automation — to make this concrete.]

Q2. ABAC vs classic row filters/column masks? Classic: per-table functions — sprawl, gaps on new tables. ABAC: policy written once at catalog/schema level, triggered by governed tags, auto-covers future objects; classification agent applies tags. Migration path: keep table-level filters where bespoke, ABAC for estate-wide rules.

Q3. How does UC secure storage access on each cloud? Storage credential wraps access connector managed identity (Azure) or IAM role with external ID (AWS); external locations bind paths to credentials; grants on the UC object, not the storage. CloudTrail/Azure logs + UC audit both see access.

Q4. Managed vs external — why has the default flipped to managed? Predictive optimization (auto OPTIMIZE/VACUUM/stats), managed Iceberg with lifecycle handled, no path management. External keeps: existing lake layouts, non-Databricks writers, migration staging.

Q5. How do you prove compliance (who accessed PII last quarter)? System tables: join audit log with lineage and tag inventory — a SQL query, schedulable, alertable. External lineage extends the graph to source systems and BI reports.
