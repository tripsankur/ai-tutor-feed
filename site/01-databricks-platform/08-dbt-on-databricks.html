Track 1 · Databricks Platform & Data Engineering · Episode 8

dbt on Databricks: Where It Fits vs Declarative Pipelines

17 min listen · The tailor-shop mental model of dbt — how SELECT-plus-ref compiles into a tested, documented DAG on a SQL warehouse, the 2026 Fusion engine and Fivetran merger, and the honest dbt-versus-Declarative-Pipelines decision an interviewer wants to hear.

Facts verified: 2026-07-17 (Fivetran + dbt Labs merger completed 2026-06-01; dbt Core v2.0 Fusion engine, Apache 2.0; state-aware orchestration cost claims from Coalesce 2025)

The mental model: tailor shop above the warehouse

dbt does no compute — it compiles patterns (models) and sends DDL downstairs. A model = a SQL SELECT in a file. dbt wraps it in CREATE TABLE/VIEW ceremony and runs it on a Databricks SQL warehouse via dbt-databricks adapter; results = UC-governed tables/views.

Core machinery

Concept What Key point
ref('model') Reference other models Builds DAG automatically + free environments (dev schema vs prod catalog per target)
Sources Declared raw tables (bronze) Graph entry points + freshness checks
Materializations view / table / incremental / ephemeral Incremental: dbt generates merge logic from config (unique_key)
Snapshots Hand-rolled SCD2 by diffing query results vs AUTO CDC (SCD2 from change stream) — same goal, different mechanism/freshness
Tests YAML: unique, not_null, relationships, custom SQL Compile to must-return-zero-rows queries; run per build
Docs Generated site: lineage graph + column docs from YAML
Workflow Everything in git, PRs, CI The actual revolution dbt sold 
-- models/marts/fct_revenue.sql — this IS a dbt model
select region, sum(amount) as revenue
from {{ ref('stg_orders') }}
group by region

2026 headlines

  1. Fusion engine (dbt Core v2.0, Rust, Apache 2.0): real SQL parsing (not Jinja-holes-in-text) → state-aware orchestration — skips models whose inputs didn't change. Claimed 60–65% warehouse cost cut on large projects. Same convergence as MV incremental maintenance: "only compute what changed."
  2. Fivetran + dbt Labs merger completed 2026-06-01 — neutral EL+T stack consolidating against platform bundles (Lakeflow/Snowflake/Fabric full-stacks). dbt = the lock-in hedge.

dbt vs Lakeflow Declarative Pipelines (both declarative SQL DAGs)

Dimension dbt Declarative Pipelines
Workload Batch SQL only Streaming + batch, AUTO CDC, continuous
Persona Analytics engineers (SQL-first, marts) Data engineers (Python+SQL, pipelines)
Ecosystem Packages, community, portability across warehouses Platform-native: serverless autoscaling, engine-chosen incremental, expectations→event log/UC
Ops on Databricks dbt task in Lakeflow Jobs, warehouse compute, UC governance Pipeline task, same orchestra

Decision rule: streaming/CDC → pipelines, no contest. Existing dbt estate/analytics team → keep dbt as Jobs task. Greenfield batch marts → either, pick by team identity. Common enterprise split: pipelines own bronze+silver (streaming/CDC), dbt owns gold marts — handoff at silver.

Pitfalls

  1. Incremental drift — wrong unique_key/late data → diverges from full rebuild. Periodic full-refresh sanity runs; Fusion state-awareness helps.
  2. Thousand-model sprawl — models are cheap; enforce naming/folders, prune dead patterns.
  3. Tests as decoration — test business invariants (join keys, money columns), fail builds; else the green badge is theatre.

Interview Q&A

Q1. How does dbt fit on Databricks? Models are SELECTs, ref builds the DAG, compiled onto a SQL warehouse — declarative transformation, same philosophy as Lakeflow Declarative Pipelines. Operationally: dbt task in Lakeflow Jobs, UC governance end to end, no exceptions to the platform's governance model. Streaming → pipelines; analyst marts → dbt; handoff at silver. [If you're light on hands-on dbt experience, lead with the architecture fit, then say what you'd ramp on.]

Q2. What is the Fusion engine? Rust rewrite of dbt's compiler/runtime (dbt Core v2.0, open source): parses SQL properly → state-aware orchestration skipping unchanged models; big warehouse-cost claims. Industry converging on incremental-everything.

Q3. dbt snapshots vs AUTO CDC SCD2? Snapshots: periodic query-diff — freshness bound by snapshot cadence, works without change feed. AUTO CDC: from actual change stream, sequence-resolved, continuous. Prefer AUTO CDC when CDC exists; snapshots for sources without it.

Q4. Why dbt at all when pipelines exist? Team fit (analytics engineers), existing estate, package ecosystem, portability/lock-in hedge (sharpened by Fivetran merger). Not a technical knockout either way — it's a people-and-strategy call.

Q5. What breaks in badly-run dbt projects? Incremental drift, model sprawl, decorative tests — all governance-of-the-repo problems, fixed with conventions, full-refresh audits, invariant tests in CI.
