Track 1 · Databricks Platform & Data Engineering · Episode 10

Open Lakehouse: Iceberg Support, UniForm, Lakebase (Serverless Postgres)

17 min listen · The bilingual-vault mental model of the open lakehouse — why two table formats exist, how UniForm and managed Iceberg dissolve the format war, catalog federation via the Iceberg REST API, and Lakebase bolting a real OLTP database onto the same governed platform.

Facts verified: 2026-07-19 (managed Iceberg GA, full Iceberg support incl. REST catalog, Lakebase GA w/ branching + Lakehouse sync, UniForm async read-only)

The mental model: one vault, two ledgers

Same parquet in the cabinets; Delta ledger (numbered log + checkpoints) and Iceberg ledger (snapshot → manifest-list → manifest tree) mounted at the door. The format war was about READING, not storing.

flowchart LR
    P[(Parquet files\none copy)]
    DL["Delta log"] --> P
    IB["Iceberg metadata"] --> P
    SPARK[Spark/Databricks] --> DL
    SNOW[Snowflake/Trino/Flink] --> IB
    UC["Unity Catalog\n(Iceberg REST catalog API + credential vending)"] --- DL
    UC --- IB

Three mechanisms (escalating commitment)

Mechanism What Caveats
UniForm Delta table maintains BOTH ledgers — Iceberg metadata generated async over same files; external engines read it as normal Iceberg Iceberg side read-only; async lag (no read-after-write for external readers)
Managed Iceberg (GA) Native, writable Iceberg tables as UC managed tables — snapshot expiry + compaction automated First-class citizen: same grants, lineage, predictive optimization
Iceberg REST catalog API + federation UC speaks the standard Iceberg catalog protocol (external engines connect + credential vending); UC also federates Glue/Hive catalogs inward City gates open both directions

Strategic reframe (say in interviews): "The format war ended in interoperability — parquet either way, dual-readable metadata, open catalog protocol. Differentiation moved up the stack: governance + automation." (Same consolidation pattern as dbt/Fivetran vs platform bundles.)

Lakebase (the OLTP gap)

Serverless Postgres (real, wire-compatible) on separated compute/storage, GA, millions of launches/day.

Feature Why it matters
Branching Copy-on-write fork of a live operational DB — test migrations/agent experiments disposably ("branch production" — impossible in classic OLTP)
Lakehouse sync Continuous CDC replication Lakebase ⇄ UC Delta tables — the hand-built operational→analytical pipeline as a platform feature
Same governance Corner store + warehouse, one landlord, one key system

Pitfalls / honest edges

  1. UniForm lag — async metadata: external read-after-write freshness needs native Iceberg or direct integration.
  2. Feature asymmetry — newest Delta features (DVs, clustering behaviours) lack same-day Iceberg equivalents; protocol-version interop check now spans TWO ecosystems.
  3. Lakebase maturity — adopt new lakehouse-native apps + agent state first; core banking ledgers last. Enthusiasm with rollout discipline.

Interview Q&A

Q1. Delta or Iceberg? Both, one vault: UniForm for Delta-write/Iceberg-read, managed Iceberg for Iceberg-native teams, REST catalog + federation for outside engines — all under one UC governance spine. Format no longer locks you in; governance/automation differentiate.

Q2. How does UniForm work and when is it wrong? Each Delta commit asynchronously generates equivalent Iceberg metadata over the SAME parquet — no copy, one table, two descriptions. Wrong when external readers need read-after-write freshness or write access.

Q3. How does Snowflake read a Unity Catalog table? Via UC's Iceberg REST catalog endpoint: discovers the table, gets short-lived storage credentials (credential vending), reads Iceberg metadata + parquet directly.

Q4. What is Lakebase and why did a lakehouse vendor build it? Serverless Postgres closing the OLTP gap — apps need ms row transactions the lakehouse can't serve; classic answer was a separate DB + fragile sync. Lakebase: same platform, branching, CDC sync into Delta.

Q5. Your Iceberg migration stance for a Delta estate? Don't migrate for fashion: enable UniForm where Iceberg readers exist, create managed Iceberg for new Iceberg-native workloads, keep Delta where the automation pays. Formats coexist under one catalog.
