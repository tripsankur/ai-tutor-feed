Track 6 · LangChain / LangGraph · Episode 2

LangGraph: State Machines, Nodes, Edges, Checkpoints

16 min listen · LangGraph opened up as a board game: a shared scoreboard of state with per-column merge rules, squares that do the work, arrows that route, ticks that run in lockstep, and a camera that photographs every tick into a per-thread filing cabinet — which is what makes agents durable, resumable, and debuggable.

Facts verified: 2026-09-25 (langgraph 1.2.12 on PyPI; docs source langchain-ai/docs @ 2026-09-24)

One-sentence thesis

LangGraph is a durable runtime for state machines: nodes return partial updates merged into shared state by per-key reducers, execution advances in Pregel-style super-steps, and a checkpointer snapshots the whole state at every super-step per thread — which is what gives you memory, crash recovery, time travel and human-in-the-loop.

Code

import operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import Command, Send, RetryPolicy
from langgraph.checkpoint.postgres import PostgresSaver

class State(TypedDict):
    messages: Annotated[list, add_messages]        # append / update-by-id
    summaries: Annotated[list[str], operator.add]  # append (safe for parallel writes)
    draft: str                                     # default reducer: replace

def model_node(state: State):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

def route(state: State) -> Literal["tools", "__end__"]:
    return "tools" if state["messages"][-1].tool_calls else END

def review(state: State) -> Command[Literal["model", "__end__"]]:
    ok = len(state["draft"]) > 0
    return Command(update={"draft": state["draft"].strip()}, goto=END if ok else "model")

def fan_out(state: State):
    return [Send("summarize", {"doc": d}) for d in state["docs"]]   # map-reduce

builder = StateGraph(State)
builder.add_node("model", model_node, retry_policy=RetryPolicy(max_attempts=3))
builder.add_node("tools", tool_node)
builder.add_edge(START, "model")
builder.add_conditional_edges("model", route)
builder.add_edge("tools", "model")

with PostgresSaver.from_conn_string(DB_URI) as saver:
    saver.setup()
    graph = builder.compile(checkpointer=saver)
    cfg = {"configurable": {"thread_id": "user-42:conv-9f1c"}, "recursion_limit": 50}
    graph.invoke({"messages": [("user", "hi")]}, cfg, durability="sync")
    snap = graph.get_state(cfg)                       # latest StateSnapshot
    history = list(graph.get_state_history(cfg))      # newest first
    graph.update_state(cfg, {"draft": "edited"})      # creates a NEW checkpoint (fork)

Tradeoffs to volunteer

  1. InMemorySaver is not production — multi-replica or restart = lost threads. Use Postgres (or MongoDB).
  2. thread_id is the only key — opaque, per-conversation, scoped to the authenticated user; Postgres saver column limit 255 chars.
  3. Checkpoint growth — full state per super-step; prune, keep large blobs out of state (store references), consider DeltaChannel (beta).
  4. Nodes re-run from the top on resume/retry — side effects must be idempotent or isolated after the decision point.
  5. Parallel writes to a replace key error out — declare reducers upfront.
  6. Durability mode — async default can lose the last checkpoint on a crash; sync if every step must be durable.

5 interview questions

Q1. Why LangGraph instead of a while loop around the model? The loop keeps state in memory; crashes, deploys or human pauses lose it. LangGraph checkpoints full state every super-step into a persistent store keyed by thread, giving durable execution, memory, long human pauses, and time travel; reducers make parallel branches safe; the graph is inspectable.

Q2. Explain LangGraph's execution model. Pregel-style super-steps: active nodes run in parallel, return partial updates, updates are merged via per-key reducers, edges determine next active nodes, checkpoint written at the boundary; ends when no nodes active or at recursion_limit.

Q3. What's a reducer, and when do you need a custom one? A function (existing, update) -> new per state key. Default replaces. You need an append/merge reducer when multiple nodes (especially parallel branches or Send fan-outs) write the same key, and add_messages for chat history so edits by ID update in place.

Q4. Conditional edge vs Command vs Send? Conditional edge: route only, based on state. Command: a node both updates state and routes (and can jump to a parent graph). Send: dynamic fan-out of the same node with different per-item inputs for map-reduce.

Q5. What do you check before production? Persistent checkpointer (Postgres), opaque user-scoped thread IDs, deliberate durability mode, idempotent side effects, reducers on shared keys, checkpoint retention, explicit recursion limits, per-node RetryPolicy and (1.2+) timeouts / error handlers.
