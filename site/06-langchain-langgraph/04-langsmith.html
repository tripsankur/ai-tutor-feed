Track 6 · LangChain / LangGraph · Episode 4

LangSmith: Tracing, Datasets, Evals

18 min listen · How LangSmith turns a non-deterministic agent into something you can observe and test: runs and traces captured from the live river of traffic, failures scooped into versioned datasets, and experiments scored by code, L L M judges, and humans before and after every release.

Facts verified: 2026-09-25

One-sentence thesis

LangSmith closes the loop between production and testing: it records every agent execution as a trace, lets you harvest real failures into versioned datasets, and scores every candidate version against them (offline) and against live traffic (online) — and it works with or without LangChain.

The mental image: the river and the bank

  • River (left → right) = production traffic, one drop per request.
  • Bridge of cameras above the river = tracing (runs → traces → projects; threads for multi-turn).
  • Shelf of labelled jars on the near bank = datasets (examples with inputs + reference outputs, versioned).
  • Test bench downstream on the right, with judges = experiments + evaluators (code, LLM-as-judge, human, pairwise).
  • Buoys in the water = online evaluators on sampled live traces (no reference outputs).
  • The loop: bad drop → scooped into a jar / annotation queue → becomes a regression test on the bench → only then does the next version enter the river.

Concept Meaning

Project Container for all traces of one app/environment (keep dev and prod separate).

Code snippets

Auto-tracing for LangChain / LangGraph (no code change):

export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=...
export LANGSMITH_PROJECT=support-agent-dev

Tracing plain Python (no LangChain):

from langsmith import traceable
from langsmith.wrappers import wrap_openai
import openai

client = wrap_openai(openai.OpenAI())

@traceable(run_type="chain", metadata={"prompt_version": "v7"})
def answer(question: str) -> str:
    resp = client.chat.completions.create(
        model="gpt-4.1-mini",
        messages=[{"role": "user", "content": question}],
    )
    return resp.choices[0].message.content

Offline experiment with a code evaluator and an LLM judge (openevals):

from langsmith import Client
from openevals.llm import create_llm_as_judge
from openevals.prompts import CORRECTNESS_PROMPT

client = Client()

def target(inputs: dict) -> dict:
    return {"answer": answer(inputs["question"])}

def has_disclaimer(outputs: dict) -> bool:          # deterministic check
    return "not financial advice" in outputs["answer"].lower()

correctness = create_llm_as_judge(
    prompt=CORRECTNESS_PROMPT, model="openai:o3-mini", feedback_key="correctness"
)

def correctness_eval(inputs, outputs, reference_outputs):
    return correctness(inputs=inputs, outputs=outputs,
                       reference_outputs=reference_outputs)

client.evaluate(
    target,
    data="support-golden-set",
    evaluators=[has_disclaimer, correctness_eval],
    experiment_prefix="prompt-v8",
    num_repetitions=3,          # non-determinism: look at variance
)

Evaluator types

Type How it scores Use for Watch out
Code / heuristic Deterministic function Schema validity, required phrases, exact match, tool-call counts Can't judge meaning
LLM-as-judge Model grades vs rubric (openevals / agentevals) Correctness, groundedness, tone, trajectory quality Costs per example; drifts; shared blind spots with same model family
Human (annotation queue) Experts score with rubric; pairwise queues pick A vs B Ground truth, judge calibration Slow, expensive — sample
Pairwise Compare two experiments per example Subjective tasks (summaries, tone) Needs two runs on same dataset version
Summary Aggregate over whole experiment Precision/recall, pass rate Hides row-level regressions if used alone

Offline vs online: offline = dataset examples with reference outputs (pre-deploy, regression, backtesting). Online = live traces/threads, no references (groundedness, frustration, loops, PII), configured as rules with filter + sampling rate + action (run evaluator, add to dataset, send to annotation queue). Multi-turn online evals score whole threads; Insights Agent clusters traces into usage patterns and failure modes.

Tradeoffs to volunteer

  1. Cost is per trace (Sep 2026 public pricing, order of magnitude): free Developer tier ≈ 1 seat + 5k traces/month; Plus ≈ $39/seat/month; base traces ≈ $2.50 per 1k (14-day retention), extended ≈ $5.00 per 1k (400-day retention). Any trace that receives feedback is auto-upgraded to extended — running an online evaluator on 100% of traffic can silently upgrade everything. Evaluator and playground runs count as traces. Sample production; keep all errors/flagged.
  2. Privacy: traces hold raw prompts/outputs → mask inputs/outputs client-side, pick region, self-host (Enterprise) if required. Decide before enabling prod tracing.
  3. Serverless flush: tracing is async/batched; short-lived functions can exit before the queue flushes → silently missing traces. Flush explicitly.
  4. Judge calibration: periodically route judged samples to humans; if agreement falls (e.g. >20% disagreement), fix the rubric first.
  5. Lock-in / alternatives: Langfuse (open source, self-hostable; acquired by ClickHouse Jan 2026), Arize Phoenix (open source), Braintrust (evals), MLflow 3 (Databricks-native tracing + eval). LangSmith accepts OpenTelemetry ingestion, which eases portability.

Naming (Oct 2025): LangGraph Platform → LangSmith Deployment; LangGraph Studio → LangSmith Studio. LangSmith is now observability + evaluation + deployment.

5 interview questions

Q1. How do you evaluate an LLM agent end to end? Split offline and online. Offline: versioned dataset seeded by hand and grown from production failures; every candidate runs as an experiment scored by deterministic checks first, LLM judges for fuzzy criteria, human-calibrated samples; gate on no row-level regressions, with repetitions for variance. Online: sampled reference-free evaluators on live traces; low scores go to annotation queues and back into the dataset.

Q2. Quality dropped after a prompt change. How do you find out why? Traces carry prompt version/model/commit as metadata, so filter before vs after and compare the failure signal; open failing traces, walk the run tree to find the diverging node (retrieval, tool, model decision); compare the two experiments row by row; add the failure to the dataset.

Q3. Does LangSmith require LangChain? No. LangChain/LangGraph get automatic tracing via callbacks with env vars, but plain code uses @traceable or wrapped provider clients, and LangSmith ingests OpenTelemetry spans.

Q4. What are the risks of LLM-as-judge? Cost per example, non-determinism, rubric ambiguity, and shared blind spots when the judge and app are the same model family. Mitigate with deterministic checks where possible, pairwise instead of absolute scores for subjective tasks, and periodic human agreement checks via annotation queues.

Q5. What does production tracing cost and how do you control it? Priced per trace with retention tiers; feedback auto-upgrades traces to extended retention; evaluator runs count too. Control with sampling (keep 100% of errors/flagged), separate dev/prod projects, client-side masking for PII, and explicit flush in serverless.

Tracing is sent asynchronously in a background thread, batched, so it should not add meaningful latency to the request itself. But in short-lived environments — a serverless function that exits right after returning — the background queue can be killed before it flushes, and traces silently vanish. The fix is to flush explicitly before the function returns. Silent missing traces are worse than no tracing, because you trust the gaps. Fourth, judges drift. An L L M judge is an instrument that needs calibration. If the judge and the application come from the same model family, they can share a blind spot and the judge will reward it. The discipline is to periodically send a sample of judged examples to human reviewers in an annotation queue and measure agreement. If the humans and the judge disagree more than, say, one time in five, fix the rubric before you trust the dashboard. Fifth, lock-in. LangSmith is a commercial SaaS product. The traces are available through an A P I and exports, and OpenTelemetry ingestion helps, but your evaluators, datasets, and annotation workflows live in its model. Alternatives exist: Langfuse is open source and self-hostable, and was acquired by ClickHouse earlier this year; Arize Phoenix is open source; Braintrust focuses on evals; and if you are on Databricks, M L flow three covers tracing and evaluation natively. The honest framing is that LangSmith is the lowest-friction choice if you are already on LangGraph, and one of several reasonable choices if you are not. [PAUSE 2s] ## Interview angle Three questions come up constantly. When they ask, "How do you evaluate an agent?", a strong answer sounds like this: "I separate offline and online. Offline, I keep a versioned dataset of real examples, seeded by hand and grown from production failures, and every candidate runs as an experiment against it, scored by deterministic checks first, L L M judges for the fuzzy criteria, with a human-calibrated sample to keep the judges honest. I gate releases on no row-level regressions, not just the average. Online, I sample production traces with reference-free evaluators and route low scores into an annotation queue, which feeds the dataset. The loop is production to dataset to experiment to production." When they ask, "Your agent's quality dropped after a change. How do you debug it?", a strong answer: "Every trace carries the prompt version, model, and commit as metadata, so I filter before and after the change and compare the failure signal. Then I open individual traces, walk the run tree, and find the node where behavior diverged — retrieval, a tool call, or the model's decision. Then I turn that failure into a dataset example so it can never regress silently again." And when they ask, "What does tracing cost you?", say: "Real money at volume, priced per trace with a retention tier, plus privacy exposure. So I sample routine traffic, keep all errors and flagged traces, mask personal data at the client, and flush explicitly in serverless environments." [PAUSE 2s] ## Sixty-second recap Let's walk the river one last time. Production traffic flows left to right. Above it, the bridge of cameras — tracing. Every request becomes a trace: a tree of runs, one per model call, tool call, and node, with inputs, outputs, tokens, cost, and timing. Traces live in projects, conversations link into threads, metadata makes it searchable, feedback stamps a verdict on it. Below, the shelf of jars — datasets. Examples with inputs and reference outputs, seeded by hand, scooped from real failures, versioned so experiments stay comparable. Downstream on the right, the test bench — experiments. Every candidate runs every jar, scored by code checks, L L M judges, human annotation queues, and pairwise comparisons, and you read the row-by-row diff, not just the average. In the water, the buoys — online evaluators — scoring live traffic without an answer key, and routing the bad drops back onto the shelf. And the price tag: per trace, with feedback upgrading retention, so sample wisely and mask before you record.
