Track 6 · LangChain / LangGraph · Episode 1

LangChain Core: LCEL, Runnables, Chains vs Agents

18 min listen · The foundation of the LangChain stack in its version-one shape: one universal Runnable interface, the pipe that composes it into fixed chains, and the create-agent loop with middleware that replaced a decade's worth of legacy agent classes.

Facts verified: 2026-09-25 (langchain 1.4.2, langchain-core 1.6.5, langgraph 1.2.12 on PyPI)

One-sentence thesis

Modern LangChain (v1.x) is a small agent-building surface — create_agent + middleware — sitting on one universal Runnable interface; the chain-vs-agent decision is about who decides the control flow: you at design time (chain) or the model at run time (agent).

The mental image: the pipe wall

  • Standard fitting on every pipe section = the Runnable interface (invoke / batch / stream + async, shared RunnableConfig).
  • Left: straight pipe = a chain (LCEL RunnableSequence): tee (RunnableParallel: retriever + RunnablePassthrough) → prompt → model → parser.
  • Right: roundabout = an agent: model in the center, tools hanging below as taps, loop until no tool calls.
  • Collars clamped on the roundabout = middleware hooks.

Code

LCEL chain (still in langchain-core 1.x):

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
from langchain.chat_models import init_chat_model

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer using only this context:\n{context}"),
    ("human", "{question}"),
])
model = init_chat_model("anthropic:claude-sonnet-4-6")

chain = (
    RunnableParallel(context=retriever, question=RunnablePassthrough())
    | prompt
    | model
    | StrOutputParser()
)
chain.invoke("What is our refund window?")
for chunk in chain.stream("What is our refund window?"):
    print(chunk, end="")
chain.batch(["q1", "q2"], config={"max_concurrency": 4})

Agent with middleware (LangChain v1):

from langchain.agents import create_agent
from langchain.agents.middleware import (
    SummarizationMiddleware, HumanInTheLoopMiddleware,
    ModelCallLimitMiddleware, ToolCallLimitMiddleware, PIIMiddleware,
)

agent = create_agent(
    model="claude-sonnet-4-6",
    tools=[search_kb, send_email],
    system_prompt="You are a support assistant.",
    middleware=[
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        SummarizationMiddleware(model="claude-sonnet-4-6", trigger=("tokens", 4000), keep=("messages", 20)),
        HumanInTheLoopMiddleware(interrupt_on={"send_email": {"allowed_decisions": ["approve", "edit", "reject"]}}),
        ModelCallLimitMiddleware(run_limit=10),
        ToolCallLimitMiddleware(run_limit=15),
    ],
)
agent.invoke({"messages": [{"role": "user", "content": "Where is my order?"}]},
             config={"configurable": {"thread_id": "t-123"}})

Tradeoffs to volunteer

  1. Agent token cost is ~quadratic in loops — every loop re-sends the whole conversation + tool schemas. E.g. 3k-token prompt+schemas, +2k per tool result: 10th call reads >20k tokens; 10 calls total >100k. Mitigate: summarization middleware, call limits, prompt caching.
  2. Runaway loops — empty tool results cause retries; Python LangGraph default recursion_limit is now 10007 steps in 1.2.x (was 25, later 1000), so it's not a practical cost cap. Always set ModelCallLimitMiddleware / ToolCallLimitMiddleware and make tools return explicit "no results, do not retry" messages.
  3. Don't build an agent for a fixed flow — if you can draw the flowchart before seeing the input, use a chain/workflow.
  4. Abstraction weight — wrappers can lag provider features; content blocks + tool extras help; always inspect the actual request via tracing.
  5. Legacy code — pre-v1 tutorials use classes now in langchain-classic.

5 interview questions

Q1. What is a Runnable and why does it matter? The shared interface (invoke/batch/stream + async + config) implemented by prompts, models, parsers, retrievers, tools and compiled graphs. Because everything shares it, components compose with |, and the composite automatically supports streaming, batching, async and callbacks/tracing.

Q2. Chain vs agent — how do you choose? Who decides control flow. Chain: fixed at design time, one model call, predictable cost. Agent: model picks tools in a loop at run time — flexible but variable latency, ~quadratic token growth, runaway-loop risk. Default to a chain/workflow; escalate to an agent only when the path depends on input or tool results, and cap it.

Q3. What changed in LangChain v1? create_agent became the standard agent (replacing create_react_agent and legacy agent classes), middleware became the customization mechanism, standard content blocks unified message content, the namespace was slimmed and legacy moved to langchain-classic. Stability promise: no breaking changes until 2.0. create_agent runs on LangGraph, so persistence/streaming/HITL/time travel come built in.

Q4. How would you stop an agent from running up the bill? Call-limit middleware (model and tool), summarization or context editing to bound context size, prompt caching, a cheap-model/expensive-model router in wrap_model_call, tools that return explicit terminal messages, and tracing to spot outlier runs. Don't rely on the recursion limit (default 10007 in Python LangGraph 1.2.x).

Q5. Where does middleware run, and give three uses? Six hooks around the loop: before/after the whole agent, before/after each model call, and wrapping each model call and each tool call. Uses: summarize long history before the model; route/retry/fallback models in wrap_model_call; approve sensitive tool calls (HITL); redact PII; turn tool exceptions into recoverable messages.
