Vector DB Internals: HNSW, IVF, Quantization

17 min listen · How a vector database finds the nearest pins among a hundred million without checking them all: H N S W's stack of transparent sheets, I V F's neighborhoods and capitals, and quantization's shorthand coordinates, with the memory math, tuning dials, and filtering traps that decide cost and recall.

Facts verified: 2026-09-25

One-sentence thesis

Vector databases avoid brute-force search with approximate indexes (HNSW graphs, IVF partitions, disk graphs like DiskANN) and shrink memory with quantization plus rescoring; every setting trades recall against latency and memory, and filtered search is where those trades break silently.

The mental image: the map, with overlays

Same map of meaning as episode 1, now with 100M pins like sand. - Stack of transparent sheets above the map = HNSW (few pins + long threads on top, every pin + short threads at the bottom). - Borders and capitals drawn on the map = IVF (k-means centroids, search only the nearest nprobe neighborhoods). - Shorthand coordinates on each pin = quantization (fp16, int8, binary, PQ codes), rescored with exact coordinates.

Memory math

  • Raw vector: d × 4 bytes (float32). 1,024-d = 4 KB; 100M vectors ≈ 400 GB.
  • HNSW (Faiss guideline): (d × 4 + M × 2 × 4) bytes/vector → M=16 adds ~128 B. Vectors dominate.
Encoding Bytes (1,024-d) Compression Typical recall impact
float32 4,096 1× baseline
float16 / halfvec 2,048 2× negligible
int8 scalar 1,024 4× small
binary (1 bit/dim) 128 32× needs oversampling + rescoring
PQ (m=64, 8 bits) 64 64× needs rescoring

HNSW vs IVF vs DiskANN

HNSW IVF (+PQ) DiskANN (Vamana)
Structure Multi-layer graph k-means partitions Single-layer graph on SSD
Memory Highest (vectors in RAM) Low (with PQ) Compressed vectors in RAM, rest on SSD
Recall at equal latency Best Lower High
Inserts Incremental, natural Easy, but clusters go stale Supported in newer versions
Deletes Tombstones, degrade until rebuild Easy Supported
Sweet spot Up to ~100M in RAM Billion-scale, memory-bound Billion-scale on one machine

DiskANN original result: ~1B vectors, single machine with 64 GB RAM, >95% recall@1, few-ms latency.

Filtered search pitfall

Post-filtering an ANN candidate list (e.g. ef_search = 40) with a selective filter (one small tenant) leaves too few or wrong results. Fixes: filter-aware traversal / iterative scans (pgvector 0.8 hnsw.iterative_scan, bounded by hnsw.max_scan_tuples), exact search on small filtered subsets, partition per tenant. Always measure recall with real filters.

Key terms

Term Meaning
ANN Approximate nearest neighbour search
Recall@k Fraction of true top-k returned
HNSW Hierarchical Navigable Small World graph (Malkov & Yashunin)
IVF Inverted file index: k-means partitions
PQ Product quantization: sub-vector codebooks
Scalar / binary quantization Fewer bits per dimension
Oversampling + rescoring Retrieve extra candidates, re-rank with full precision
DiskANN / Vamana SSD-resident graph ANN from Microsoft Research
RaBitQ Binary-style quantization with theoretical error bounds
Tombstone Deleted marker left in graph

5 interview questions

Q1. How does HNSW work? Multi-layer proximity graph; each node appears in the bottom layer and, with exponentially decaying probability, higher layers. Greedy search descends from the sparse top to the dense bottom, then explores with a candidate list of size ef_search. M and ef_construction trade memory/build time for graph quality.

Q2. HNSW or IVF? HNSW: best recall/latency in memory, incremental inserts, but high RAM and awkward deletes. IVF: k-means partitions probed by nprobe, less memory, faster builds, pairs with PQ for billion scale, but lower recall at equal latency and needs retraining as data drifts.

Q3. Cut vector memory 10×? Quantize: binary (32×), PQ (64×+), int8 (4×), fp16 (2×). Recover recall via 2–3× oversampling and full-precision rescoring from disk. Also Matryoshka-truncate embeddings. Validate recall against exact search.

Q4. Why does filtered search return too few results? The ANN shortlist is built before the filter; a selective filter removes most candidates. Use filter-aware traversal or iterative scans, brute-force the small subset, or partition by tenant.

Q5. How do you know your index is good enough? Compute ground-truth neighbours by exact search on a query sample, measure recall@k and p95 latency across ef_search/nprobe values, with real filters, and pick the cheapest setting that meets the recall target. Re-check after heavy inserts/deletes.
