Track 4 · RAG · Episode 2

Chunking Strategies

17 min listen · Where you cut a document decides where its pins land on the map of meaning. Fixed, recursive, structure-aware, and semantic chunking, overlap, late chunking and contextual retrieval, with the numbers and failure stories that tell you which to reach for.

Facts verified: 2026-09-25

One-sentence thesis

Where you cut a document decides how sharp each chunk's embedding is and how much context the LLM gets, so parsing quality, boundaries, and context attached to each chunk matter more than which clever splitting algorithm you pick.

The mental image: the workbench

  • Left end: the bound manual (source document). Parse it well first.
  • Middle: the scissors and ruler (splitting strategy, chunk size, overlap).
  • Right end: the drawer of index cards (chunks). Each card gets its own pin on the map of meaning from episode 1. Retrieval only ever pulls cards, never the whole book.
  • Key question: what do you write on each card so it still makes sense away from the manual?
flowchart LR
    DOC["Source doc (PDF / HTML / MD)"] --> PARSE["Parser / layout extraction"]
    PARSE --> SPLIT["Splitter: fixed / recursive / structure-aware / semantic"]
    SPLIT --> CTX["Add context: title + section path, or LLM blurb"]
    CTX --> EMB["Embed chunk"]
    CTX --> BM["BM25 index"]
    EMB --> IDX[("Vector index")]
    BM --> IDX2[("Keyword index")]

Strategies compared

Strategy How Pros Cons
Fixed-size Cut every N tokens Simple, fast Cuts mid-sentence / rule-exception splits
Recursive Try \n\n, then \n, then spaces (words), then characters (default); add ". " for sentences Strong default Unaware of headings/tables
Structure-aware Split on headings, keep tables/code whole Best ROI for enterprise docs Needs a good parser
Semantic Cut where consecutive sentence embeddings diverge Helps unformatted text Costly, threshold-sensitive, modest gains
Late chunking Embed whole doc with long-context model, pool token vectors per chunk Context without extra LLM calls Needs token-level outputs, long-context model
Contextual retrieval LLM writes 50-100 token blurb per chunk, prepended before embedding + BM25 Big recall gains One LLM call per chunk at index time
Small-to-big (parent-doc) Match small chunks, return parent section Sharp matching + rich context Extra storage/lookups (episode 5)

Numbers to remember

  • Chroma chunking study: RecursiveCharacterTextSplitter at ~200–400 tokens, no overlap, was a consistently strong baseline (~88–89% token-level recall at 400); semantic/LLM chunkers beat it by only a couple of points.
  • Typical sizes: ~200–800 tokens; overlap ~10–20% (helps less than assumed when boundaries are good).
  • Contextual retrieval (Anthropic): failed retrievals (top-20) down 35% with contextual embeddings, 49% adding contextual BM25, 67% adding reranking. Cost ≈ $1.02 per 1M document tokens one-time with prompt caching.
  • Anthropic: if the whole knowledge base is < ~200K tokens (~500 pages), consider putting it all in the prompt (with caching) instead of RAG.

Code

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    chunk_size=400,        # tokens
    chunk_overlap=40,      # ~10%
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.split_text(doc_text)

# Prepend title + section path (cheap contextualisation)
records = [
    {"text": f"{doc_title} > {section_path}\n\n{c}",
     "doc_id": doc_id, "section": section_path}
    for c in chunks
]

Contextual retrieval prompt shape (per chunk, document cached):

<document>{WHOLE_DOCUMENT}</document>
Here is the chunk we want to situate within the whole document:
<chunk>{CHUNK_CONTENT}</chunk>
Give a short succinct context to situate this chunk within the overall
document for the purposes of improving search retrieval of the chunk.
Answer only with the succinct context and nothing else.

Pitfalls

  1. Parser is the real chunker: two-column PDFs interleaved, repeated headers/footers, flattened tables, scanned pages with no OCR. Eyeball extracted chunks first.
  2. Q/A pairs split apart: keep FAQ question+answer, heading+first paragraph, list intro+list together.
  3. Tables: never split mid-table; repeat header row in each table chunk.
  4. Chunking is versioned: changing it re-chunks and re-embeds everything; label eval sets by source passage text, not chunk ID.
  5. One size for everything: route by doc type (FAQ vs contract vs code).
  6. Chunk > embedding model max input → silent truncation.

Key terms

Term Meaning
Chunk Unit of text embedded and retrieved
Overlap Tokens repeated between adjacent chunks
Recursive splitting Hierarchical separator fallback
Structure-aware chunking Splitting along document structure (headings, tables)
Semantic chunking Splitting at embedding-similarity drops between sentences
Late chunking Pooling contextualised token embeddings per chunk after full-doc encoding
Contextual retrieval LLM-generated situating context prepended to each chunk
Parent-document retrieval Retrieve small, return larger parent

5 interview questions

Q1. How would you chunk a corpus of policy PDFs? Fix parsing first (layout-aware extraction, tables with headers, OCR where needed). Structure-aware recursive splitting on headings, a few hundred tokens, modest overlap, tables and lists kept whole. Prepend title and section path and store them as metadata. Tune size on a labelled eval set; add contextual retrieval if chunks are ambiguous out of context.

Q2. What's the tradeoff in chunk size? Small = sharp embeddings, high precision, but context loss and scattered answers. Large = context preserved, but embeddings blur toward an average of topics and each retrieved chunk costs more prompt tokens and latency.

Q3. Is overlap always good? It patches bad boundaries at the cost of duplication (storage, embedding cost, near-duplicate results). With good structural boundaries its benefit is often small; measure it.

Q4. Explain contextual retrieval and its cost. Per chunk, an LLM sees the full document and writes a 50-100 token situating blurb, prepended before embedding and BM25 indexing. Anthropic reported 35% / 49% / 67% fewer failed retrievals (embeddings / +BM25 / +rerank). One LLM call per chunk; ~$1 per million doc tokens with prompt caching.

Q5. What is late chunking and when can't you use it? Encode the whole document with a long-context embedding model, then mean-pool token embeddings within each chunk span, so each chunk vector carries document context. Requires a long-context model and access to token-level embeddings, which many hosted APIs don't expose.
