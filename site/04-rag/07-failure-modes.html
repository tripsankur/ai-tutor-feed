Track 4 · RAG · Episode 7

Production RAG Failure Modes & Fixes

16 min listen · A walk down the water line from source documents to the model's answer, stopping at every place production RAG actually breaks — dirty sources, bad parsing, stale indexes, leaky filters, overfilled context, poisoned documents — and the fix for each.

Facts verified: 2026-09-25

One-sentence thesis

Most production RAG failures are silent data-engineering failures upstream of the model — dirty sources, bad parsing, stale or mismatched indexes, leaky filters, overfilled context, poisoned content — so the real fix is per-station controls plus tracing every station.

The mental image: the water line

Left to right: reservoir (source documents) → treatment plant (parse, clean, chunk, metadata, embed) → storage tank (vector + keyword index) → valve (retrieval: filters, ranking) → glass (context window) → drinker (the LLM). Water flows one way; the diagnostic question is always "at which station did the water go bad?"

flowchart LR
    RES["Reservoir: source docs"] --> PLANT["Treatment plant: parse, chunk, metadata, embed"]
    PLANT --> TANK[("Storage tank: vector + keyword index")]
    TANK --> VALVE{"Valve: retrieval, filters, rerank"}
    VALVE --> GLASS["Glass: context window"]
    GLASS --> LLM["Drinker: LLM answer"]
    POISON["Poisoned doc (indirect prompt injection)"] -.-> RES
    CACHE["Semantic cache (hidden stale glass)"] -.-> LLM

Seven failure points (Barnett et al., 2024)

  1. Missing content 2. Missed the top-ranked documents 3. Not in context (dropped during consolidation) 4. Not extracted 5. Wrong format 6. Incorrect specificity 7. Incomplete. Lesson: RAG robustness evolves in operation — validate against real questions.

Code sketches

Embedding-version guard at startup:

index_meta = vector_store.get_index_metadata("policies_v7")
if index_meta["embedding_model"] != settings.EMBEDDING_MODEL:
    raise RuntimeError(f"Embedding mismatch: index={index_meta['embedding_model']} "
                       f"query={settings.EMBEDDING_MODEL}; refuse to serve")

Permission filter inside the search (not after):

hits = index.search(
    vector=embed(q),
    k=10,
    filter={"allowed_groups": {"$in": user.groups}, "status": "current"},  # pre-/in-filter
)

Source-vs-index reconciliation (nightly):

SELECT i.doc_id FROM index_docs i
LEFT JOIN source_docs s ON s.doc_id = i.doc_id AND s.status = 'current'
WHERE s.doc_id IS NULL;   -- orphans: deleted or superseded but still retrievable

Observability checklist (per request)

Rewritten query · retrieved chunk IDs + scores + ranks · doc versions/effective dates · final assembled prompt (redacted, with retention) · answer + citations · latency per stage. Fleet-level: freshness lag, orphan count, embedding version, "I don't know" rate, rephrase rate, faithfulness on sampled traffic.

War story (generic): an embedding-library upgrade changed the default model on the query side; re-index was scheduled days later. For five days quality collapsed with perfect latency, error and uptime metrics — caught by a spike in users rephrasing questions.

Key terms

Term Meaning
Indirect prompt injection Malicious instructions arriving via retrieved content rather than the user (OWASP LLM01:2025 Prompt Injection)
Vector and embedding weaknesses OWASP LLM08:2025 — e.g. cross-tenant leakage, embedding inversion, poisoning of vector stores
Lost in the middle U-shaped accuracy vs position of relevant info in long context (Liu et al., 2023)
Blue-green re-index Build new index in parallel, evaluate, switch traffic atomically
Freshness lag Time between a source change and its reflection in the index
Reconciliation Periodic diff of source IDs vs index IDs to find orphans
Semantic cache Returns a stored answer for a sufficiently similar prior question

5 interview questions

Q1. Users report wrong answers. How do you debug? Pull traces and walk the line backwards: in corpus? parsed/chunked correctly? index fresh and same embedding model? retrieved, at what rank? survived prompt assembly? then did the model use it? Most faults are upstream of the model.

Q2. How do you enforce document permissions in RAG? As a filter inside retrieval using the caller's identity/groups and access metadata synced from the source (kept fresh). Never post-filter in the app, never rely on the prompt; red-team with per-user should-refuse questions; include permission scope in any cache key.

Q3. Name a silent RAG failure and its fix. Embedding model mismatch between index and query side: results return, no errors, quality collapses. Pin and record the model version on the index, startup check, blue-green re-index on any model change.

Q4. Why can adding more retrieved chunks make answers worse? Lost in the middle: models use information at the start/end of context better than the middle; extra chunks add distractors, cost and latency. Retrieve wide, rerank, keep 5–10, put the strongest at the edges.

Q5. How do you defend RAG against prompt injection in documents? Layered: restrict ingested sources, mark retrieved text as untrusted data, scan ingested content, faithfulness/output checks — and above all least-privilege on tools and actions so a poisoned chunk can't trigger side effects.
