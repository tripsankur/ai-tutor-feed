Track 4 · RAG · Episode 6

RAG Evaluation: RAGAS & Friends

16 min listen · How to stop judging a RAG system on vibes: the triangle of question, context and answer, the metrics that live on each edge, how RAGAS computes them underneath, and why your LLM judge needs its own evaluation.

Facts verified: 2026-09-25

One-sentence thesis

RAG evaluation is decomposition: measure retrieval and generation on separate edges of the question–context–answer triangle, so a regression points at the component that caused it — and evaluate the LLM judge before trusting any judge-based score.

The mental image: the triangle and the lamp

  • Bottom-left corner = question. Top corner = retrieved context. Bottom-right corner = answer.
  • Lamp hanging above = the human-written reference (ground truth). Only exists in the offline golden set.
  • Every metric is a line between two points: three triangle edges (reference-free → can run on production traffic) and two dashed lines from the lamp (need references → offline only).

Golden set checklist

  • 50–200 questions to start; tag each with a slice (prose, table, numeric, multi-hop, unanswerable).
  • Sources, best first: sampled production questions → expert-written hard cases → synthetic (RAGAS test set generator). Synthetic-only sets flatter the retriever (questions written in the chunk's own vocabulary).
  • Store: question, reference answer, relevant doc IDs, slice.
  • Owner + refresh cadence (references go stale when docs change). Feed bad production conversations back in.

Where each layer runs

flowchart LR
    COMMIT["Every commit"] --> DET["Deterministic retrieval metrics: recall@k, MRR"]
    NIGHT["Nightly / pre-release gate"] --> JUDGE["Judge suite on golden set: faithfulness, relevancy, context precision/recall, correctness"]
    PROD["Production (sampled traces)"] --> TRIAD["Reference-free triad + user signals: thumbs, citation clicks, rephrase rate, escalations"]

Deterministic retrieval metrics need no framework:

def recall_at_k(retrieved_ids, relevant_ids, k=10):
    return len(set(retrieved_ids[:k]) & set(relevant_ids)) / len(relevant_ids)

def mrr(retrieved_ids, relevant_ids):
    for rank, d in enumerate(retrieved_ids, 1):
        if d in relevant_ids:
            return 1 / rank
    return 0.0

Judge pitfalls and statistics

  • Biases: position (pairwise order flips verdicts), verbosity (longer rated higher), self-preference (same-family judge is kinder).
  • Calibrate: 100–200 human-labelled items → measure judge–human agreement; ~90% = trust the trend, ~70% = you're measuring the judge. Cross-family judge; randomise/both orderings in pairwise; re-calibrate when the judge model changes.
  • Noise: n=200, p≈0.8 → 95% margin ≈ ±5.5 points (1.96·√(0.16/200)). Use paired comparisons (count fail→pass vs pass→fail flips on the same items) or larger sets.
  • Cost: 200 questions × 4 judge metrics × 2–3 calls ≈ 1,600–2,400 LLM calls per run → run nightly, not per commit.

War story (generic): faithfulness sat at 0.95 for months while users got "I don't have information on that" for documented topics — a re-index broke metadata filters, retrieval returned the wrong department's docs, the model faithfully refused. Adding context recall + recall@10 on a labelled subset exposed it on the first run.

Key terms

Term Meaning
Golden set Fixed, versioned evaluation set of questions (+ references, relevant IDs, slices)
RAG triad Context relevance, groundedness, answer relevance — reference-free
Faithfulness Fraction of answer claims supported by retrieved context
Context recall Fraction of reference claims attributable to retrieved context
Context precision Rank-aware share of retrieved chunks that are relevant
MRR Mean reciprocal rank of the first relevant result
nDCG Graded, position-discounted ranking quality
LLM-as-judge Model scoring outputs against a rubric; must be calibrated against humans
Paired comparison Old vs new on identical items; count flips instead of comparing averages

5 interview questions

Q1. How would you evaluate a RAG system? Separate retrieval from generation. Golden set of ~100–200 tagged questions (production samples + expert hard cases, synthetic for coverage) with references and relevant IDs. Retrieval: recall@k/MRR (deterministic, every commit) + context precision/recall. Generation: faithfulness, answer relevance, correctness vs reference, reported per slice. Judge suite gates releases; reference-free triad on sampled production traces; judge calibrated against humans.

Q2. Faithfulness is high but users are unhappy. Why? Faithfulness only checks answer against context. Wrong, stale or missing context → the model can be perfectly faithful to bad evidence, or faithfully refuse. Check context recall and recall@k; look for broken filters, stale index, chunking regressions.

Q3. How does RAGAS compute faithfulness and answer relevancy? Faithfulness: judge splits the answer into atomic claims, checks each against the context, score = supported/total. Response relevancy: judge generates questions the answer would answer, embeds them, averages cosine similarity to the original question.

Q4. Can you trust LLM-as-judge? Only after calibration: known position, verbosity and self-preference biases. Human-label a sample, measure agreement, use a different model family from the generator, randomise order in pairwise tests, re-calibrate when the judge changes.

Q5. Your new version scores 81 vs 78 on 200 questions. Ship it? Not on that evidence: ±~5.5 points sampling margin at that size. Run a paired comparison (count per-item flips), repeat runs to average out judge non-determinism, and check per-slice results for hidden regressions (e.g. tables) before deciding.
