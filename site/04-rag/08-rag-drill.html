DRILL: RAG Rapid-Fire

10 min listen · Fifteen rapid-fire interview questions across the whole R A G track — embeddings, chunking, hybrid retrieval and reranking, vector index internals, advanced techniques, evaluation, and production failure modes. Answer aloud in the pause, then compare.

One-sentence thesis

A strong RAG interview answer always names the stage (ingest → index → retrieve → assemble → generate), the mechanism underneath, the cost, and how you'd measure it.

This is the Track Four drill — fifteen questions across the whole R A G track, from embeddings to production failure modes. Same format as always: I ask, you answer out loud in the pause, then I give you a strong answer to compare against. The questions run roughly in track order, so you'll hear where your gaps are. Ready. [PAUSE 2s] Question one. What is an embedding, and what does cosine similarity actually measure? [PAUSE 6s] Strong answer: an embedding is a fixed-length vector a model produces for a piece of text, trained contrastively so that related texts point in similar directions. Cosine similarity measures the angle between two vectors and ignores their length; normalise to unit length and cosine, dot product, and Euclidean distance give the same ranking. And the scores aren't calibrated probabilities, so any threshold has to be tuned per model on labelled data. [PAUSE 2s] Question two. You need to change your embedding model. What has to happen? [PAUSE 6s] Strong answer: every vector must be regenerated, because vectors from different models live in different spaces and aren't comparable. Build a parallel index, re-embed the corpus, evaluate it, and cut queries and documents over together. Store the model identifier on the index and check it at startup, so a mismatch is refused rather than silently served as near-random results. [PAUSE 2s] Question three. What's the tradeoff in chunk size, and what's a sensible default? [PAUSE 6s] Strong answer: small chunks give sharp embeddings and precise matches but lose context; large chunks keep context but blur the embedding across several topics and cost more prompt tokens. A sensible default is structure-aware recursive splitting at a few hundred tokens, following headings, keeping tables and code whole, with modest overlap and the title and section path attached. Then tune against measured recall, not intuition. [PAUSE 2s] Question four. Why not just use vector search? Make the case for hybrid. [PAUSE 6s] Strong answer: dense retrieval is great at paraphrase but weak on exact identifiers, rare names, and error codes; B M twenty-five is the opposite. Run both and fuse the ranked lists with reciprocal rank fusion, which scores each result by one over sixty plus its rank in each list, so agreement wins. It covers both failure modes for tens of milliseconds of extra latency. [PAUSE 2s] Question five. What does a cross-encoder reranker do, and why not use it for everything? [PAUSE 6s] Strong answer: a cross-encoder reads the query and a candidate together and scores relevance far more accurately than a bi-encoder, which embeds them separately. But it costs a model pass per candidate and nothing can be precomputed, so you apply it only to the top fifty to a hundred fused candidates and keep the top handful. It's usually the biggest single quality gain available without re-indexing. [PAUSE 2s] Question six. Explain H N S W and its tuning dials. [PAUSE 6s] Strong answer: a multi-layer proximity graph — every vector in the bottom layer, a shrinking random subset in each layer above, each node linked to its nearest neighbours. Search descends greedily from the sparse top to the dense bottom, then explores locally. M and ef construction trade memory and build time for graph quality; ef search is the query-time dial between recall and latency. [PAUSE 2s] Question seven. How would you cut vector index memory by ten times or more? [PAUSE 6s] Strong answer: quantize. Scalar quantization gives two to four times, binary gives thirty-two times, product quantization can go further; then win recall back by oversampling and rescoring the shortlist with full-precision vectors kept on disk. Matryoshka truncation of the embeddings helps too. Always validate recall against exact search. [PAUSE 2s] Question eight. Filtered vector search returns only two results for a small tenant. Why? [PAUSE 6s] Strong answer: post-filtering. The approximate search fetched a top-k shortlist first, and the selective filter then removed almost everything in it. Fix it with filter-aware traversal or iterative scans, exact search over the filtered subset when it's small, or partitioning by tenant — and test recall with real filters. [PAUSE 2s] Question nine. What is HyDE, and when does it hurt? [PAUSE 6s] Strong answer: hypothetical document embeddings — the model drafts a fake answer, and you search with the embedding of that fake answer, because answer-shaped keys land near answer-shaped chunks. The fake text is only a search key, never shown as evidence. It hurts on exact-match lookups like part numbers, and in domains the model doesn't know, where the fake answer drifts to the wrong topic — so fuse it with the original query rather than replacing it. [PAUSE 2s] Question ten. When is Graph R A G worth its cost? [PAUSE 6s] Strong answer: when questions are about the whole collection — themes and trends — or need multi-hop relationships, which no single chunk answers. It pays for that with model-based entity and relationship extraction over the entire corpus, community detection, and summaries at every level, then answers global questions by map-reduce over those summaries. For "find the passage about X" questions, plain vector search is enough; lighter variants like LazyGraphRAG defer the cost to query time. [PAUSE 2s] Question eleven. What does agentic R A G add, and what's the main production risk? [PAUSE 6s] Strong answer: the model decides whether to retrieve, grades what came back, rewrites the query and retries when results are poor, and can route to other tools like sequel. The risk is multiplied latency and cost, and unbounded loops on questions the corpus simply can't answer. Cap retries at two or three and give an honest "not found" answer when the cap is hit. [PAUSE 2s] Question twelve. Name the core RAGAS metrics and which part of the system each one tests. [PAUSE 6s] Strong answer: context precision and context recall test retrieval — are the retrieved chunks relevant and ranked well, and do they cover what the reference answer needs. Faithfulness tests generation against context — the share of answer claims supported by the retrieved chunks. Answer relevance tests whether the answer addresses the question; factual correctness compares it with a reference. Context recall and correctness need references; faithfulness and relevance don't, so they can run on live traffic. [PAUSE 2s] Question thirteen. Faithfulness is at zero point nine five, but users are unhappy. What's going on? [PAUSE 6s] Strong answer: faithfulness only checks the answer against the retrieved context. If retrieval returned stale or wrong documents, or nothing useful, the model can be perfectly faithful to bad evidence, or faithfully refuse. Check context recall and recall at k, and look for a retrieval regression like a broken metadata filter or a stale index. [PAUSE 2s] Question fourteen. Can you trust an L L M as a judge? [PAUSE 6s] Strong answer: only after you've evaluated the judge. Judges show position bias, verbosity bias, and self-preference toward their own model family. Label a hundred to two hundred items by hand, measure agreement, use a different model family from the generator, randomise order in pairwise tests, and re-calibrate whenever the judge model changes. [PAUSE 2s] Question fifteen. How do you enforce document permissions in R A G, and what's the classic mistake? [PAUSE 6s] Strong answer: enforce them as a filter inside retrieval, based on the caller's identity and group memberships, using access metadata synced fresh from the source system. The classic mistakes are filtering after retrieval in application code, or telling the model in the prompt not to reveal things — neither is access control. And remember that stale access metadata in the index means revoked users keep access until the next sync. [PAUSE 2s] That's the drill.
