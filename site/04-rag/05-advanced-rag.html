Track 4 · RAG · Episode 5

Advanced RAG: HyDE, Parent-Document, GraphRAG, Agentic RAG

18 min listen · Four upgrades to a plain retrieval pipeline, each fixing a different failure: HyDE fixes the question-shaped query, parent-document fixes the too-small chunk, GraphRAG fixes the question no single chunk can answer, and agentic RAG fixes the one-shot retrieval that never checks its own work.

Facts verified: 2026-09-25

One-sentence thesis

Each advanced RAG technique fixes one specific failure of a correctly-built plain pipeline — diagnose the failure first, then pay for the one upgrade that fixes it, never all four by default.

The mental image: the library

Left to right: reference desk (the question arrives; the librarian = retrieval logic) → card catalog + stacks (index cards = chunks, drawers = embedding neighbourhoods, shelves = the full corpus) → reading room (the writer = the LLM, who only sees what is carried in).

Upgrade Where it lives in the library Failure it fixes
HyDE Reference desk: the writer drafts a fake answer; the librarian searches with it Short or vague question doesn't land near answer-shaped chunks
Parent-document Between the catalog and the shelves: search small cards, carry the whole chapter Chunk matches, but lacks the context around it
GraphRAG Map on the ceiling: entities, relationships, nested community regions with summaries "Whole-collection" or multi-hop questions no single chunk answers
Agentic RAG The librarian walks back and forth: retrieve → grade → rewrite → retry One-shot retrieval that never checks its own work

Code sketches

HyDE (framework-agnostic):

def hyde_search(question, llm, embed, index, k=10):
    fake = llm(f"Write a short passage that answers: {question}")
    # search with both, then fuse (e.g. reciprocal rank fusion)
    hits_q = index.search(embed(question), k=k)
    hits_h = index.search(embed(fake), k=k)
    return reciprocal_rank_fusion([hits_q, hits_h])[:k]   # fake passage is NEVER shown to the user

Parent-document retrieval (small-to-big):

children = index.search(embed(question), k=20)          # ~200-token child chunks
parent_ids = list(dict.fromkeys(c.metadata["parent_id"] for c in children))
parents = docstore.mget(parent_ids[:4])                   # cap parents: context budget

LangChain ships this as ParentDocumentRetriever (a MultiVectorRetriever subclass); since LangChain v1 it lives in langchain_classic.retrievers.

Agentic RAG loop (LangGraph-style nodes, as in the official tutorial): generate_query_or_respond → retrieve (ToolNode) → grade_documents → generate_answer | rewrite_question → back to generate_query_or_respond. Add a retry counter in state and a "not found" terminal.

Costs at a glance

Technique Index-time cost Query-time cost Main pitfall
HyDE none +1 LLM generation (hundreds of ms to 1s+) Wrong-topic fake answer in unfamiliar domains; hurts exact-match (codes, IDs)
Parent-document second store + ID mapping more context tokens (10 parents × 2k = 20k tokens) Child/parent stores drift out of sync; lost-in-the-middle
Contextual chunks 1 LLM call per chunk (cacheable) none Indexing cost; Anthropic reported −49% retrieval failures (−67% with reranking)
GraphRAG LLM extraction over whole corpus + community reports global search = many LLM calls Indexing bill; extraction errors propagate into summaries
LazyGraphRAG ≈ vector RAG (≈0.1% of full GraphRAG) deferred LLM work, budget-controlled Newer; fewer production references
Agentic RAG none 4–8 LLM calls, 5–15s typical Unbounded loops on unanswerable questions → cap retries

War story (generic): an agentic assistant with a relevance grader and no retry cap looped on questions about an undocumented product; each cost ~50× a normal query; a few percent of traffic doubled the monthly model bill. Fix: cap at 2–3 attempts + an honest "not found" answer.

Key terms

Term Meaning
HyDE Hypothetical Document Embeddings (Gao et al., 2022): embed an LLM-written fake answer instead of the query
Small-to-big / parent-document Retrieve on small child chunks, return their larger parents
Multi-vector retrieval Several representations (summary, hypothetical questions, raw text) per parent, all pointing to the parent
Contextual retrieval Prepend an LLM-written chunk-in-document context before embedding + BM25 (Anthropic, 2024)
GraphRAG Entity/relationship graph + hierarchical community summaries for global and multi-hop questions (Microsoft Research, 2024)
Leiden Community detection algorithm used to build GraphRAG's nested communities
Global / Local / DRIFT search GraphRAG query modes: map-reduce over communities / entity neighbourhood / local primed with community context
LazyGraphRAG Defers LLM summarisation to query time; indexing cost ≈ vector RAG
Agentic RAG LLM decides when/what to retrieve, grades results, rewrites and retries
Self-RAG Asai et al., 2023: model trained to emit reflection tokens (retrieve? relevant? supported? useful?)
Corrective RAG (CRAG) Yan et al., 2024: retrieval evaluator labels results correct/incorrect/ambiguous and triggers fallback (e.g. web search)

5 interview questions

Q1. Your RAG system gives bad answers. Which advanced techniques would you use? Diagnose first with an eval set separating retrieval from generation. Short/vague queries missing the right chunk → query rewriting or HyDE (fused with the original query). Right chunk found but answer lacks context → parent-document or contextual chunks. Whole-corpus/thematic or multi-hop questions → GraphRAG. Retrieval sometimes wrong with nothing catching it → agentic loop with a grader and a retry cap.

Q2. Why does HyDE work if the hypothetical document contains false facts? Queries and documents are shaped differently; an answer-shaped key lands nearer answer-shaped chunks (document-to-document similarity). The embedding captures topic and structure and largely ignores specific false details, and the fake text is only a search key — never shown or used as evidence. It fails when the LLM doesn't know the domain and drafts the wrong topic.

Q3. When would you choose GraphRAG over vector search, and what does it cost? For questions about the whole collection ("main themes across all reports") and multi-hop relationship questions. Cost: LLM entity/relationship extraction over every chunk plus community reports at every hierarchy level — orders of magnitude more indexing spend than vector RAG, and repainting on corpus change. Consider LazyGraphRAG to defer cost to query time.

Q4. What is parent-document retrieval and what can go wrong? Index small child chunks for precise matching; at query time map children to parent IDs, dedupe, and return parents for context. Risks: context bloat (cap parents), lost-in-the-middle, and child/parent stores drifting out of sync after updates (rebuild both atomically per document version).

Q5. What are the risks of agentic RAG in production? Latency and cost multiply (several LLM calls per question), loops can be unbounded on unanswerable questions, and debugging is harder. Mitigations: hard retry cap, explicit "not found" path, per-step tracing, and routing so simple questions skip the loop.
