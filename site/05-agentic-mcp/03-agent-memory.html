Track 5 · Agentic AI + MCP · Episode 3

Agent Memory: Short-Term, Long-Term, Summarization

16 min listen · A stateless model only knows what's on the scroll. This episode builds the scribe at the in-slot who trims and compacts the scroll, and the basement archive of semantic, episodic, and procedural memory, then covers write paths, read paths, and the ways memory fails: lost constraints, poisoning, leakage, and staleness.

Facts verified: 2026-09-25

One-sentence thesis

The model is stateless, so "agent memory" means only two things — what is on the context now (short-term: persisted, trimmed, cleared, compacted) and what machinery puts back onto it (long-term: namespaced semantic / episodic / procedural stores with explicit write and read paths). A bigger context window is a bigger desk, not a filing system.

Why not just a huge context window?

  1. Cost — whole context re-sent every lap (100k tokens × 30 laps = 3M input tokens; caching softens, doesn't eliminate).
  2. Latency — longer input, slower response.
  3. Quality — "Lost in the Middle" (Liu et al., 2023): facts mid-context are used worse; "context rot" as context grows.
  4. Session end — context vanishes; tomorrow starts blank.

Short-term mechanics

Tool What it does Cost Risk
Checkpointer (LangGraph) Persist full thread state after every step, keyed by thread_id Storage writes None — prerequisite for resume, HITL pauses, time travel
Trim / sliding window Keep system prompt + last N turns Free Early constraints vanish; never split a tool call from its result (API rejects orphaned results)
Tool-result clearing Replace old tool outputs with placeholder, keep the call Free (server-side) Breaks prompt cache → clear in chunks
Compaction / summarization Older turns → summary; recent turns verbatim One extra model call Lossy; summarizer decides what matters

Summarization prompt checklist (the fix for the cold-open war story)

Preserve verbatim: user constraints/instructions · decisions + rationale · open tasks · exact identifiers (ticket IDs, file paths, order IDs, table names) · unresolved errors. Standing rules go in the system prompt (never summarized) and are enforced in code (approval gates).

Long-term memory

Cabinet Content Storage shape Example
Semantic Facts about user/domain Profile doc (update in place) or collection of atomic facts (search, dedupe) "Team runs on Azure"
Episodic Past experiences Past runs / trajectories retrieved as few-shot examples "Last payments incident: schema change"
Procedural How to behave System prompt, learned rules, skills (human-approved updates) "Always add a date filter"

Dedicated memory layers (landscape, 2026): Mem0 (fact extraction → vector store), Zep / Graphiti (bi-temporal knowledge graph: valid-from / valid-to), Letta (MemGPT lineage: in-context core memory + archival memory, self-editing), LangMem (LangChain memory SDK).

Write path (dumbwaiter down)

  • Hot path: agent calls a save-memory tool mid-conversation → immediate, but adds latency and relies on in-the-moment judgment.
  • Background: post-session/scheduled extraction → no user-facing latency, better consolidation, delayed.
  • Conflicts: update/retire old facts, timestamp everything, or keep validity intervals (temporal graph).

Read path (dumbwaiter up)

  • Always-on small profile (tokens every lap — keep it small).
  • Per-turn retrieval (RAG over memories; score by relevance + recency + importance — Generative Agents, Park et al. 2023). Retrieve per user turn, not per lap.
  • Agent-driven memory tool (just-in-time context; lean, but model may not look).

Pitfalls

  1. Lost constraints after compaction → system prompt + checklist summary + code-enforced gates.
  2. Memory poisoning — injected text persisted into memory, resurfaces in future sessions → treat writes as untrusted, record provenance, no external-source writes to procedural memory, human review for behavior-changing memories.
  3. Cross-user leakage — wrong/missing namespace key → enforce tenant/user namespaces in the storage layer; test it.
  4. Right to erasure — deletion must reach fact store, vector index, transcripts, and summaries → keep an inventory.
  5. Staleness & bloat → timestamps, decay/expiry, periodic consolidation.
  6. Token overhead — 2k tokens of memories × 30 laps = 60k extra input tokens; measure that memory actually helps.

5 interview questions

Q1. How do you give an agent memory? Separate short-term (thread context, checkpointed; kept within budget by turn-boundary trimming, tool-result clearing, and compaction with a must-preserve checklist) from long-term (namespaced semantic/episodic/procedural store with hot-path + background writes and profile / retrieval / tool-based reads).

Q2. Why not rely on a million-token context window? Re-sent every lap (cost), slower, degraded use of mid-context info (lost in the middle / context rot), and gone at session end. Bigger desk, not a filing system.

Q3. How do you stop summarization from losing critical information? Standing rules in the system prompt (never summarized); a summarization prompt with explicit preserve-list (constraints, decisions, open tasks, exact IDs); keep recent turns verbatim; enforce safety rules in code, not memory.

Q4. What is memory poisoning and how do you defend against it? Prompt injection that gets written into long-term memory and resurfaces in later sessions. Defend by treating memory writes as untrusted, recording provenance, blocking external-content writes to procedural memory, human review for behavior-changing memories, per-user namespaces.

Q5. Hot-path vs background memory writes? Hot-path: immediate availability, adds latency, depends on the model's in-the-moment judgment — use for explicit "remember this". Background: no live latency, better dedupe/consolidation/conflict resolution, delayed — use for everything else. Many systems do both.
