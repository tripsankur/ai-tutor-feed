Track 5 · Agentic AI + MCP · Episode 6

MCP vs Function Calling; Security & Auth in Real Deployments

16 min listen · Function calling is how a model decides; MCP is how that decision gets delivered to a tool you don't own. Then the security half: OAuth 2.1 with protected resource metadata, PKCE, resource-bound tokens and client ID metadata documents, plus the attacks that actually hit MCP deployments.

Facts verified: 2026-09-25 (authorization per MCP spec revision 2026-07-28)

One-sentence thesis

Function calling is the model's decision interface ("call X with these args"); MCP is the discovery + delivery layer that connects that decision to tools you may not own — and securing remote MCP means OAuth 2.1 done precisely (protected resource metadata, CIMD, PKCE, resource-bound tokens, issuer validation, no token passthrough) plus defenses against prompt injection that no OAuth flow can stop.

The mental image: the line, the badge office, and the doors

  • Horizontal line across the middle. Above = model's world: reads tool menu, emits a structured call (function calling). Below = the MCP pipe running left→right from the host to server doors.
  • Badge office (upper right) = authorization server issuing tokens.
  • Back hallway behind each door = upstream APIs; the server needs its own token there.
  • Poisoned menu (above the line) = tool descriptions/results as injection vectors.

Function calling vs MCP

Plain function calling MCP
Layer Model ↔ your app (decision format) Host ↔ server (discovery, transport, execution)
Who writes the tool You, in-process Anyone — often the SaaS vendor
Discovery Hard-coded list tools/list at runtime; list-changed notifications
Reuse One app Every compliant host (chat, IDE, agents)
Security boundary Your process, your creds Separate process/service with its own creds + OAuth
Latency Lowest Extra hop (local stdio ≈ negligible; remote HTTP = network RTT)
Best for App-private, tightly coupled, latency-critical tools Shared, third-party-owned, or isolated capabilities

They compose: the host translates MCP tool definitions into the provider's function-calling schema; the model's tool_call is routed back as tools/call.

Requirement Standard Rule
OAuth 2.1 draft-ietf-oauth-v2-1-13 Auth code + PKCE; no implicit flow
Protected Resource Metadata RFC 9728 Servers MUST publish; clients MUST use for AS discovery
AS metadata RFC 8414 / OIDC Discovery AS provides ≥1; clients support both
PKCE OAuth 2.1 MUST, S256; refuse if code_challenge_methods_supported absent
Resource indicators RFC 8707 resource param in auth + token requests = canonical server URI
Audience validation RFC 8707 / OAuth 2.1 §5.2 Server MUST reject tokens not issued for it
Issuer identification RFC 9207 AS SHOULD return iss; client MUST validate (mix-up defense) — new in 2026-07-28
Client ID Metadata Documents draft-ietf-oauth-client-id-metadata-document client_id is an HTTPS URL to a JSON metadata doc — preferred registration
Dynamic Client Registration RFC 7591 Deprecated 2026-07-28 (backward compat only)
Step-up RFC 6750 403 insufficient_scope + required scope → re-authorize
Token use OAuth 2.1 §5 Authorization: Bearer on every request; never in query string
Extensions ext-auth Enterprise-Managed Authorization (IdP-controlled, ID-JAG); OAuth Client Credentials (M2M)

Attacks and mitigations

Attack What happens Mitigation
Token passthrough Server forwards client token to upstream API Forbidden: server gets its own upstream token; validate audience
Confused deputy Proxy with static client ID + cached third-party consent lets attacker's registered client receive a code Proxy MUST get per-client user consent before forwarding
Mix-up Malicious AS tricks client into sending code to wrong AS Validate iss (RFC 9207); issuer-bound client credentials
Tool poisoning / rug pull Hidden instructions in tool descriptions; descriptions change after approval Allow-list + pin servers; treat descriptions/annotations as untrusted; re-approve on change
Indirect prompt injection Tool results (issues, tickets, web pages) instruct the model Break the lethal trifecta (private data + untrusted content + external comms); human approval on outbound/destructive actions
Supply chain Malicious postmark-mcp (Sept 2025) BCC'd all emails after 15 clean versions Official publishers, pinned versions, review, SBOM
DNS rebinding Web page reaches local HTTP server Validate Origin; bind to 127.0.0.1
State handle hijacking Guessed/stolen cart/workflow handle Random handles, bind to authenticated user, never auth-by-handle
SSRF Server fetches attacker-supplied URLs (incl. metadata URLs) Block private/metadata IP ranges; allow-list

Production checklist: allow-list + pin servers · human-in-the-loop for destructive/outbound tools · short-lived tokens, rotated refresh tokens · no tokens in URLs/logs · gateway metering on Mcp-Method/Mcp-Name · full audit log (user, server, tool, args, result).

5 interview questions

Q1. MCP or function calling — which should we use? They're layers: function calling is how the model expresses the decision; MCP is how the host discovers tools and delivers the call to a server it may not own. Plain function calling for app-private, tightly coupled, latency-critical tools; MCP for capabilities reused across hosts, owned by third parties, or needing an isolated security boundary.

Q2. Walk me through authorization for a remote MCP server. Server = OAuth 2.1 resource server. Unauthenticated request → 401 with WWW-Authenticate pointing to protected resource metadata (RFC 9728), which names the AS. Client discovers AS metadata, registers (pre-registered → CIMD → deprecated DCR), runs auth code + PKCE S256 with a resource indicator, validates iss, sends Bearer token. Server validates audience; step-up via 403 insufficient_scope.

Q3. Why is token passthrough forbidden? It breaks audience binding and audit (upstream can't attribute the caller), bypasses the server's own controls, and turns one stolen token into access to every upstream. The server must obtain its own token for upstream APIs and reject tokens not issued for itself.

Q4. What's the biggest real-world MCP risk, and how do you mitigate it? Prompt injection — via tool descriptions (tool poisoning) or tool results (indirect injection) — combined with broad permissions. OAuth guards the door, not the model's instructions. Break the lethal trifecta, require human approval on outbound/destructive actions, allow-list and pin servers, and log every call.

Q5. How do you roll MCP out in an enterprise? Central allow-list/registry of approved servers; Enterprise-Managed Authorization so the corporate IdP (Entra ID, Okta) controls which employees reach which servers; client credentials extension for M2M jobs; remote servers behind a gateway that routes/rate-limits on Mcp-Method/Mcp-Name; minimal scopes with step-up; audit logging into the SIEM.
