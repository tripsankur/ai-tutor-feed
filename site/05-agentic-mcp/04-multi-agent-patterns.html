Multi-Agent Patterns: Orchestrator-Worker, Handoffs, Debate

17 min listen · One office floor, three layouts: how orchestrator-worker, handoffs, and debate actually move context between agents, what each costs in tokens and failure modes, and why the strongest multi-agent systems keep writes single-threaded.

Facts verified: 2026-09-25

One-sentence thesis

Multi-agent is a context-management and compute-spending technique, not an org chart: orchestrator-worker wins on breadth-first, parallel, read-heavy tasks; handoffs win on sequential conversational flows; debate rarely beats plain majority voting at equal compute — and in every pattern, writes should stay single-threaded.

The mental image: one office floor, three layouts (seen from above)

  • Top half — raised desk + row of worker desks: orchestrator writes detailed assignments down the lines; workers start with clean contexts, work in parallel, send compressed summaries back up. Workers never talk to each other.
  • Bottom right — row of service counters: the user is walked from counter to counter; control transfers, and whoever holds the current counter owns the conversation (handoff / swarm).
  • Bottom left — round table + judge's chair: agents propose, read each other, revise over rounds; a judge decides (debate / generator-critic).

Minimal agents-as-tools vs handoff sketch (OpenAI Agents SDK, Python):

from agents import Agent, Runner

researcher = Agent(name="Researcher", instructions="Research ONE platform's governance model. Return <=200 words.")
billing = Agent(name="Billing", instructions="Resolve billing disputes.")

# Orchestrator-worker: parent stays in control, gets result back
lead = Agent(
    name="Lead",
    instructions="Split the comparison into sub-tasks, call researcher per platform, then synthesize.",
    tools=[researcher.as_tool(tool_name="research_platform", tool_description="Research one platform")],
)

# Handoff: control transfers, Billing owns the conversation
triage = Agent(name="Triage", instructions="Route the user.", handoffs=[billing])

result = Runner.run_sync(lead, "Compare governance in A, B, C for a regulated bank")

Numbers to quote

  • Anthropic research system (orchestrator-worker, Opus 4 lead + Sonnet 4 subagents): +90.2% vs single-agent Opus 4 on internal research eval.
  • Tokens: agents ≈ 4× chat; multi-agent ≈ 15× chat. Token usage explained ~80% of performance variance on BrowseComp.
  • Parallelism (3–5 subagents, 3+ parallel tool calls each) cut research time up to 90% on complex queries.
  • Effort scaling rule: simple fact = 1 agent, 3–10 tool calls; comparison = 2–4 subagents; complex research = 10+ subagents.
  • War story: early versions spawned 50 subagents for simple queries.
  • Error compounding: 0.95^5 ≈ 0.77 end-to-end for a five-agent chain.
  • MAST (Berkeley, NeurIPS 2025 D&B): 14 failure modes in 3 categories — system design/specification, inter-agent misalignment, task verification.
  • Debate vs voting: multiple 2025 studies find majority voting (self-consistency) captures most debate gains at equal compute.

Tradeoffs to volunteer

  1. Cost — multi-agent multiplies tokens (workers × calls, debaters × rounds). Only for tasks valuable enough.
  2. Context fragmentation (Cognition, "Don't Build Multi-Agents") — actions carry implicit decisions; parallel writers make conflicting choices. Later principle: writes single-threaded, extra agents contribute intelligence, not actions.
  3. Vague assignments → duplicated or misdirected work. Give objective, output format, tool/source guidance, boundaries.
  4. Handoff pathologies — ping-pong loops (cap hops), lost context in summaries, no global view.
  5. Debate echo chambers — same-model debaters share blind spots; make them different (model, tools, evidence) or give the judge a verifier.
  6. Synchronous bottleneck — orchestrator waits for slowest worker; async adds coordination complexity.
  7. Observability — shared run ID, every assignment/result as a span; limits on subagents, hops, rounds.

5 interview questions

Q1. When would you choose a multi-agent architecture over a single agent? Only when the task is breadth-first and parallelizable (research, due diligence across many sources) and valuable enough to justify ~15× chat tokens. First try one agent with good context engineering and a lean tool set. If I split, I use orchestrator-worker, give workers detailed assignments and clean contexts, and have them return compressed summaries.

Q2. Handoff vs sub-agent (agent-as-tool) — what's the difference? Both are usually tool calls. A sub-agent returns its result to the parent, which stays in control and synthesizes. A handoff transfers control: the receiving agent owns the user conversation, usually with the prior history (full or filtered). Handoffs fit sequential conversational flows like support triage; sub-agents fit decomposition with one synthesis point.

Q3. Would you use multi-agent debate to improve accuracy? Not by default. At equal compute, majority voting over independent samples captures most of debate's gains, and same-model debaters can converge on shared mistakes. Debate or a critic helps when the critic has something the generator lacks — a different model, a verifier (tests, DB lookups), or grounded sources.

Q4. What's the most common way multi-agent systems fail in production? Design, not model quality: vague role specs, inter-agent misalignment, and missing verification (MAST's three buckets). Concretely, parallel agents making conflicting implicit decisions. Mitigation: share context/plans, keep writes single-threaded in one agent, and add an explicit verification step.

Q5. How do you make a multi-agent system observable and bounded? Distributed tracing with one run ID — orchestrator as root span, each worker/handoff as child spans with inputs, outputs, tokens, latency. Explicit limits: max subagents, max handoff hops, max debate rounds, token budget per run. Evaluate both per-agent and end-to-end.

The orchestrator writes detailed assignments, workers start with clean contexts, work in parallel, and send compressed summaries back up. Best for breadth-first research. Costs roughly fifteen times chat tokens. Teach it effort scaling, or it spawns fifty workers for a simple question. Bottom right, the service counters. Control moves sideways; the agent at the current counter owns the user conversation. Great for support flows. Decide what history crosses the counter, cap the hops, and accept that nobody has the global view. Bottom left, the round table and the judge's chair. Agents propose, critique, revise; a judge decides. Beat majority voting at equal compute before you believe it's helping, and make the debaters genuinely different. Across the whole floor: context is the reason to split, cost is the price, and the golden rule is that writes stay single-threaded at the raised desk while the other desks contribute intelligence.
