Track 5 · Agentic AI + MCP · Episode 1

What an Agent Is: The Loop, ReAct, Function Calling Internals

19 min listen · Strip away the hype and an agent is a stateless model in a sealed room, a runner looping outside it, and a row of tools the model can only request, never touch. This episode builds that picture and walks the tool-calling contract, the ReAct pattern, and the costs that compound with every lap.

Facts verified: 2026-09-25

One-sentence thesis

An agent is a stateless LLM in a loop with tools: each turn the model reads the full context and emits either a final answer or a structured tool call, and your harness (not the model) validates, executes, appends the result, and decides when to stop — "the model proposes; the runner disposes."

The mental image: the sealed room and the runner

  • Sealed room (center) = the model. No memory between calls, no ability to act.
  • Left slot (in) = the scroll: system prompt → tool card (all tool definitions) → full conversation + prior tool results. Re-read top to bottom every lap.
  • Right slot (out) = one sheet per lap: a final answer or an order slip (tool name + JSON args + call ID).
  • Runner (circling path) = your loop code: validate slip → execute in the right workshop → append result tagged with the same ID → push scroll back in.
  • Workshops (bottom row) = tools (DB, search, email…). Several slips at once = parallel tool calls.
  • Counter + clock (above) = stop conditions: iteration cap, spend/time budget, human approval gates.

Minimal loop (Anthropic Messages API, Python)

import anthropic
client = anthropic.Anthropic()

tools = [{
    "name": "get_shipment_status",
    "description": "Return shipment status for ONE order number. Use only after you have an order number.",
    "input_schema": {
        "type": "object",
        "properties": {"order_id": {"type": "string"}},
        "required": ["order_id"],
    },
}]

messages = [{"role": "user", "content": "Has order 456 shipped?"}]
MAX_LAPS = 15

for lap in range(MAX_LAPS):
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=2048,
                                  tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break                      # end_turn / max_tokens / refusal / etc.
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            out = run_tool_safely(block.name, block.input)   # validate + authorize + execute
            results.append({"type": "tool_result",
                            "tool_use_id": block.id,          # ties result to the slip
                            "content": out})
    messages.append({"role": "user", "content": results})
else:
    raise RuntimeError("iteration cap hit")

OpenAI equivalent: tools with "strict": true (every property required, additionalProperties: false, optional fields as null unions); the model returns function-call items with a call_id; you return function_call_output items with the same call_id.

Numbers to remember

  • Reliability compounds: 0.95^20 ≈ 0.36 → a 20-step chain of 95%-reliable steps succeeds about a third of the time.
  • Cost compounds: 8k-token prefix + 2k tokens/lap → lap 20 context = 48k; cumulative input ≈ 580k tokens. Roughly quadratic in laps.
  • Tool card: ~200–300 tokens per detailed tool; 50 tools ≈ 10–15k tokens per call.
  • Prompt-cache reads bill at a fraction of base input (≈10% on Anthropic) — keep the prefix stable.
  • Each lap = one model call (≈1–10 s) + tool time.
  • Typical iteration caps: 10–50 laps depending on task.

Pitfalls to volunteer

  1. Runaway loops — no cap, no repeated-failure detection, opaque tool errors ("error 42") → hours of retries. Fix: caps, budgets, and model-readable errors ("table not found; available: A, B, C").
  2. Prompt injection via tool results — tool output lands on the scroll with the same authority as instructions. Fix in the runner: least privilege, allowlists, approval on destructive/outbound actions, avoid combining private data + untrusted content + external send in one agent.
  3. Tool-card bloat — too many / vaguely described tools → wrong picks. Fix: precise descriptions, tool search, fewer broader tools.
  4. Using an agent where a workflow would do — pay latency, cost, and nondeterminism for no benefit.

5 interview questions

Q1. What is an agent, precisely? An LLM in a loop with tools. The model is stateless; each turn it reads the whole context and emits a final answer or a structured tool call. The harness validates, executes, appends the result tagged with the call ID, and loops until an answer or a stop condition (iteration cap, budget, human gate).

Q2. How does function calling work under the hood? Tool definitions (name, description, JSON Schema) are rendered into the prompt — costing tokens each call and steering selection via descriptions. The model is trained to emit a structured call block; the API halts and returns it with a tool-use stop reason. Strict mode constrains decoding to the schema. Results return tagged by ID, which enables parallel calls.

Q3. What does ReAct add, and is it still relevant? ReAct interleaves a reasoning "thought" before each action and reads the observation after, so each step is grounded in fresh evidence and the stateless model leaves itself notes. The pattern is everywhere; the original regex-parsed text template has been replaced by native tool calls plus model-internal (often interleaved) reasoning.

Q4. Why does agent cost grow faster than linearly? Every lap re-sends the entire growing context, so cumulative input tokens grow roughly quadratically with laps. Mitigate with prompt caching of the stable prefix, trimming/summarizing large tool results, fewer laps (parallel calls), and smaller models for routing steps.

Q5. When would you NOT build an agent? When the steps are known in advance. A fixed workflow (code calls the model at predetermined steps) is cheaper, lower-latency, deterministic in structure, and easier to test and audit. Use an agent only when the path depends on what is discovered along the way.

A fixed workflow, where your code calls the model at each predetermined step, is cheaper, faster, easier to test, and easier to explain to an auditor. Agents earn their cost when the path genuinely depends on what you discover along the way. A good rule: start with the simplest thing — a single call, then a fixed workflow — and only hand the steering wheel to the model when the task demands it. [PAUSE 1s] ## The interview angle Three questions this episode prepares you for. First: "What is an agent?" A strong answer sounds like: "An L L M in a loop with tools. The model is stateless; each turn it reads the full context — instructions, tool definitions, conversation, prior tool results — and emits either a final answer or a structured tool call. My code validates and executes the call, appends the result tagged with the call I D, and loops, until the model answers or a stop condition fires: iteration cap, budget, or a human gate. The model decides; the harness acts." Second: "How does function calling actually work?" Strong answer: "Tool definitions — name, description, JSON schema — are rendered into the prompt, so they cost tokens every call and their descriptions steer selection. The model is trained to emit a structured tool-call block; the A P I stops generation and returns it with a stop reason indicating tool use. Strict mode constrains decoding so arguments always match the schema, but that guarantees shape, not correctness. Results go back tagged with the call I D, which is also what enables parallel calls." Third: "What goes wrong with agents in production, and how do you control it?" Strong answer: "Compounding error across steps, quadratic token cost as context grows, latency stacking, runaway loops, and prompt injection through tool results. Controls: iteration and spend caps, repeated-failure detection, informative tool errors, prompt caching on the stable prefix, trimming large tool outputs, least-privilege tools with human approval on side effects — and using a fixed workflow instead of an agent when the path is known."
