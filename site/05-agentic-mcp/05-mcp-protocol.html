MCP: Protocol, Host/Client/Server, Tools/Resources/Prompts, Transports

17 min listen · The Model Context Protocol as of its 2026-07-28 revision: host, clients and servers drawn as one hub-and-spoke picture, the three server primitives and who controls each, the two transports, and why the protocol just went stateless.

Facts verified: 2026-09-25 (against spec revision 2026-07-28, the current "latest")

One-sentence thesis

MCP turns the M×N integration problem into M+N: a host creates one client per server; servers expose tools (model-controlled), resources (application-controlled) and prompts (user-controlled) over JSON-RPC 2.0 via stdio or Streamable HTTP — and as of 2026-07-28 the protocol is stateless (no initialize handshake, no sessions).

The mental image: the hub and its spokes

  • Big circle in the center = host (the AI app: chat, IDE, agent service) — holds model, conversation, user; only component that sees everything.
  • Sockets around the rim = clients, one per server.
  • Cabinets outside = servers; no lines between cabinets (isolation).
  • Three drawers: right = tools (model's hand), left = resources (application's hand), top = prompts (user's hand).
  • Short copper cables below = stdio (local child process). Long network lines right = Streamable HTTP.

The three server primitives (+ client-side features)

Primitive Controlled by Methods Example
Tools Model tools/list, tools/call create_ticket, run_query
Resources Application resources/list, resources/read, resources/templates/list, subscribe file:///…/config.json, table schema
Prompts User prompts/list, prompts/get slash command "/summarize-incident"

Client features a server can request (via MRTR in 2026-07-28): - Elicitation — elicitation/create; form mode (flat JSON-schema form) and URL mode (out-of-band web page for sensitive flows: credentials, payments). Servers MUST NOT request sensitive info via form mode. - Sampling (server asks host's LLM to generate) — Deprecated 2026-07-28 → call LLM provider APIs directly. - Roots (host tells server allowed directories) — Deprecated → pass paths as tool params/config. - Logging — Deprecated → stderr for stdio, OpenTelemetry for observability. (Deprecated = still works; earliest removal in first revision on/after 2027-07-28.)

Tool definition shape:

{
  "name": "create_ticket",
  "description": "Create a support ticket in the given project.",
  "inputSchema": {
    "type": "object",
    "properties": { "project": {"type": "string"}, "title": {"type": "string"} },

  },
  "outputSchema": { "type": "object", "properties": { "ticket_id": {"type": "string"} } },
  "annotations": { "destructiveHint": false }

Annotations are hints — clients MUST treat them as untrusted unless the server is trusted.

Transports

stdio Streamable HTTP
Where Local child process launched by host Remote/independent server process
Framing Newline-delimited JSON-RPC on stdin/stdout Each message = HTTP POST to a single MCP endpoint (e.g. /mcp)
Response stdout application/json or per-request SSE stream (progress notifications then final response)
Auth No OAuth — credentials from environment OAuth 2.1 (next episode)
Security Process isolation Validate Origin (DNS rebinding), bind localhost when local

Legacy HTTP+SSE (2024-11-05, two endpoints) is Deprecated — replaced by Streamable HTTP (introduced 2025-03-26).

initialize / notifications/initialized handshake Removed; optional server/discover

State you still need → server mints an explicit handle (cart ID, workflow ID) returned in a tool result; model passes it back as an argument. Never treat possession of a handle as authentication; bind handles server-side to the authenticated user.

Tradeoffs / pitfalls

  1. Context bloat — all tool definitions from all servers land in context; accuracy drops as the menu grows. Anthropic's "code execution with MCP" cut one workflow from ~150k to ~2k tokens (~98.7%).
  2. Name collisions — tool names unique only per server; host must prefix/disambiguate.
  3. Version skew — mixed fleets of 2025-era (session) and 2026-07-28 (stateless) servers during migration.
  4. Supply chain — Sept 2025 malicious postmark-mcp npm package: after 15 clean versions, v1.0.16 added one line BCC'ing every email to an attacker (~1,500 weekly downloads).

5 interview questions

Q1. What is MCP and what problem does it solve? An open protocol (Linux Foundation / AAIF since Dec 2025) standardizing how AI applications connect to tools and data. It collapses M apps × N integrations into M clients + N servers. Hosts create one client per server; servers expose tools, resources and prompts over JSON-RPC.

Q2. Tools vs resources vs prompts? Split by who controls them: tools are model-controlled executable functions; resources are application-controlled data addressed by URI that the host decides to attach; prompts are user-controlled templates invoked like slash commands.

Q3. Why one client per server? Isolation: a server sees only its own traffic, never the full conversation or other servers. The host is the only component with the full picture and enforces consent and policy.

Q4. Compare stdio and Streamable HTTP. stdio: host spawns a local child process, newline-delimited JSON-RPC over stdin/stdout, credentials from environment, no OAuth. Streamable HTTP: one endpoint, each message a POST, response as JSON or a per-request SSE stream; OAuth 2.1 for auth; validate Origin; replaced the deprecated two-endpoint HTTP+SSE transport.

Q5. What changed in the 2026-07-28 revision and why does it matter for deployment? MCP went stateless: no initialize handshake, no Mcp-Session-Id; each request carries version and capabilities in _meta. Server-to-client asks use MRTR (return input_required, client retries). So remote servers scale behind plain round-robin load balancers without sticky sessions or shared session stores; gateways can route on Mcp-Method/Mcp-Name. Sampling, roots and logging were deprecated.
