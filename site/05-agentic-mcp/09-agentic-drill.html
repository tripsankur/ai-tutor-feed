DRILL: Agents + MCP Rapid-Fire

10 min listen · Fifteen rapid-fire interview questions across the whole agentic track — the agent loop and function calling, planning and reasoning, memory, multi-agent patterns, the Model Context Protocol and its security, frameworks, and evals and guardrails. Answer aloud in the pause, then compare.

Facts verified: 2026-09-25

One-sentence thesis

The whole track in one line: an agent is a stateless model in a harness loop; planning, memory, and multi-agent patterns shape what goes into each turn; MCP standardises how tool calls reach tools you don't own; and evals, guardrails, and human gates are what make any of it safe to ship.

9 Transports + 2026 change? stdio (local) and Streamable HTTP (remote); HTTP+SSE formally deprecated. 2026-07-28 spec: stateless (no initialize handshake, no Mcp-Session-Id), per-request _meta, multi round-trip requests (input_required + retry), sampling/roots/logging deprecated
10 MCP vs function calling? Function calling = model's decision format; MCP = delivery/discovery protocol to tools you don't own; complementary; N×M → N+M; portable tools

15 Guardrails + humans? Input (incl. tool results), tool layer (least privilege, arg validation, sandbox, budgets — most important), output (schema, PII, grounding); humans only on irreversible actions via checkpoint + interrupt, raw args, deny-by-default timeout

This is the Track Five drill — fifteen questions across agents and the Model Context Protocol, from the basic loop all the way to evals and guardrails. Same format as always: I ask, you answer out loud in the pause, then I give you a strong answer to compare. Ordered roughly as the track ran. Ready. [PAUSE 2s] Question one. What is an agent, mechanically? [PAUSE 6s] Strong answer: an L L M in a loop with tools. Each turn, the stateless model reads the full context — instructions, tool definitions, conversation, and prior tool results — and returns either a final answer or a structured tool call. The harness validates and executes the call, appends the result tagged with the call I D, and loops until the model answers or a stop condition fires, like an iteration cap, a budget, or a human gate. The model proposes; the runner disposes. [PAUSE 2s] Question two. How does function calling actually work under the hood, and what does strict mode guarantee? [PAUSE 6s] Strong answer: tool names, descriptions, and JSON schemas are rendered into the prompt, so they cost tokens on every call and their descriptions steer tool selection. The model is trained to emit a structured tool-call block, generation stops with a tool-use stop reason, and your code runs the tool. Strict mode constrains decoding so arguments always match the schema — it guarantees shape, not correctness. [PAUSE 2s] Question three. What is Re-Act, and is it still relevant with reasoning models? [PAUSE 6s] Strong answer: Re-Act interleaves reasoning and acting — the model writes a thought, takes an action, reads the observation, and repeats, so each step is grounded in real tool results. Reasoning models moved much of the thinking into a private, effort-controlled reasoning phase that can interleave with tool calls, so you rarely prompt for explicit thoughts anymore. The loop itself is unchanged, and you must pass the reasoning blocks back between tool calls or the model loses its thread. [PAUSE 2s] Question four. Plan-and-execute versus reflection — when do you use each? [PAUSE 6s] Strong answer: plan-and-execute has a planner produce a step list up front, which is cheap to execute, parallelisable, and easy for a human to approve — but a plan is a guess made with the least information, so you need replanning on errors and surprises. Reflection is generate, critique, revise; it only really helps when the critic has external signal like tests, validators, or evidence. Cap the rounds either way, or you just burn tokens. [PAUSE 2s] Question five. How do you design agent memory? [PAUSE 6s] Strong answer: short-term memory is the thread's working context — the message history, checkpointed per thread so a run can resume. As it grows, you trim or summarise older turns, keeping the stable prefix cacheable. Long-term memory lives outside the context in a store — the basement archive with three cabinets: facts about the user, past episodes, learned procedures — retrieved selectively by namespace and relevance. The risks are stale or poisoned memories, so writes should be deliberate, scoped per user, and auditable. [PAUSE 2s] Question six. Name three multi-agent patterns and when each fits. [PAUSE 6s] Strong answer: orchestrator-worker, where a lead agent delegates to workers with clean contexts that run in parallel and return compressed summaries — ideal for breadth-first research. Handoffs, where control moves sideways and the current agent owns the conversation — good for support flows with specialists. Debate, where agents propose and critique and a judge decides — only worth it if it beats simple majority voting at equal compute. [PAUSE 2s] Question seven. What does multi-agent cost, and what's the golden rule? [PAUSE 6s] Strong answer: roughly four times the tokens of chat for a single agent, and around fifteen times for a multi-agent system, based on Anthropic's research-system numbers. So it's only justified when subtasks are genuinely independent and parallel. The golden rule is to keep writes single-threaded — workers contribute intelligence, but one agent makes the changes, so you don't get conflicting actions. [PAUSE 2s] Question eight. Describe M C P's architecture and its three server primitives. [PAUSE 6s] Strong answer: a host application holds the model, the user, and the conversation; it creates one client per server, and each server exposes capabilities. Tools are model-controlled actions with a JSON schema. Resources are application-controlled data addressed by U R I. Prompts are user-controlled templates, typically surfaced as slash commands. Servers can also ask the user for input through elicitation. [PAUSE 2s] Question nine. What are M C P's transports, and what changed in the July twenty twenty-six revision? [PAUSE 6s] Strong answer: two standard transports — standard input and output for a local child process, and Streamable H T T P for remote servers, with the old H T T P plus server-sent-events transport formally deprecated. The twenty twenty-six July revision made the protocol stateless: no initialize handshake, no session I D header, every request carries its own version and capabilities, so any server replica behind a plain load balancer can serve it. Servers now ask for input by returning an "input required" result that the client retries with answers, and sampling, roots, and logging are deprecated. [PAUSE 2s] Question ten. M C P versus plain function calling — what's the difference? [PAUSE 6s] Strong answer: function calling is how the model decides — it reads a menu of tools and writes an order, but never executes anything. M C P is how that order gets delivered to tools you don't own: a standard protocol for discovering tools from servers, translating them into the model's menu, and invoking them. They're complementary layers — M C P turns an N-times-M integration problem into N-plus-M, and makes tools portable across hosts and frameworks. [PAUSE 2s] Question eleven. How does authorization work for a remote M C P server, and what's token passthrough? [PAUSE 6s] Strong answer: O Auth two point one. The server answers four oh one pointing to its protected resource metadata, which names the authorization server; the client identifies itself, often with a client I D metadata document, uses pixie, the P K C E extension, and a resource indicator, and gets a token bound to that one server, with scopes starting small and stepping up. Token passthrough — forwarding the client's token to an upstream A P I — is forbidden; the server must get its own upstream token, otherwise you create a confused deputy. [PAUSE 2s] Question twelve. What's the lethal trifecta, and how do you break it? [PAUSE 6s] Strong answer: an agent that has access to private data, is exposed to untrusted content, and can communicate externally can be prompt-injected into exfiltrating that data. Tool descriptions and tool results are untrusted input, so you can't rely on the model to resist. You remove one leg per agent — no external send, or no untrusted content, or no sensitive data — and add least privilege plus human approval on outbound actions. [PAUSE 2s] Question thirteen. How would you choose between Lang Graph, Crew A I, Microsoft Agent Framework, and the Claude Agent S D K? [PAUSE 6s] Strong answer: decide who owns the control flow and whether the work is really a team. Regulated, approval-gated, long-running workflows want a graph with checkpointing — Lang Graph, or Microsoft Agent Framework in Azure and dot net shops, which succeeded AutoGen after it went into maintenance mode. Crew A I is fastest for role-based teams, with Flows as the production backbone; the Claude Agent S D K suits open-ended tasks, fenced with hooks and permission rules. Whatever you pick, put tools behind M C P so the framework stays replaceable. [PAUSE 2s] Question fourteen. How do you evaluate an agent, and what's the difference between pass at k and pass to the k? [PAUSE 6s] Strong answer: grade four levels — the outcome by checking end state, the trajectory by matching tool-call sequences, individual steps like tool choice and arguments, and efficiency and safety — with code graders first, L L M judges for open-ended quality, and humans to calibrate the judges. Pass at k means any of k attempts succeeded; pass to the k means all k did. For an unattended agent, pass to the k is the honest number — ninety percent per attempt is only about forty-three percent across eight in a row. [PAUSE 2s] Question fifteen. Where do guardrails and humans go in an agent system? [PAUSE 6s] Strong answer: in layers. Input checks on user text and on tool results, because indirect prompt injection is the top agentic risk; tool-layer controls — least-privilege credentials, argument validation in code, sandboxing, and step and spend budgets — which matter most; and output checks for schema, personal data, and grounding. Humans approve only irreversible or external actions, implemented as a checkpoint plus interrupt so the pause can last hours, with the raw arguments shown and a deny-by-default timeout.
