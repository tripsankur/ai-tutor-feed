Agent Evals, Guardrails, Human-in-the-Loop

16 min listen · How you prove an agent works and keep it from doing damage: outcome, trajectory, and step-level evals with code, model, and human graders; pass-at-k versus pass-to-the-k; layered input, tool, and output guardrails; and human approval gates built on checkpoints and interrupts.

Facts verified: 2026-09-25

One-sentence thesis

Instructions are not controls: an agent is trusted only when evals prove it works (outcome, trajectory, steps, efficiency — over multiple trials), layered guardrails contain it (input, tool, output — deterministic wherever possible), and humans approve only the irreversible actions, via durable checkpoint-and-resume.

The mental image: the arena, the gates, the balcony

  • Arena (centre) = the agent loop.
  • Entrance gate (left) = input guardrails — also applied to tool results flowing back in (indirect prompt injection).
  • Exit gate (right) = output guardrails.
  • Turnstiles (below) = tool guardrails: least privilege, argument validation, sandbox, budgets. The most important layer.
  • Balcony (above) = human approval, wired only to irreversible turnstiles.
  • Practice range (far left) = offline evals in reset replica environments.
  • Watchtower (far right) = online evals/monitoring on production traces.
  • Return path (across the top) = production failures become new eval scenarios (data flywheel).

What to grade (four levels)

Level Question Typical grader
Outcome Did the world end up in the right state (refund row exists, tests pass, query rows match)? Code (preferred)
Trajectory Right tool calls, in an acceptable order? Code: trajectory match (strict / unordered / subset / superset) or LLM judge
Step Right tool chosen? Arguments correct? Code
Efficiency & safety Steps, tokens, latency, $; any policy violation attempted? Code + LLM judge

Graders: code-based (deterministic, cheap, never drift) → model-based (LLM judge, rubric with pass/fail criteria, justification before verdict, randomised order, different model family) → human (calibration: measure judge–human agreement).

Compounding error: 0.95 per step over 20 steps = 0.95^20 ≈ 36% clean runs.

pass@k vs pass^k: - pass@k = at least one of k attempts succeeds (fine when a verifier picks the winner). - pass^k = all k attempts succeed (tau-bench; right metric for unattended actions). With p = 0.9 per attempt, pass^8 = 0.9^8 ≈ 43%.

Code: trajectory eval (agentevals)

from agentevals.trajectory.match import create_trajectory_match_evaluator

evaluator = create_trajectory_match_evaluator(
    trajectory_match_mode="superset",   # strict | unordered | subset | superset
)
result = evaluator(outputs=actual_messages, reference_outputs=reference_messages)
# -> {"key": "trajectory_superset_match", "score": True/False, ...}

Code: human approval with LangGraph

from langgraph.types import interrupt, Command

def refund_node(state):
    decision = interrupt({                  # pauses; state checkpointed
        "tool": "issue_refund",
        "args": {"order_id": state["order_id"], "amount": state["amount"]},  # raw args, not a summary
    })
    if decision["action"] == "approve":
        issue_refund(**decision.get("edited_args", {"order_id": state["order_id"], "amount": state["amount"]}))
    return {"refund_decision": decision["action"]}

# graph compiled with a durable checkpointer; later, possibly on another server:
app.invoke(Command(resume={"action": "approve"}), {"configurable": {"thread_id": "t-42"}})

Tradeoffs to volunteer

  1. Judges cost roughly an extra model call per scored trace → sample in production.
  2. Model-based gates add tens–hundreds of ms → run in parallel; prefer deterministic checks.
  3. Every gate has false positives → evaluate the gates too.
  4. Trajectory strictness: strict match catches policy violations but flags harmless reorderings; pick mode per scenario.
  5. HITL adds latency and staffing; durable checkpoints make multi-hour pauses cheap but UX still suffers.

5 interview questions

Q1. How do you evaluate an agent (not a chatbot)? Four levels: outcome (end-state checks), trajectory (tool-call match modes), step (tool choice, argument accuracy), efficiency/safety (steps, tokens, violations). Code graders first, LLM judges for open-ended quality, humans to calibrate. Multiple trials in reset environments; report pass^k for unattended actions; run in CI as a release gate; feed production failures back.

Q2. pass@k vs pass^k — which and why? pass@k = any of k succeeds; right when a verifier/human selects among attempts. pass^k = all k succeed; right for agents acting unattended. 90% per attempt → pass^8 ≈ 43%, which is the realistic reliability for a customer who gets one shot.

Q3. How do you defend against prompt injection in a tool-using agent? Assume the model can be hijacked and contain it: scan tool outputs as well as inputs, least-privilege credentials, argument validation in code, sandboxed execution with no default egress, break the lethal trifecta, budgets on steps/spend, human approval with raw arguments for irreversible actions.

Q4. How do you implement human-in-the-loop without holding resources for hours? Checkpoint the full state to durable storage and stop (LangGraph interrupt + checkpointer + thread_id; Claude Agent SDK ask rule → canUseTool). Resume from the checkpoint with the human's decision (approve / reject / edit / respond), possibly on another worker. Timeout defaults to deny; every decision audited.

Q5. How do you keep LLM-as-judge honest? Concrete pass/fail rubric, justification before verdict, randomised order, different model family than the agent, and a permanent human-graded sample to track agreement; if agreement drops, recalibrate before trusting scores.
