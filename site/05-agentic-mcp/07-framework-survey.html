Framework Survey: LangGraph vs CrewAI vs AutoGen vs Claude Agent SDK

19 min listen · Four agent frameworks placed on one map: who owns the control flow — you or the model — and whether the unit of work is one agent or a team. Covers LangGraph 1.x, CrewAI Crews and Flows, AutoGen's move to maintenance mode and its successor Microsoft Agent Framework, and the Claude Agent SDK.

Facts verified: 2026-09-25

One-sentence thesis

Every agent framework is a position on one tradeoff — who owns the control flow (you vs the model) — plus a second choice of one agent vs a team; in 2026 they are all converging on the same production recipe: a durable, deterministic backbone you own, with bounded pockets of model autonomy.

The mental image: the map with four pins

  • Horizontal axis (control): far left = you wrote the control flow (railway: model fills in steps, can't invent new ones). Far right = the model runs its own loop (off-road vehicle: you steer via toolbox + prohibitions).
  • Vertical split (unit of work): below = one agent; above = a team of agents.
  • Pins: LangGraph on the left (on the line — single or multi). CrewAI top half (sequential crew = top-left, hierarchical = top-right; Flows pull it left). AutoGen top-right (conversation-as-computation) → successor Microsoft Agent Framework slid left (graph workflows + checkpoints). Claude Agent SDK bottom-right (model-driven loop, rich harness, hooks/permissions as the fence).
  • Trend arrow: everything converges on the middle-left.

Snippets

LangGraph — state, nodes, conditional edge, checkpointer, interrupt:

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver   # Postgres saver in prod
from langgraph.types import interrupt, Command

class S(TypedDict):
    order_id: str
    eligible: bool
    approved: bool

def check_policy(s: S):  return {"eligible": True}           # plain code, not the LLM
def approve(s: S):       return {"approved": interrupt({"refund": s["order_id"]})}
def refund(s: S):        return {}

g = StateGraph(S)
g.add_node("check_policy", check_policy); g.add_node("approve", approve); g.add_node("refund", refund)
g.add_edge(START, "check_policy")
g.add_conditional_edges("check_policy", lambda s: "approve" if s["eligible"] else END)
g.add_conditional_edges("approve", lambda s: "refund" if s["approved"] else END)
g.add_edge("refund", END)
app = g.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "t-42"}}
app.invoke({"order_id": "A1"}, cfg)          # pauses at interrupt, state checkpointed
app.invoke(Command(resume=True), cfg)        # same thread_id -> resumes

Tradeoffs to volunteer

  1. Control vs adaptability — left side is auditable/testable; right side adapts but step count and cost vary run to run.
  2. Token cost — ≈4× (agent) / ≈15× (multi-agent) vs chat. Justify multi-agent with parallelism.
  3. Durable state cost — per-step writes (ms–tens of ms), storage grows with thread length; keep state lean, store blobs by reference, expire threads.
  4. Framework churn — AutoGen rewrite → fork → maintenance mode. Keep tools as MCP servers, prompts in a registry, policy in plain code; framework = thin orchestration shell.
  5. Observability — LangSmith, OpenAI Agents SDK tracing, OpenTelemetry in MAF, MLflow tracing across most; no trajectory visibility = no evals.

5 interview questions

Q1. Which agent framework would you pick for a new enterprise use case? Decide who owns control flow and whether it's truly multi-agent. Regulated, approval-gated, long-running → graph with checkpointing (LangGraph, or MAF workflows in Azure/.NET shops). Open-ended tasks → model-driven harness (Claude Agent SDK) fenced by hooks/permissions. Multi-agent only for parallel subtasks (~15× tokens). Tools behind MCP, policy in code, so the framework is replaceable.

Q2. What happened to AutoGen? v0.4 was a ground-up async, event-driven rewrite; original creators continued the older line as the community fork AG2; in Oct 2025 Microsoft put AutoGen in maintenance mode and named Microsoft Agent Framework (AutoGen abstractions + Semantic Kernel enterprise features, Python + .NET) the successor, which reached 1.0 in April 2026.

Q3. How does LangGraph achieve human-in-the-loop and crash recovery? A checkpointer saves full state after each super-step under a thread_id. interrupt() raises inside a node, state is saved, the payload goes to the client; Command(resume=value) on the same thread_id continues the node. The same checkpoints let a crashed run resume and let you replay/fork from history.

Q4. How do you keep a model-driven agent (e.g., Claude Agent SDK) safe without a graph? Fence it: allowed/disallowed tools, permission modes, ask rules routed to a canUseTool callback for human approval, PreToolUse hooks that validate arguments and block (e.g., refunds above a threshold), max turns/budgets, sandboxed execution, and subagents with narrower tool sets.

Q5. When is multi-agent worth it? When work splits into independent, parallelizable subtasks that benefit from separate context windows (breadth-first research). Not for tightly coupled sequential work (most coding), where agents just pass a baton and multiply tokens. Always cap turns/budgets and prefer a deterministic orchestrator over open-ended negotiation.

Left-side frameworks give you determinism, auditability, and testability, and they cost you verbosity and brittleness when reality doesn't match the diagram. Right-side frameworks adapt to messy tasks and cost you predictability — in one run the agent might take five steps, in the next, thirty. If your compliance team needs to explain every decision, you want to be left of centre. Second: token cost scales with agents and turns. Remember the rough multipliers — around four times chat for a single agent, around fifteen for multi-agent. A research workflow that costs a few cents as a single prompt can cost dollars as a crew. Multi-agent earns its keep when subtasks are genuinely parallel and independent — breadth-first research is the classic case — and it's wasteful when agents mostly pass a baton in sequence. Third: durable state isn't free. Checkpointing every step to a database adds write latency — typically milliseconds to tens of milliseconds per step against a nearby Postgres — and storage that grows with thread length. Budget for it, and expire old threads. Fourth: framework churn is a first-class risk. The war story from the top of this episode is the pattern: a team welds business logic, prompts, and tool code into framework-specific classes, then the framework rewrites or retires, and the migration becomes a project. The defence is a thin adapter: tools as plain functions or, better, as M C P servers; prompts in a registry; policy in plain code; and the framework only as the orchestration shell. When your tools are M C P servers, they survive any framework change — every framework on this map can consume them. Fifth: observability decides whether you can run it. Lang Smith for Lang Graph, built-in tracing in OpenAI's S D K, OpenTelemetry in Microsoft Agent Framework, hooks and message streams in the Claude Agent S D K, and M L flow tracing can instrument most of them. If you can't see the trajectory, you can't debug it, and you certainly can't evaluate it — which is next episode. [PAUSE 1s] ## The trend: everyone is moving toward the middle-left Now name the trend we've been watching on the map. Crew A I added Flows — code-first, event-driven, persisted. AutoGen's successor added graph workflows with checkpoints. Lang Graph was already there. Even the model-driven harnesses add hooks, permission modes, and approval callbacks that act like gates on a track. Every framework is converging on the same production recipe: a deterministic, durable backbone that you own, with bounded pockets of model autonomy inside it. Anthropic's own guidance on building effective agents says the same in plain words: start with the simplest thing — a workflow — and reach for autonomous agents only where the flexibility pays for itself. [PAUSE 1s] ## Interview angle When they ask, "Which agent framework would you choose?", a weak answer names a favourite. A strong answer sounds like this: "It depends on who should own the control flow and whether the work is really a team. For a regulated workflow with approval gates and long-running steps, I'd use a graph with checkpointing — Lang Graph, or Microsoft Agent Framework workflows in a dot net or Azure-heavy shop — because I need durable state, interrupts, and auditability. For open-ended tasks where the path can't be drawn up front, like coding or investigation, a model-driven harness such as the Claude Agent S D K, with hooks and permission rules as the fence. I'd use multi-agent only when subtasks are parallel, because it's roughly fifteen times the tokens of chat. And whatever I pick, tools live behind M C P and policy lives in plain code, so the framework is replaceable." When they ask, "What happened to AutoGen?", a strong answer: "Microsoft rewrote it as version zero-point-four on an async actor model, a community fork called A G two continued the older line, and in October twenty twenty-five AutoGen went into maintenance mode with Microsoft Agent Framework as the successor — it combines AutoGen's agent abstractions with Semantic Kernel's enterprise features and hit one-point-oh in April twenty twenty-six." When they ask, "How do you stop a multi-agent system from looping?", a strong answer: "Hard ceilings — maximum turns, maximum tool calls, token or dollar budgets — plus explicit termination conditions, and preferably a deterministic orchestrator deciding who works next instead of letting agents negotiate indefinitely."
