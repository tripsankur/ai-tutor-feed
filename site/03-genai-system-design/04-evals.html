Track 3 · GenAI System Design · Episode 4

Evals: LLM-as-Judge, Golden Sets, Regression Gates

19 min listen · How production teams know an LLM change is actually better: golden sets built from real traffic, three kinds of graders including a calibrated LLM judge, honest statistics, and a regression gate that blocks a release before users ever see it.

Facts verified: 2026-09-25

One-sentence thesis

An LLM change is only "better" if a versioned, sliced golden set, graded by layered graders (code → calibrated LLM judge → humans), says so beyond statistical noise — and a CI regression gate enforces that automatically, with production failures fed back into the set.

Golden set rules

  • Start with 50–100 expert-labelled cases; grow to hundreds–thousands.
  • Source from production traffic (thumbs-down, regenerations, escalations), not engineer imagination.
  • Slice by intent, difficulty, segment, language, answer-vs-refuse; gate per slice.
  • Keep a held-out subset you never tune against (prompt overfitting is real).
  • Version the golden set; scores are only comparable on the same version.
  • References can be: ideal answer, required facts, expected tool call, or a rubric.

Grader layers

Grader Good for Cost Watch-outs
Code / deterministic JSON schema, tool name+args, SQL result equivalence, must/must-not contain, latency/tokens ~free, instant, repeatable Brittle to valid paraphrase
LLM judge Faithfulness, relevance, tone, helpfulness cents per run of hundreds Position, verbosity, self-preference bias; rubric vagueness; drift
Human Labelling, calibration, ambiguous cases expensive, slow Inter-rater disagreement — measure it

LLM-as-judge: biases and fixes

Bias Fix
Position (favors first shown) Run pairwise both orders; count only consistent wins
Verbosity (favors longer) Conciseness criterion in rubric; track answer length as a metric
Self-preference (favors own family) Judge from a different model family
Vague 1–10 scales Binary / 3-point scales with each level defined; reasoning before verdict; one judge per criterion
Uncalibrated Label 100–200 cases by a domain expert; measure agreement (and Cohen's kappa); recheck after any judge/app change

Reference point: in the MT-Bench / Chatbot Arena study, strong judges reached >80% agreement with humans — about the human-human agreement rate — while exhibiting position, verbosity and self-enhancement biases.

Example judge (binary faithfulness)

JUDGE_PROMPT = """You are grading an answer for FAITHFULNESS only.
Context:
{context}
Question: {question}
Answer: {answer}

List each factual claim in the answer. For each, say whether the context supports it.
Then output exactly one line: VERDICT: PASS if every claim is supported, else VERDICT: FAIL."""

def judge_faithfulness(llm, case, answer):
    out = llm(JUDGE_PROMPT.format(context=case["context"], question=case["question"], answer=answer))
    return out.strip().splitlines()[-1] == "VERDICT: PASS"

def pairwise(llm_pair_judge, q, a, b):
    """Swap order to cancel position bias; only a consistent win counts."""
    first = llm_pair_judge(q, a, b)    # returns "A" or "B"
    second = llm_pair_judge(q, b, a)
    if first == "A" and second == "B": return "a"
    if first == "B" and second == "A": return "b"
    return "tie"

RAG metric vocabulary (RAGAS)

Metric Question Low score means
Faithfulness Are answer claims supported by retrieved context? Generation problem (hallucination / embellishment)
Response (answer) relevancy Does the answer address the question? Generation / prompt problem
Context precision Are relevant chunks ranked near the top? Ranking / reranker problem
Context recall Was everything needed retrieved? Retrieval / chunking / index problem

Agents

  • Outcome grading (final state correct — checked in code) preferred; trajectory grading for cost and safety.
  • pass@k = at least one success in k tries (capability). pass^k = all k succeed (consistency).
  • 90% single-try success → pass^10 = 0.9^10 ≈ 35%.

The statistics (scoreboard)

  • Standard error of a pass rate p on n cases: sqrt(p(1-p)/n).
  • n=200, p=0.8 → SE ≈ 2.8 pts → 95% CI ≈ ±5.6 pts. A 2-point gain is noise.
  • n=30 slice → CI ≈ ±14–15 pts.
  • 4× cases → ½ interval width.
  • Use paired comparison on identical cases (count flips pass→fail vs fail→pass; McNemar-style) instead of comparing two independent means.
  • Cost: 500 cases × 3 judges × ~2k tokens ≈ 3M tokens → single-digit dollars on a mid-tier judge.

Regression gate (CI)

# illustrative gate config
triggers: [prompt, model_version, retrieval_config, tools, dependencies]
pr_suite: {code_checks: all, judged_sample: 100}      # minutes
nightly_suite: {code_checks: all, judged: all}        # full
rules:
  floors:      {faithfulness: 0.90, refuse_when_should: 1.00}
  no_regress:  {per_slice_max_drop: "outside CI band for slice size"}
  ops_budget:  {p50_latency_ms: "+10%", cost_per_request: "+5%", error_rate: "+0.5pt"}
model: pinned-version   # never a floating alias

Online evaluation

Judge 1–5% of live traffic asynchronously; track implicit signals (thumbs, regenerate, copy, escalation, abandonment); every confirmed failure → new golden case. Use A/B experiments for large changes — offline says "safe to try," online says "users better off."

Pitfalls

  1. Average hides slices — cheaper-model swap: overall 81→80 (pass), non-English slice (25 cases) −20 pts. Fix: per-slice gates + enough cases per high-stakes slice.
  2. Goodhart — optimizing against a length-loving judge produced ever-longer answers. Fix: length metric + conciseness criterion.
  3. Reference leakage in judge prompts; stale golden sets; evaluating against a different retrieval config than production.
  4. Floating model aliases make scores irreproducible.

5 interview questions

Q1. How would you evaluate an LLM application end to end? Golden set from real traffic, sliced, with a held-out portion and versioning. Layered graders: deterministic code checks first; one LLM judge per criterion with binary rubrics, calibrated on ~100–200 human labels; humans for labelling and recalibration. Wire into CI as a regression gate with per-slice thresholds plus latency/cost budgets; judge a sample of production traffic and feed failures back.

Q2. What are the failure modes of LLM-as-judge and how do you mitigate them? Position bias (swap order, count consistent wins), verbosity bias (conciseness criterion, track length), self-preference (different model family), vague scales (binary/3-point, reasoning first, one criterion per judge). Above all, measure judge–human agreement before trusting it and recheck after changes.

Q3. Your candidate prompt scores 82% vs 80% on 200 cases. Ship? The 95% CI is ~±5.6 points, so that difference is noise. Do a paired comparison of flipped cases, verify no critical slice regressed, check latency/cost. Ship if it's quality-neutral and cheaper or better on a slice that matters — not because of the 2 points.

Q4. How do you evaluate an agent differently from a single LLM call? Grade the outcome (final state, checked in code) first, trajectory second (redundant calls, unsafe tools, cost). Measure consistency with pass^k, not just pass@k: 90% single-try success is only ~35% for 10/10.

Q5. How do RAG metrics help you diagnose a bad answer? Split into retrieval and generation: low context recall/precision → retrieval, chunking or ranking problem; good context but low faithfulness → the model is embellishing or ignoring evidence; low answer relevancy → prompt/generation problem. Different fixes, often different owners.

One team noticed their judge rewarded thoroughness, tuned their prompt against it for weeks, and watched scores climb steadily while answers got longer and longer. Users hated it. Answer length had quietly become the thing being optimized. A length metric on the scoreboard and a conciseness criterion in the rubric would have caught it in the first week. Here's a longer war story, the kind worth telling in an interview. A large retail platform switched its assistant to a newer, cheaper model to cut serving cost by about forty percent. The overall eval score moved from eighty-one to eighty — inside the noise band, gate passed, change shipped. Two weeks later, complaints spiked from customers writing in a second language. When the team finally sliced the golden set, the non-English drawer had dropped nearly twenty points. It had only twenty-five cases, so it barely moved the average. The fixes were exactly the pieces of the bench we've been walking: per-slice gates, not just an average; enough cases in each high-stakes drawer to see a real drop; and a return pipe that fed the complaint conversations straight back into the cabinet. [PAUSE 1s] ## Interview angle Three ways this comes up. First: "How would you evaluate an L L M application?" A strong answer sounds like this. "I'd build a golden set from real production traffic, sliced by intent and difficulty, with a held-out portion. I'd grade in layers: deterministic code checks first for format, tool calls, and required facts; then an L L M judge per criterion with a binary or three-point rubric, calibrated against a hundred or so human labels before I trust it; and humans for labelling and periodic recalibration. Then I'd wire it into C I as a regression gate with per-slice thresholds, plus online judging on a sample of live traffic feeding failures back into the set." Second: "What are the problems with L L M as a judge?" Strong answer: position bias, fix it by swapping order; verbosity bias, fix it with a conciseness criterion and a length metric; self-preference, fix it with a judge from a different model family; and vague rubrics, fix them with narrow, binary criteria and reasoning before the verdict. Then add the one that shows maturity: none of that matters unless you've measured judge-human agreement, because an uncalibrated judge is just a confident random number generator. Third: "Your new prompt scores two points higher. Do you ship it?" Strong answer: "Depends on the noise. On two hundred cases at eighty percent, the confidence interval is about plus or minus five points, so two points is noise. I'd look at a paired comparison on the same cases — which ones flipped from fail to pass and which flipped the other way — check that no critical slice regressed, and check latency and cost. If it's genuinely neutral on quality but cheaper, that can still be a reason to ship." [PAUSE 2s] ## Sixty-second recap Let's walk the bench one last time. On the left, the filing cabinet — the golden set — built from real production traffic, organized into drawers by slice, with a held-out drawer you never tune against, and versioned. In the middle, the machine under test, versioned as one unit with a pinned model. On the right, three graders: the ruler first, deterministic code checks, fast and free; then the L L M judge, one narrow criterion at a time, order swapped for pairwise comparisons, a different model family, calibrated against human labels; then the human expert, spent on labelling and calibration. Above, the scoreboard, where you remember that two hundred cases gives you roughly plus or minus five points, so you use paired comparisons and watch every drawer, not just the average. Below, the trapdoor — the regression gate in C I, with absolute floors, per-slice no-regression rules, and latency and cost budgets. And along the floor, the return pipe, carrying production failures back into the cabinet, so no failure ships twice.
