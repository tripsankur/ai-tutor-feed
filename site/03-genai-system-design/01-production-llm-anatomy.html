Anatomy of a Production LLM System

19 min listen · The corridor mental model of a production LLM system: front door, gateway, input guards, orchestrator, context shelves above, model basement below, output guards, and the glass floor of tracing underneath, with the latency budget, costs, and failure modes of each station.

Facts verified: 2026-09-25

One-sentence thesis

The model call is roughly a tenth of a production LLM system; the rest is the request path around it (gateway, guards, orchestrator, context, routing, tracing) plus an improvement loop that turns production traffic into regression gates.

The mental image: the corridor

  • Corridor, left → right: front door (client, streaming) → gateway (security desk) → input guard → orchestrator (big middle room) → output guard → exit.
  • Shelves above the orchestrator: retrieval (left), memory (middle), tools / MCP (right).
  • Basement below: a row of models small → large, with a router at the foot of the stairs.
  • Glass floor underneath: tracing — every step a span.
  • Return pipe: production traces + feedback loop back to an eval lab → golden set → regression gate on every change.

Worked latency / cost budget (interactive assistant)

Station Typical cost in time Notes
Gateway ~single-digit ms auth, quota lookup
Input guard tens of ms small classifier; run in parallel with retrieval when possible
Retrieval + rerank ~100–300 ms embed query, hybrid search, rerank top-50 → top-5
Tool call 100–500 ms+ depends on backend health
Model prefill (TTFT) few hundred ms – ~1 s for ~4k-token prompt grows with input length
Model decode 200 tokens at 50–100 tok/s ≈ 2–4 s why you stream
Target TTFT p50 < ~1 s, p95 < ~2–3 s

Cost: ~4k input + ~200 output tokens at mid-tier prices ≈ 1–2 cents/request → ~$10–20k per million requests/month. Order-of-magnitude only; check current price sheets.

Code sketch: bounded agent loop (the war-story fix)

MAX_STEPS = 10
MAX_TOKENS_PER_REQUEST = 60_000

def run_agent(request, llm, tools, tracer):
    messages, used = [request], 0
    for step in range(MAX_STEPS):
        with tracer.span("llm.call", step=step) as span:
            resp = llm.chat(messages)
            used += resp.usage.total_tokens
            span.set("tokens", resp.usage.total_tokens)
        if resp.tool_call is None:
            return resp.text
        if used > MAX_TOKENS_PER_REQUEST:
            break
        result = tools.call(resp.tool_call)          # errors returned as data, not retried blindly
        messages += [resp.message, result.as_message()]
    return "I couldn't complete this request. It has been escalated."

Gateway-side: per-workload spend limit + circuit breaker + alert on anomalous span counts. Retries live in one place (gateway) with exponential backoff, jitter, retry budget, fallback model/provider.

5 interview questions

Q1. Design an AI assistant for a customer support team — give me the high-level architecture. Clarify first (users/QPS, latency, data sources and permissions, cost ceiling, advisory vs action-taking). Then walk the path: streaming client → gateway (identity, rate limits, budgets, fallback) → input guard → orchestrator with versioned prompts and bounded loop → context (retrieval, memory, tools) → routed model tier → output guard → tracing underneath → eval loop feeding a regression gate. Offer to go deep on any component.

Q2. Why put a gateway in front of model providers? Central credential custody, per-team rate limits and budgets, cost attribution, data-residency/provider policy enforcement, one place for retries with backoff and fallback, and consistent logging for audit. Without it, outages cascade and spend is invisible until the invoice.

Q3. What's the hardest part of running LLMs in production? Evaluation and change control, not the model call. Outputs are non-deterministic, providers update models, prompts change weekly; without a golden set built from real traffic gating every change, you can't tell whether things improved or regressed.

Q4. How do you stop an agent from running away with cost? Hard ceilings in the orchestrator (max steps, token budget per request), per-workload spend limits and circuit breakers at the gateway, errors returned to the model as data with limited retries, and alerts on trace anomalies (span count, tokens per request).

Q5. Hosted API or self-hosted open-weight model? Hosted: best models, no infra, pay per token, rate limits, provider-controlled changes (pin versions). Self-hosted: control, data locality, predictable cost at high steady utilization, but you own GPUs, autoscaling, and a serving engine like vLLM. Many systems do both behind one gateway and router.
