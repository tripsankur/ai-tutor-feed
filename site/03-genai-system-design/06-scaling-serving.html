Scaling & Multi-Tenancy: KV Cache, vLLM-Style Serving, Queues

17 min listen · What actually limits how many users one GPU can serve: KV-cache memory arithmetic, paged blocks and prefix sharing, continuous batching and chunked prefill, and the queues, token budgets, and fairness rules that keep one noisy tenant from ruining everyone else's latency.

Facts verified: 2026-09-25

One-sentence thesis

LLM serving capacity is bounded by KV-cache memory, not compute — so paged KV blocks, prefix sharing, continuous batching and chunked prefill decide how many users a GPU serves, while token-denominated budgets, latency-class lanes, fair queuing and queue-driven autoscaling decide whether a multi-tenant fleet stays fair.

Prefill vs decode

Prefill Decode
Work All prompt tokens in parallel One token per step
Bound by Compute Memory bandwidth (re-read weights each step)
Drives Time to first token (TTFT) Time per output token / inter-token latency
Batching Already parallel Amortizes weight reads across users → near-free extra users until KV memory runs out

Rule of thumb: 8B model FP16 ≈ 16 GB weights; at ~3 TB/s HBM, batch-1 decode ceiling ≈ a couple hundred tokens/s.

KV cache arithmetic (memorize)

bytes_per_token = 2 (K,V) × n_layers × n_kv_heads × head_dim × bytes_per_elem

Capacity example — 80 GB GPU, 8B model: at 0.9: 0.9 × 80 = 72 GB usable → −16 GB weights → −few GB activations/CUDA graphs → ~50 GB KV → ~400k tokens → ~200 concurrent 2k-token or ~50 concurrent 8k-token sequences. FP8 KV cache ≈ doubles it.

def kv_bytes_per_token(layers, kv_heads, head_dim, bytes_per=2):
    return 2 * layers * kv_heads * head_dim * bytes_per

per_tok = kv_bytes_per_token(32, 8, 128)          # 131072 = 128 KiB
kv_budget = 50 * 1024**3
print(kv_budget // per_tok)                        # ~409,600 tokens

vLLM-style serving mechanics

Tradeoff: bigger batch → more throughput, slower per-user tokens. Tune batch caps to SLOs.

Multi-tenancy rules

  1. Budget in tokens, not requests (Azure OpenAI and Bedrock quotas are TPM + RPM). Token bucket per tenant; charge estimated input on admit, settle actual output after.
  2. Latency-class lanes (interactive vs batch) + weighted fair queuing across tenants.
  3. Admission control / load shedding — 429 + Retry-After; clients use exponential backoff with jitter.
  4. Async batch for anything that can wait (hosted batch APIs ≈ 50% discount, up to ~24h turnaround; self-hosted batch lane off-peak).
  5. Multi-LoRA instead of per-tenant model copies.
  6. Scope prefix cache per tenant (cache_salt) — cross-tenant sharing is a timing side channel.

Autoscaling

  • 70B FP16 = 140 GB weights → ≥2×80 GB GPUs, usually TP=4/8; cold start = image pull + weight load + warmup = minutes.
  • Scale on queue wait / queue depth / KV-cache usage; never on GPU memory (pre-reserved), not on GPU util alone.
  • Warm minimum replicas; weights cached on local NVMe / shared volume near nodes.
  • Managed alternative: Azure OpenAI PTUs / Bedrock Provisioned Throughput — predictable latency, committed price; pays off at steady high utilization.

War story (generic)

40-tenant cluster; daily TTFT spike <1s → 8–9s. Cause: one tenant's batch of 50-page documents landing in another region's business morning; FCFS single queue, no chunked prefill, autoscaler on memory (always 90%). Fix: token budgets, batch lane + WFQ, chunked prefill, autoscale on queue wait + KV usage.

5 interview questions

Q1. How many concurrent users can one GPU serve for model X? Do the KV arithmetic: 2 × layers × KV heads × head_dim × bytes. 8B GQA FP16 = 128 KiB/token; 80 GB card − 16 GB weights − overhead ≈ 50 GB KV ≈ 400k tokens ≈ 200 × 2k-token sessions. Then check against latency SLOs.

Q2. Why is vLLM faster than naive HF-Transformers serving? Paged KV (waste 60–80% → <4%) enables bigger batches; continuous batching fills slots every step; prefix caching skips shared prefill; chunked prefill protects streaming latency.

Q3. Design serving for a multi-tenant LLM platform. Gateway with per-tenant token buckets; interactive vs batch lanes with WFQ; admission control with 429/Retry-After; KV-cache-aware routing; multi-LoRA; per-tenant cache_salt; autoscale on queue wait/KV usage with warm floor; batch APIs for deferrable work; P/D disaggregation at large scale.

Q4. Users report streams "freezing" mid-answer at peak. Cause? Long prefills monopolizing the GPU between decode steps, or KV exhaustion causing preemption. Fix with chunked prefill, caps on prompt length per lane, batch lane for long-document jobs, more KV capacity (FP8 KV, more replicas), or P/D disaggregation.

Q5. What should you autoscale an LLM fleet on? Queue wait time / depth and KV-cache block usage. GPU memory is pre-reserved (~90%) and GPU utilization is ambiguous. Keep a warm floor because cold starts take minutes.
