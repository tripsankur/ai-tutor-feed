Latency & Cost Engineering: Caching, Batching, Streaming, Model Routing

18 min listen · The pipe-to-the-engine mental model of LLM latency and cost: answer caches that let requests exit early, a router that forks easy traffic to small models, a batch side-channel at half price, prompt caching inside the engine, and a streaming tap at the end, with the numbers and failure modes of each.

Facts verified: 2026-09-25

One-sentence thesis

LLM latency is queue + prefill (input length) + output tokens × time-per-token, and cost is metered per input/output/cached token — so the levers are: measure per trace, trim tokens, prompt-cache a stable prefix, batch what nobody waits on, route easy traffic to small models, cache repeated answers carefully, and stream.

The mental image: the pipe to the engine

  • Pipe left → right into the big expensive engine (frontier model) at the far right.
  • Two gauges above: stopwatch (latency) on the left, cash counter (cost) on the right.
  • Exit hatch on top (left): answer cache — exact, then semantic.
  • Fork: the router — lower branch to a small engine below the pipe.
  • Side channel down to the canal: batching (batch APIs ~50% off; continuous batching when self-hosting).
  • Shelf inside the engine intake: prompt caching of the identical prefix.
  • Tap on the far right: streaming — tokens drip out as generated.

  • 500 output tokens at 50 tok/s ≈ 10 s regardless of everything else → output length is usually the biggest latency lever.
  • Reasoning models bill hidden thinking tokens as output; use effort/thinking-budget settings deliberately.
  • Metrics: TTFT, inter-token latency (ITL) / time per output token (TPOT), end-to-end, p50/p95.

Layout rule — stable first, variable last:

[system instructions]        <- stable
[tool definitions]           <- stable
[few-shot examples]          <- stable
[long reference docs]        <- stable-ish       <== cache breakpoint here
[conversation history]       <- grows
[retrieved chunks]           <- per request
[today's date, user name]    <- per request (NEVER at the top)
[user question]              <- per request

Semantic cache sketch

def answer(q, user):
    scope = (user.tenant_id, user.acl_fingerprint)          # never share across permission scopes
    hit = sem_cache.nearest(embed(q), scope=scope)
    if hit and hit.similarity >= THRESHOLD and not hit.source_changed():   # tune THRESHOLD on labelled pairs
        return hit.answer
    ans = llm_pipeline(q, user)
    sem_cache.put(embed(q), ans, scope=scope, sources=ans.source_ids, ttl=TTL)
    return ans

Routing facts

  • RouteLLM (LMSYS/Berkeley, 2024): >85% cost reduction on MT Bench while retaining ~95% of GPT-4 quality (benchmark-specific).
  • Microsoft Foundry model router: one deployment routing across a model pool; Balanced / Cost / Quality modes.
  • Amazon Bedrock Intelligent Prompt Routing: routes within a model family; AWS cites up to ~30% cost savings.

Key terms

Term Meaning
Prefill Model reads the prompt in parallel; drives TTFT
Decode Sequential token generation; drives total time
TTFT / ITL / TPOT Time to first token / gap between streamed tokens / average time per output token
Prompt (prefix) caching Reusing processed state of an identical prompt prefix
Semantic cache Returning a stored answer for a semantically similar past question
Continuous batching Iteration-level batching in serving engines (vLLM)
Batch API Async bulk submission, ~50% discount, results within 24h
Cascade Small model first, escalate on failed check
Speculative decoding Draft model proposes tokens, big model verifies — lowers ITL

5 interview questions

Q1. LLM costs grew 5× while traffic grew 2×. Diagnose. Instrument per-request input/output/cached tokens by model and step. Faster-than-usage growth usually means longer prompts or a collapsed prompt-cache hit rate (e.g. a per-request value like a timestamp added at the top of the prompt). Fix layout stable-first, dashboard + alert on cache hit rate, then trim tokens, batch offline work, and route.

Q2. p95 latency is 8 seconds. What do you do? Split TTFT from generation. High TTFT → queueing, prompt length, cache misses, serial retrieval/tools. High generation time → output length (cap, concise, reasoning effort), smaller/faster model on that route, speculative decoding if self-hosted. Stream so first words appear in ~1 s.

Q3. Explain prompt caching and how to get high hit rates. The provider/engine stores processed state for an exact prompt prefix; later requests with the same prefix skip re-reading it — cheaper (reads ~0.1× on one major provider; up to 90% off on another) and faster TTFT. Order prompts stable-first, variable-last; keep tool definitions and system prompt byte-identical; monitor hit rate.

Q4. Would you add a semantic cache? What are the risks? Only for repetitive traffic. Risks: semantically close but different-intent questions get wrong cached answers (tune threshold on labelled pairs, track wrong-hit rate), cross-tenant/permission leakage (scope keys by tenant + ACL), staleness (invalidate on source change).

Q5. How does model routing save money, and how can it hurt? Most traffic is easy; small models are several to tens of times cheaper and faster. Rules, learned routers, or cascades send only hard requests to the big model. Risk: averages hide a degraded hard tail — evaluate per segment, especially hard examples; cascades add latency on escalations.

Then I'd work the levers in order: trim tokens and tighten retrieval, restructure prompts stable-first for prompt caching and put cache hit rate on a dashboard, move offline workloads to batch A P Is at roughly half price, and route easy traffic to a smaller model, evaluated per segment so the hard tail doesn't regress." When they ask "p ninety-five latency is eight seconds, fix it", say: "Split it into time to first token and generation time. If time to first token is high, look at queueing, prompt length, and cache misses, and at slow steps before the model, like retrieval or tools running in series. If generation time is high, it's output length: cap it, ask for concise answers, check reasoning effort settings, consider a smaller or faster model for that route, or speculative decoding if we self-host. And stream, so first words appear in about a second." When they ask "would you add a semantic cache?", say: "Only if traffic repeats. I'd tune the similarity threshold on labelled pairs from our own traffic, scope the cache per tenant and permission set, and invalidate on source changes. And I'd track the wrong-answer rate on cache hits, not just the hit rate." [PAUSE 2s] ## Sixty-second recap Let's re-walk the pipe. Two gauges on the wall: a stopwatch and a cash counter. Inside the big engine on the far right: prefill reads the prompt, decode writes the answer one token at a time, and output length usually dominates the wait. On the left, the exit hatch: exact and semantic answer caches, with thresholds tuned on your own traffic, scoped by tenant, invalidated on source change. Then the fork: a router sending easy traffic down to a small engine, by rules, a learned router, or a cascade, always evaluated on the hard tail. Then the side channel down to the canal: batch A P Is at about half price for anything no human waits on, and continuous batching inside a self-hosted engine. Inside the big engine's intake, the shelf: prompt caching, cheap reads for an identical prefix, so stable content goes first and anything that changes goes last, and never, ever put a timestamp at the top. And on the far right, the tap: streaming, so first words arrive in about a second, with generation cancelled when the user walks away.
