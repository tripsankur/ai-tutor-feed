"Design a RAG System" — Interview Walkthrough

17 min listen · A full forty-five-minute interview walkthrough of designing a RAG system over millions of permissioned documents, built on one whiteboard: the offline indexing lane above the line, the online query lane below it, the index on the line between them, and the evaluation frame around the edge.

Facts verified: 2026-09-25

One-sentence thesis

A strong RAG design answer starts from requirements (permissions, freshness, traffic, cost of error), separates an incremental offline indexing lane from an online query lane that meet only at the index, enforces permissions as a pre-filter inside retrieval, and wraps everything in retrieval-vs-generation evaluation.

The mental image: the whiteboard with a line across it

  • Top-left box: requirements + back-of-envelope (start here, every time).
  • Above the line (offline, left → right): sources/connectors (content + metadata + ACLs) → parse (keep tables) → chunk (structure-aware, contextualized) → embed + keyword index.
  • On the line, center: the index cylinder — the only thing both lanes touch.
  • Below the line (online, left → right): question + identity → rewrite → hybrid retrieve with permission pre-filter → RRF → rerank → prompt assembly → generate → cite.
  • Frame around the board: evaluation — retrieval metrics separate from generation metrics.

Back-of-envelope (the scenario: 2M docs, 20k employees)

Quantity Estimate
Corpus tokens 2M docs × ~5k tokens ≈ 10B tokens
Chunks ~500 tokens + overlap → ~20M chunks
Raw vector size 20M × 1024 dims × 4 bytes ≈ 82 GB (int8 ≈ 20 GB) + index overhead
Embedding cost (one-time) order of hundreds of dollars with a small hosted embedding model
Traffic 20k users × 10 q/day = 200k/day → single-digit QPS avg, ~20–30 peak
Latency target first token within ~1–2 s

Code: reciprocal rank fusion

def rrf(result_lists, k=60):
    """result_lists: list of ranked lists of doc ids (e.g. [bm25_ids, vector_ids])."""
    scores = {}
    for ranked in result_lists:
        for rank, doc_id in enumerate(ranked, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

Permission pre-filter (pseudocode — filter is part of the search, not applied afterwards):

groups = idp.groups_for(user)                     # Entra ID / IAM Identity Center / IdP
hits = index.hybrid_search(query_text, query_vec,
                           filter={"acl_groups": {"any_of": groups}},
                           top_k=50)
top5 = reranker.rerank(query_text, hits)[:5]

Key terms

Term Meaning One-liner
Hybrid search Vector + keyword (BM25) in parallel "Meaning plus exact identifiers"
RRF Sum of 1/(k + rank) across lists, k≈60 "Fuse ranks, ignore incomparable scores"
Reranker (cross-encoder) Scores question+chunk jointly "Accurate but slow — run on 50, not 20M"
Contextual chunk Chunk prefixed with doc/section context Reported ~49% fewer retrieval failures, ~67% with reranking
ACL pre-filter Permission filter inside the search "Never filter after retrieval"
Query rewriting Turn follow-ups into standalone queries "What about the second one?" → searchable
Recall@k Share of questions whose gold chunk is in top k Retrieval-lane health
Faithfulness Answer claims supported by retrieved context Generation-lane health
Freshness SLA Time from source change to searchable Alert on it

Failure modes → fixes

Failure Fix
Index built by an all-reading service account, no ACLs Carry ACLs as metadata, pre-filter by user groups, audit cross-boundary
Stale / duplicate document versions Dedup at ingestion, only current version active, recency boost
Tables mangled Layout-aware parsing, keep tables whole
Codes / acronyms missed Hybrid search
Aggregation questions ("how many…") Route to a structured / text-to-SQL tool
Over-stuffed context Rerank, keep top 5–10, put best first

5 interview questions

Q1. Design a RAG system over 2M permissioned internal documents. Requirements first (corpus types, ACLs, freshness, traffic, latency, cost of error) + back-of-envelope. Offline lane: connectors with content+metadata+ACLs, layout-aware parsing, structure-aware contextual chunking, embeddings + BM25, incremental updates including deletes and permission changes. Online lane: rewrite, hybrid search with ACL pre-filter, RRF, rerank to top 5, grounded prompt with citations, streaming. Evaluation: retrieval and generation measured separately, golden set, regression gate.

Q2. How do you enforce document permissions? Ingest ACLs with content, store as chunk metadata, resolve user groups at query time from the IdP, apply as a pre-filter inside search. Propagate permission changes incrementally like content, and audit with cross-group probes. Post-filtering risks empty results and leaks.

Q3. Answers are wrong — how do you debug? Split the problem: measure recall@k on the labelled set. Low recall → parsing, chunking, hybrid search, reranker, query rewriting. Good recall but bad answers → prompt, context ordering, model. Use traces to see what was actually retrieved for failing questions.

Q4. Why hybrid search and a reranker? Vectors catch paraphrase but miss exact identifiers; BM25 catches identifiers but misses paraphrase. RRF merges without score normalization. A cross-encoder reranker is far more accurate than similarity and cheap enough on ~50 candidates; it's one of the highest-return additions.

Q5. When would you not use RAG? Small, stable corpora (a few hundred pages) fit in modern context windows; with prompt caching, reusing that context is cheap. RAG earns its complexity for large, frequently changing, or permission-bounded corpora. Aggregation questions belong to structured queries, not retrieval.
