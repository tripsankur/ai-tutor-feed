Track 2 · Databricks AI Stack · Episode 3

Model Serving: Endpoints, Provisioned Throughput, AI Gateway, External Models

17 min listen · The power-grid mental model for Databricks Model Serving — governed outlets, reserved generators for guaranteed throughput, and the AI Gateway substation that meters, limits, and reroutes every current — plus the pay-per-token-versus-provisioned-throughput decision and the governance model interviewers probe.

Facts verified: 2026-07-22 (Unity AI Gateway new standalone experience in Beta, Foundation Model APIs pay-per-token vs provisioned throughput, external model proxying, endpoint permission model)

One-sentence thesis

A serving endpoint is a governed REST API in front of any model — your own, a Databricks-hosted foundation model (pay-per-token or reserved provisioned throughput), or a proxied external model — and the AI Gateway is the single control plane every one of those calls passes through for metering, limits, routing, and guardrails.

Key terms

Term What it is Interview one-liner
Serving endpoint Governed REST API in front of a model Same shape regardless of what's behind it — swapping the model is a config change
Custom model tenant Your trained/fine-tuned model, UC-registered, deployed to serverless compute Scales to zero when idle; cold start of a few seconds on the first request after
Foundation Model APIs Databricks-hosted foundation models (Llama family, Databricks-trained models) Two purchase modes: pay-per-token or provisioned throughput
Pay-per-token Shared capacity, metered per token, no minimum Cheap and fast to start; not built for sustained high-throughput production traffic
Provisioned throughput (PT) Reserved capacity, guaranteed tokens/sec, sold in model-specific increments Bills in DBUs whether used or not; the answer when a latency SLA exists
External models Governed proxy to an outside provider (OpenAI, Anthropic) Provider key never leaves Databricks; the call looks identical to any other endpoint
Traffic splitting One endpoint routes a % of requests across served model versions Canary rollout pattern — same release discipline as a data pipeline
AI Gateway / Unity AI Gateway Enterprise control plane over all model (and now coding-agent) traffic; new standalone experience in Beta Metering, rate limits, load-balance/routing, automatic fallback, PII/safety guardrails — one front door
CAN MANAGE Permission to create/rewire an endpoint (routing, capacity, limits, fallback) Reserved for admins; everyone else gets query-only

Tradeoffs to volunteer

  1. Pay-per-token vs provisioned throughput — break-even on steady-state token volume; a latency SLA forces PT regardless of the break-even number; PT bills whether idle or not.
  2. Proxying external models adds a hop — worth it for centralised credentials, rate limits, cost attribution, payload logging, guardrails, automatic fallback: "centralise, govern, abstract," replayed on model access.
  3. Pay-per-token misused as production infrastructure — the classic failure: a prototype endpoint takes a real traffic spike and throttles exactly when the business needs it most.

Interview Q&A

Q1. What are the three kinds of tenant behind a Databricks serving endpoint? Your own custom model (UC-registered, deployed to serverless compute); a Databricks-hosted foundation model via Foundation Model APIs (pay-per-token or provisioned throughput); and an external model proxied to an outside provider (OpenAI, Anthropic). All three present the same governed REST API, so swapping one for another is a configuration change, not a rewrite.

Q2. How do you decide between pay-per-token and provisioned throughput? Estimate steady-state tokens/sec and find the break-even against reserved pricing; below it, pay-per-token is cheaper since you're not paying for idle capacity. Above it — or wherever a latency SLA already exists — use provisioned throughput: it guarantees tokens/sec but bills whether used or not.

Q3. Why proxy an external model through Databricks instead of calling the provider directly? Centralised credential custody (no keys scattered in app code), rate limits, usage/cost attribution, payload logging for audit, PII/safety guardrails, and automatic fallback to a backup model on a provider outage. The endpoint interface is identical either way, so nothing is lost in convenience by routing through the gateway.

Q4. What does the AI Gateway actually do, mechanically? Sits in front of every endpoint (now a standalone control plane, in Beta) and: logs usage and cost per call; enforces rate limits at the endpoint, user, or group level; load-balances or routes traffic across models both proactively (cost/performance routing) and reactively (fallback on failure); applies PII and safety guardrails to payloads in both directions.

Q5. How is access to model serving governed so guardrails can't be bypassed? Creating and reconfiguring an endpoint requires the CAN MANAGE permission, restricted to administrators; everyone else gets query-only access to call it. This stops anyone from routing around rate limits or guardrails by standing up their own direct connection to a provider.
