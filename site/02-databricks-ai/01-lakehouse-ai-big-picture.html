Track 2 · Databricks AI Stack · Episode 1

Lakehouse AI: The Big Picture (MLflow 3, UC, Serving, Vector Search — how pieces fit)

19 min listen · The five-floor tower mental model of the Databricks AI stack — Unity Catalog at the base, MLflow 3 observability, Model Serving and the AI Gateway, Vector Search, and Agent Bricks on top — with current 2026 product names and interview narrations.

Facts verified: 2026-07-17 (Agent Bricks, MLflow 3, AI Gateway GA, Lakeflow naming)

One-sentence thesis

Databricks built its AI platform out of the lakehouse, not next to it — every AI capability is Delta storage + Unity Catalog governance + serverless compute, reused.

The five-floor tower

flowchart TB
    A5["Floor 5 — Applications\nAgent Bricks (auto-optimise, MCP tool catalog) · Agent Evaluation (judges, review app) · AI Functions (ai_query) · Genie"]
    A4["Floor 4 — Retrieval\nVector Search (Delta Sync indexes)"]
    A3["Floor 3 — Serving\nEndpoints: custom · hosted foundation (PPT / provisioned throughput) · external proxies\nAI Gateway (GA): keys, rate limits, cost attribution, guardrails, auto-fallback"]
    A2["Floor 2 — Lifecycle & Observability\nMLflow 3: tracing (agents anywhere) · evaluation · prompt/app versioning"]
    A1["Ground floor — Delta + Unity Catalog\nmodels, functions/tools, indexes, volumes, eval sets = UC objects"]
    A5 --> A4 --> A3 --> A2 --> A1

Calling a model — the shape of it

from databricks.sdk import WorkspaceClient
client = WorkspaceClient().serving_endpoints.get_open_ai_client()

resp = client.chat.completions.create(
    model="my-gateway-endpoint",      # Llama, GPT, Claude — same interface, gateway-governed
    messages=[{"role": "user", "content": "Summarise this incident record..."}],
)

-- Batch inference from SQL (AI Functions)
SELECT complaint_id,
       ai_query('my-endpoint', CONCAT('Classify sentiment: ', complaint_text)) AS sentiment
FROM silver.complaints;

Tradeoffs to volunteer

  1. Integrated vs best-of-breed — tower wins governance/TCO/audit for enterprises already on Databricks; dedicated vector DBs may win raw retrieval latency/features.
  2. Pay-per-token vs provisioned throughput — break-even on steady-state token volume; PT also for latency guarantees; reserved bills whether used or not.
  3. Auto-optimisation ≠ absolution — Agent Bricks tunes against benchmarks; YOUR golden eval set + release gating remain your discipline.

Interview Q&A

Q1. How would you add document Q&A to an existing Databricks platform? Walk the tower bottom-up: docs in Delta/UC (governance day one) → Delta Sync Vector Search index (freshness automatic) → model behind endpoint via AI Gateway (keys, limits, cost attribution, payload logging, fallback) → agent whose tools/knowledge are UC objects, MLflow 3 tracing on → golden eval set + judge-gated releases + human review. Close: nothing sensitive leaves the perimeter — that's what passes a telco security review.

Q2. Why proxy external models through Databricks instead of calling OpenAI directly? Central credential custody, rate limits, cost attribution, payload logging for audit, PII/safety guardrails at the gateway, automatic provider fallback, provider swap as config change — "centralise, govern, abstract", replayed on model access.

Q3. What's Agent Bricks and how is it different from writing agent code? Declarative agent building with auto-optimisation: generates domain-specific synthetic data and task-aware benchmarks, evaluates candidates, tunes for quality+cost. Native MCP support and a UC-governed MCP tool catalog. You still own the golden eval set and release gates.

Q4. What does MLflow 3 add for GenAI over classic MLflow? Production-scale tracing (agents on any platform, not just Databricks), redesigned evaluation with judges + feedback APIs, and versioning extended to prompts and full applications.

Q5. Biggest production RAG risk this stack removes vs DIY? Stale embeddings — Delta Sync keeps the index consistent with the source table via CDF, removing the hand-rolled sync pipeline that drifts in DIY stacks.
