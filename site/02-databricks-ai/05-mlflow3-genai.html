Track 2 · Databricks AI Stack · Episode 5

MLflow 3 for GenAI: Tracing, Evals, Prompt & App Versioning

17 min listen · One floor of the lakehouse AI tower, opened up in full: how MLflow 3 turns every agent request into a recorded flight, every release into a certified inspection, and every prompt into a tail-numbered, rollback-ready registry citizen.

Facts verified: 2026-07-22

One-sentence thesis

MLflow 3 was redesigned around generative AI — it turns non-deterministic, multi-step agent behavior into something you can record (tracing), certify (evaluation), and roll back (prompt/app versioning), instead of just tracking one input-output prediction like classical MLflow did.

The mental image: the flight recorder and the control tower

  • Tracing = the black box in every aircraft — records every leg of every flight (request), continuously, at production scale.
  • Evaluation = the pre-flight inspection panel — judges (automated + human) check the aircraft against a checklist before and after it carries passengers.
  • Registry = the hangar — models, prompts, and full application versions sit tail-numbered, swappable by alias, rollback-ready.

Trace tree — one request, nested spans

flowchart TB
    R["Root span: user request\n(prompt in)"]
    RT["Retrieval span\n(vector search call)"]
    T1["Tool call span\n(e.g. lookup API)"]
    T2["Tool call span\n(e.g. calculation)"]
    G["Guardrail / safety check span"]
    M["Model synthesis span\n(final response)"]
    R --> RT
    R --> T1
    R --> T2
    R --> G
    R --> M
    RT -.->|tokens, latency logged| R
    T1 -.->|tokens, latency logged| R
    M -.->|tokens, latency logged| R

Every span carries inputs, outputs, token counts, and latency. Traces are searchable — e.g. "every trace that touched document X in the last hour" — which is how a stale-context bug gets found in minutes instead of inferred from tickets. Traces work for agents deployed anywhere (Databricks, another cloud, on-prem), making MLflow 3 the observability plane for the whole AI estate, not just the Databricks corner of it.

Evaluation loop — the inspection gate

flowchart LR
    D["Dev: golden test set"] --> H["Evaluation harness"]
    H --> S1["Built-in scorers\n(groundedness, relevance, safety)"]
    H --> S2["Custom scorers\n(domain-specific rules)"]
    H --> J["LLM judges"]
    S1 & S2 & J --> SC["Scores"]
    SC -->|pass| PROD["Promote to production alias"]
    SC -->|fail| DEV2["Back to dev"]
    PROD --> FB["Production traces"]
    FB --> HR["Human review / feedback API"]
    HR -->|checks judge agreement| J

Same scorers run in dev (against the golden set) and in production (against live traffic) — the bar doesn't relax after launch. LLM judges need periodic calibration against human review; an uncalibrated judge can systematically miss a failure mode (e.g. answers grounded in retrieved text but missing what the user actually needed).

Registry — the hangar

flowchart TB
    UC["Unity Catalog\n(governance ledger)"]
    subgraph Hangar["Registry"]
        MOD["Model versions"]
        PR["Prompt versions\n(git-like: commits, aliases)"]
        APP["Application versions\n(prompt + retrieval config + tools + model)"]
    end
    UC --> Hangar
    PR -->|alias: production| LIVE1["Live traffic"]
    APP -->|alias: production| LIVE2["Live traffic"]
    PR -.->|rollback: repoint alias| PR

Prompts get git-like versioning: commit messages, aliases (e.g. "production"), instant rollback by repointing the alias. Full application versions (prompt + retrieval config + tool wiring + model choice) are versioned as a unit, so "which prompt/app was live during the incident" is a factual lookup, not a guess. The registry's ledger is Unity Catalog — same access control, lineage, and audit as tables and models elsewhere on the platform.

Tradeoffs to volunteer

  1. Tracing cost at scale — every span, every token, every request logged is real storage/latency overhead. Tiered approach: sample routine traffic, but never sample away errors or flagged requests — capture those at 100%.
  2. Judges drift — an LLM judge can be systematically lenient or share a blind spot with the model family it's built from. Keep a rotating human-review sample checking judge agreement permanently, not just at launch.
  3. Registry ≠ governance by itself — versioning is just bookkeeping unless promotion to a "production" alias actually requires clearing the evaluation gate first. The dev-test-prod discipline has to be enforced operationally, the same as any other production release process.

Interview Q&A

Q1. How would you debug an agent that gave a wrong answer in production? Pull the trace for that request, walk the span tree top to bottom (prompt in, each retrieval/tool call, model response out), and find the exact leg where things went wrong — e.g., a retrieval call that surfaced a superseded document. No speculation; the trace has the answer.

Q2. How do you find out which prompt or application version was live during an incident? Because prompts and application versions are registry citizens with commit history, aliases, and timestamps (backed by Unity Catalog), that's a factual lookup against the registry ledger, not a reconstruction from memory or scattered commits.

Q3. How do you stop a bad prompt change from reaching customers? Nothing gets promoted to a "production" alias without clearing the evaluation harness first — same scorers, same golden set, dev-to-test-to-production discipline. Compare the candidate against the current production version side by side before promoting.

Q4. What's the risk of relying entirely on LLM judges for evaluation? Judges can drift or share a blind spot with the model family they're built from, systematically passing a failure mode a human would catch. Keep a rotating human-review sample permanently checking judge agreement, not just at launch — plus feedback-collection APIs so real users can flag production traces.

Q5. What does MLflow 3 add for GenAI that classical MLflow (experiment tracking) didn't have? Classical MLflow tracked one input-output model artifact per run. MLflow 3 is built for multi-step, non-deterministic agent behavior: production-scale tracing as nested trace trees (across any deployment platform), evaluation harnesses with built-in and custom scorers plus LLM judges and human feedback, and versioning extended from models to prompts and full application versions.
