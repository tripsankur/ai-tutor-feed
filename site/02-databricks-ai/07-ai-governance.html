Track 2 · Databricks AI Stack · Episode 7

AI Governance: UC Models & Functions, AI Gateway Guardrails, Lineage, Cost

17 min listen · The governed-city model from Unity Catalog, zoomed into its AI district: every model, function, index, and prompt is a catalog object under one council, the AI Gateway is the checkpoint every request crosses, and evaluation is the quality gate guardrails alone can't provide.

Facts verified: 2026-07-22

One-sentence thesis

Databricks did not build a parallel security model for AI. Every AI asset — model, UC function, vector index, prompt, application version — is a Unity Catalog securable, and every model call transits the AI Gateway, so AI inherits the exact grants, lineage, audit, and cost-attribution machinery that already governs data.

Tradeoffs to volunteer

  1. Latency tax — PII scanning and safety scoring at the gateway add a hop; budget for it rather than discover it in production.
  2. Governance only covers governed traffic — the single biggest real-world failure: a team with rights to create its own endpoint routes around the gateway entirely, and that traffic has no payload log, no PII scan, no rate limit. Locking endpoint creation + CAN MANAGE to admins is the control, not a formality.
  3. Fallback vs compliance — automatic provider fallback protects uptime; approve the entire fallback list against data-residency and retention terms, not just the primary provider.
  4. Cost attribution needs tagging discipline — the usage ledger is only as trustworthy as consistent service/workload tagging behind it.
  5. Eval gate as theatre — an evaluation gate that isn't wired into the actual promotion pipeline (i.e., a release can still ship without clearing it) is bookkeeping, not a safety net.

Interview Q&A

Q1. Design end-to-end AI governance for a regulated lakehouse. Walk the tower bottom-up. Foundation: every AI asset (model, UC function, vector index, prompt, app version) is a Unity Catalog securable with a three-part name — grants, ownership, lineage inherited; ABAC tags/policies protecting sensitive columns extend here too. Runtime: every model call transits the AI Gateway — centralized credentials, PII/safety guardrails both directions, payload logging, per-user rate limits, cost attribution into system tables, automatic fallback — with endpoint creation and manage rights locked to admins. Observability: lineage spans AI assets like data assets; usage/billing sit in queryable system tables, so a quarterly review is a scheduled query. Quality gate: agent evaluation (judges + human review) sits before any release. Close: nothing about AI needed a parallel security model — it inherited the one already governing data, which is why a bank or telco can sign off on it.

Q2. Why isn't "we have guardrails on the gateway" a sufficient answer in a real security review? Because guardrails only govern traffic that actually transits the gateway. If any team can create its own serving endpoint and hold CAN MANAGE on it, they can wire a private, ungoverned path to the same external provider — no PII scan, no payload log, no rate limit — and an audit trying to reconstruct what data left the building hits a wall at exactly that endpoint. The actual control is restricting endpoint creation and CAN MANAGE to admins; a well-designed gateway sitting next to an endpoint anyone can spin up is not a governance program.

Q3. How do ABAC tags protect data that's been embedded into a vector index or surfaced by a UC function tool? The governed tags and policies that mask a sensitive column in a table don't stop applying once that data is used to build AI assets. Tag the source document (e.g., sensitivity=PII), and lineage carries that classification forward — the same policy governs what a retrieval call is allowed to surface from it and what a UC function is allowed to hand back to an agent. Data isn't re-classified separately for its "AI copy."

Q4. What's the difference between what the AI Gateway blocks and what agent evaluation blocks? The gateway is the safety-and-cost floor: it stops unsafe or non-compliant content and uncontrolled spend, on every request, automatically. It says nothing about whether an answer is actually correct. Agent evaluation — LLM judges plus human review against a golden set — is the quality gate that catches a confidently wrong-but-safe answer before release. A regulated deployment needs both: guardrails at runtime, evaluation at release.

Q5. How do you turn "what did AI cost us last quarter, by team" into a fast, trustworthy answer? Every gateway call logs usage and cost into queryable system tables — system.billing.usage for spend, system.ai_gateway.usage for call-level detail — attributed by user, workload, and target model. Because it's Delta, the "quarterly AI cost report" is a scheduled SQL query against those tables, not a manual pull across scattered invoices, provided the tagging discipline behind service/workload attribution is enforced structurally.
