Track 2 · Databricks AI Stack · Episode 4

Agent Bricks: Building & Auto-Optimizing Agents, MCP Tool Catalog

17 min listen · Agent Bricks turns agent-building into a declarative brief instead of hand-tuned code: an auto-optimization loop invents synthetic data and task-aware benchmarks for your use case, tunes for quality and cost, and wires tools through a governed MCP catalog living in Unity Catalog.

Facts verified: 2026-07-22

One-sentence thesis

Agent Bricks replaces hand-tuned agent prompting with a closed loop: describe the job, and the platform generates domain-specific synthetic data and task-aware benchmarks, then searches model/prompt/retrieval configurations to auto-tune for quality and cost — while tools are governed, discoverable MCP objects that live in Unity Catalog.

The workshop image → the optimization loop

flowchart LR
    B["You: declare the brief\n(task + data/tools it can touch)"] --> M["Agent Bricks\n(the auto-tuning master)"]
    M --> S["Synthetic data generation\n(domain-specific, shaped to the brief)"]
    S --> E["Task-aware benchmarks\n(LLM-judge scored evals)"]
    E --> C["Candidate search\nmodel choice x prompt x retrieval x fine-tune"]
    C -->|score each candidate| SC["Scoreboard: quality + cost"]
    SC -->|keep best, repeat| C
    SC --> A["Tuned agent"]

What an Agent Bricks agent is made of

    Agent --> Model["Model = Serving endpoint\nvia AI Gateway (GA): keys, limits, cost attribution"]
    Agent --> Trace["Every step traced in MLflow 3"]

Tradeoffs to volunteer

  1. Auto-optimization ≠ absolution — it tunes against benchmarks built from your brief; a vague brief produces a blind spot in the benchmark. The golden evaluation set reflecting real business edge cases, and the release gate blocking regressions, remain your responsibility.
  2. Governance cuts both ways — a discoverable, reusable tool catalog is a win, but an over-permissioned tool becomes discoverable by every team, not just the one that built it. Scoping grants tightly at registration time is a human judgment call, not something the platform enforces for you.
  3. Maturity curve — native MCP support and the tool catalog are shipping and real; some surrounding ecosystem pieces (broader cross-org marketplace-style tool sharing) are newer and still stabilizing. Verify current rollout status before committing a timeline.
  4. When not to reach for it — exotic custom control flow that doesn't reduce to "describe the job, optimize the configuration," or a five-minute prototype, may still be faster hand-written. Agent Bricks earns its keep once the agent needs real measurement and re-tuning in production.

Scale (for color, not personal metrics)

Databricks reported more than 100,000 agents running on the platform, processing over a quadrillion tokens a year — the argument for why the tuning loop has to be automated: nobody hand-tunes prompts at that scale one thread at a time.

Interview Q&A

Q1. How is Agent Bricks actually different from writing agent code by hand? Hand-written code gets you exactly the configuration you wrote, with no measurement of whether another configuration would score better. Agent Bricks closes the loop: it generates domain-specific synthetic data and task-aware benchmarks for your declared task, searches across model choice, prompt structure, and retrieval settings, and keeps whichever configuration scores best on quality and cost together — automatically, not via manual trial and error.

Q2. Walk me through the MCP tool catalog's governance story. Tools are Model Context Protocol objects, natively supported, and every tool is really a governed function registered in Unity Catalog. That makes tools discoverable (browse instead of reinvent), permissioned (a tool only opens for an agent granted access), and audited (every call logged) — the same governance spine that already covers tables and models, extended to cover agent actions.

Q3. Is auto-optimization a substitute for an evaluation strategy? No. It optimizes against the benchmarks it's given, and those benchmarks are shaped by your declared brief. The golden evaluation set reflecting your actual hard cases, and the release gate that blocks a regression from shipping, are still owned by the team — the same dev-test-prod discipline applied to data pipeline releases today.

Q4. What is an Agent Bricks agent actually composed of, underneath the product name? Four already-familiar objects wired together: tools that are Unity Catalog functions, knowledge from a Delta Sync vector search index, a model behind a serving endpoint reached through the AI Gateway, and every step traced in MLflow 3. Nothing about "agent" introduces a new governance model — it composes objects that already had one.

Q5. When would you NOT use Agent Bricks? When control flow is genuinely exotic and doesn't reduce to a declarative brief plus configuration search, or at the earliest prototype stage where the goal is just to see if an idea holds together. Agent Bricks pays off once the agent is past prototype and needs real, ongoing measurement and tuning in production.
