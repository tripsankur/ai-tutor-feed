Databricks Vector Search Internals (Delta Sync, embeddings, hybrid search)

17 min listen · Inside floor four of the tower: how Databricks AI Search turns documents into searchable coordinates with H N S W, keeps that index fresh automatically with Delta Sync, and where hybrid search and storage-optimized endpoints change the calculus.

Facts verified: 2026-07-22 (Databricks AI Search branding, HNSW + L2 distance mechanics, Delta Sync vs Direct Vector Access vs Full-Text Search index types, standard vs storage-optimized endpoint tradeoffs, hybrid search GA + reciprocal rank fusion, reranking GA)

Correction vs. episode brief: hybrid search (vector + full-text via reciprocal rank fusion) is generally available (GA since Aug 2024, confirmed current), not Beta — confirmed against docs.databricks.com/aws/en/ai-search/query-ai-search. The Beta feature today is a separate, newer index type: a pure Full-Text Search index (BM25-only, no embeddings, storage-optimized endpoints only). Reranking is also GA. The script and this note reflect the verified GA status.

One-sentence thesis

Databricks AI Search turns "find the right passage" into a geometry problem (embeddings + HNSW approximate nearest neighbor) and then solves the freshness problem that geometry creates by making the index a self-syncing projection of a Delta table (Delta Sync), not a pipeline you hand-maintain.

Index / endpoint / source flow

Databricks AI Search Current name (formerly Databricks Vector Search / Mosaic AI Vector Search) Same engine, name evolved like DLT → Lakeflow Declarative Pipelines
HNSW Hierarchical Navigable Small World — layered graph for approximate nearest neighbor search "Sparse long-range layer on top for a coarse fix, dense exact layer at the bottom for precision"

Direct Vector Access index You upsert vectors + metadata yourself via REST/SDK; no auto-sync Right choice when vectors originate outside a Delta table
Full-Text Search index (Beta) Pure BM25 keyword index, no embeddings, storage-optimized endpoints only New, narrower sibling of hybrid search
Endpoint Serving cluster hosting one or more indexes Standard vs Storage-Optimized — a capacity/latency/compliance tradeoff, not just a size setting

Storage-optimized endpoint Scales toward ~1B vectors, lower DBU cost per row, 10–20x faster indexing, but ~250ms higher query latency, no continuous sync (batch refresh only), no CMK/FedRAMP, ANN results capped ~200 vs 10,000 Choose when row count is the dominant cost driver and latency/compliance can flex

Index creation and query — the shape of it

from databricks.vector_search.client import VectorSearchClient

client = VectorSearchClient()

# Delta Sync index: Databricks manages embedding + sync
client.create_delta_sync_index(
    endpoint_name="my-endpoint",
    index_name="catalog.schema.support_tickets_index",
    source_table_name="catalog.schema.support_tickets",
    pipeline_type="TRIGGERED",              # or CONTINUOUS
    primary_key="ticket_id",
    embedding_source_column="ticket_body",
    embedding_model_endpoint_name="databricks-gte-large-en",
)

index = client.get_index("my-endpoint", "catalog.schema.support_tickets_index")

results = index.similarity_search(
    query_text="how do I cancel a subscription",
    columns=["ticket_id", "ticket_body"],
    num_results=5,
    query_type="HYBRID",                    # "ANN" or "HYBRID"
)

-- Querying an index directly from SQL
SELECT *
FROM VECTOR_SEARCH(
  index      => 'catalog.schema.support_tickets_index',
  query_text => 'how do I cancel a subscription',
  num_results => 5
);

Tradeoffs to volunteer

  1. Recall vs. latency is a tunable dial, not a one-time setting. Widening the search beam through the HNSW layers catches more true nearest neighbors at the cost of milliseconds; tune it against measured recall on your own data, not a default copied from a blog post.
  2. Delta Sync is "minutes," not "instant." Real production guarantee, but demo scripts and incident timelines both need to account for the propagation window off the change data feed.
  3. Standard vs. storage-optimized is a compliance/latency/cost triangle, not just a row-count switch: storage-optimized drops CMK, FedRAMP, and continuous sync, and adds roughly 250ms of query latency, in exchange for much lower per-row cost at huge scale.
  4. Hybrid search costs more than pure ANN (two retrieval passes fused), so it's the right general-purpose default, but a narrow, keyword-heavy, structured lookup (error codes, part numbers only) may do just as well on keyword search alone, more cheaply.

Interview Q&A

Q1. Why does Delta Sync eliminate the classic "stale embeddings" RAG failure? In a hand-rolled stack, the vector database drifts from the source documents because nobody's job is to keep them in sync — deleted or edited documents keep getting cited. Delta Sync watches the source Delta table's change data feed and re-embeds/re-syncs automatically within minutes; freshness becomes a platform guarantee like ACID was for the table, not a pipeline you maintain.

Q2. Explain the HNSW recall-vs-latency tradeoff and how you'd tune it. HNSW is a layered graph: a sparse top layer for long-range coarse jumps, denser lower layers for local refinement, giving approximate — not exact — nearest neighbors. Searching more candidates per layer (a wider beam) raises recall but costs latency. There's no universal correct setting; measure recall on your own query distribution and tune the beam width against your latency budget.

Q3. When would you choose a storage-optimized endpoint over standard? When row count (hundreds of millions to roughly a billion vectors) is the dominant cost driver, DBU cost per row matters more than per-query latency, and you don't need continuous (sub-minute) sync, customer-managed keys, or FedRAMP — storage-optimized trades roughly 250ms of extra latency and batch-only refresh for materially lower cost at scale.

Q4. When is hybrid search worth the extra compute over pure vector search? Almost always for general-purpose, user-facing retrieval — real queries mix semantic intent with exact terms (product names, error codes, order numbers) that embeddings under-serve. Hybrid search runs ANN and full-text in parallel and merges via Reciprocal Rank Fusion. For narrow, structured, keyword-only lookups, plain keyword search alone may be cheaper and sufficient.

Q5. Delta Sync index vs. Direct Vector Access index — how do you decide? Default to Delta Sync whenever the source of truth is a Delta table — automatic re-embedding and sync, no maintenance. Choose Direct Vector Access when vectors are produced outside Delta (an external pipeline, a non-Databricks system, or a write pattern Delta Sync doesn't support) and you're willing to own upserts and deletes yourself via the REST/SDK API.
